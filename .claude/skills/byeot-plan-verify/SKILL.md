# 기획 대조 — core 가 올린 해시를 plan 글과 줄마다 댄다

총괄 끝 걸음(`byeot-walk`)은 판을 걸어 잰다. 이 절차는 **글이 그대로 들었나 · 맞는 때에 서나**를 본다. 손가락 끊김 · 회귀는 core · 총괄 몫이다.

## 1. 해시를 떠 온다

- `git fetch origin` (pull 이 아니다) → `git log --oneline -6 origin/main` → `git show --stat <해시>`.
- `git show <해시> -- <바뀐 파일들>` 로 diff 를 먼저 읽는다(커밋 글의 «무엇이 들었나»와 같은지).
- 통째로 대 볼 파일은 `git show <해시>:<파일> > <scratchpad>/<짧은 이름>` 으로 떠서 grep 한다.
  - 까닭: 작업 트리는 여러 창이 함께 써서 남의 미완료가 섞여 있다. 해시를 떠야 core 가 올린 판 그대로를 잰다.
- 작업 트리의 파일은 고치지도 · checkout 하지도 않는다.

## 2. 글을 글자 그대로 댄다

- plan 이 넘긴 글(가장 새 `docs/handoff/plan-to-core-*.md` · SendMessage 로 넘긴 글)을 옆에 놓는다.
- 줄마다 grep: 글자 · 띄어쓰기 · 이모지 앞뒤 칸 · 문장부호까지. «뜻 같음»도 어긋남이다.
- 글이 서는 자리를 다 찾는다. 같은 배너가 두 곳에서 서면(예: commitPlace · startPhonePlacePot) 둘 다 바뀌었나. 옛 글을 grep 해 남은 자리가 주석 말고 0 인가.
- 코드로만 찾은 자리(그리는 함수 · `$('id')`)는 그 요소가 HTML 에 정말 있는지 `id="…"` 를 grep 하고 넘긴다. 걷힌 요소의 그리는 함수가 남아 있기도 하다(158a35a4 `#questBackHint` — dfe592fe 에서 걷힘 · `git log -S'id="…"'`).
- 상수(`*_KO`)로 들었으면 상수와 부르는 곳을 둘 다 본다. 돈 꼴(wonKo 등)이 예전 글과 같은 꼴인지 함수 정의를 읽는다.

## 3. 갈래 · 자를 댄다

- 갈래 차례: plan 이 말한 자리(예: «bagPots 뒤 · seeds===0 두 갈래 앞»)와 같은가. 먼저 서는 줄(예: 어두운 자리 ⚠)이 그대로 먼저인가.
- 쓰는 자: 갈래를 가르는 값이 plan 이 말한 것과 **같은 것을 세는가**. 다른 함수 이름이면 정본을 읽어 같은 목록을 세는지 본다(예: «오는 중» = `shopStatus(S).orders` = shop.js `incomingOf` 와 같은 orders).
  - 같은 낱말을 내는 자리가 여럿이면 값의 **날 · 날씨 · 철 · 등 수**까지 댄다. 같은 함수 · 같은 문턱이어도 한쪽은 내일 날씨, 한쪽은 보통 날이면 다른 자다(0400a798 목록 «밝음» ↔ 할 일 ㉮).
  - 칸을 하나 골라 재는 줄(«가장 밝은 칸» 등)은 고르는 함수의 순서도 그 자로 댄다(158a35a4 `guideBrightSlot`).
- 빌려 쓴 칸: 새 글이 기존 칸(예: `waitDo`)에 실렸으면 그 칸을 읽는 곳(머리 · 표 · 이사 줄 · 칩 고르기)을 다 grep 해, 그 칸의 뜻(«먼저 할 손»)이 새 글에도 참인지 본다(158a35a4 C9 머리 «지금 할 것 —»).
- 옮긴 셈: 함수 안 셈을 모듈 자리 함수로 옮겼으면(예: updateHint 안 셈 → `unpackCountsNow`) 새 함수가 부르는 이름이 모두 모듈 자리에 있는지 grep 한다(`^function 이름` · `^const 이름`). 함수 안 지역 이름이었으면 새 자리에서 던지고 catch 로 조용히 false 가 된다. 바깥 문(예: `ts = S.tutorial`)도 같은 것을 가리키는지 본다.
- 새 스냅샷 · 하네스 칸: 하네스에 칸이 없을 때 떨어지는 값(`num` → 0)과 그때 서는 글이 참인가.
- 참인 조건: plan 이 줄마다 단 «참인 조건»과 코드 조건이 같은가. 코드 조건이 더 넓으면 그 판에서 거짓 줄이 선다.
  - 수를 세는 줄은 그 셈에 드는 것을 방 · 가구 데이터에서 꼽아 본다. 조건이 같아도 글 낱말이 그것을 다 말하지 않으면 거짓 줄이다(f373262a P8 «벽 · 창에 붙인 가구 2개» = 처음부터 있던 창턱 받침 · 천장등).
- 글 규칙: 몬이 줄에 수가 없나 · 폰 한 줄 · 할 일 글 길이 문턱(`src/game/dialogue.js` 주석) 안인가.

## 4. 사진을 직접 본다

- core 커밋 글에서 자 이름과 회귀 판 이름을 읽고, 사진을 `find` 로 찾는다(대개 `C:/Users/pc/AppData/Local/Temp/byeot-core/<판>/shots_<자>/`). Temp 는 쓸리기도 하니 못 찾으면 core 에 묻는다.
- **고친 판**(회귀 판) 사진을 연다. 작업 전 판 사진과 헷갈리지 않는다.
- 사진에서 본다: 글이 그대로인가 · 줄바꿈이 낱말을 자르지 않나 · 같은 화면의 다른 글(손가락 · 할 일 · 몬이 · 배너)과 다른 말을 하지 않나(거짓 줄).
- 다른 말을 하는 사진이 이미 잡힌 다음 묶음의 몫이면 «다음 묶음의 작업 전 빨강으로 쓰라»고 넘긴다.
- 자 기록(`*.out`)도 읽는다. plan 글이 걸린 칸은 단언이 없고 찍기만 한 값(빈 배열 · null)이어도 본다. 사진에 안 보이는 글(대사 · 칩)은 기록이 유일한 증거다(0400a798 P5 대사 칸 `lines5: []`).

## 5. 넘긴다

- 어긋남 0: core 에 «<해시> 대 보았습니다 — plan 글과 어긋남 0 입니다» + 본 것을 줄마다(글 · 자리 · 갈래 · 자 · 사진). 총괄이 청한 글이면 총괄에도 짧게.
- 어긋남이 있으면 줄마다 이 꼴로:

```
plan → core: <해시> 대 보았습니다 — 어긋남 n
1. <파일:줄> · <무엇>
   plan 글: «…»
   게임 글: «…»
   고칠 쪽: core(게임) / plan(글을 다시 냄) / 총괄(값 · 문턱 · 판단) — 까닭 한 줄
2. …
맞는 것: <줄마다 짧게>
<언어 규칙 줄>
```

- 코드로만 본 갈림(판을 안 잼)은 «코드 위 갈림 · 판 못 잼»으로 적고 거짓 줄이라 단정하지 않는다. 그 갈림이 실제 방 데이터(걸이 · 창 · 가구 자리)에서 나는지 먼저 본다.
- 고칠 쪽 가르기:
  - plan 글이 맞고 게임 글이 다르면 core.
  - 게임이 plan 이 못 본 갈래 · 자를 드러내 plan 글이 그 판에서 거짓이 되면 plan 이 글을 다시 내 core 에 넘긴다(`byeot-plan-lines`).
  - 값 · 문턱 · 새 계통이 걸리면 총괄(값은 박사님 몫).
- 박사님께는 존댓말로 짧게: 무엇을 댔고 · 어긋남 · 남은 것.
- 다른 창에 보내는 말 끝에는 언어 규칙 줄을 그대로 붙인다.
- 총괄 창이 꺼져 있으면 `docs/handoff/plan-to-master.md` 맨 위에 날짜 절을 더하고 push 한다.

## 하지 않는 것

- 게임 코드를 고치지 않는다(core 몫). 값을 바꾸지 않는다.
- 헤드리스 크롬으로 따로 걷지 않는다 — 걸어서 재야 하면 총괄 `byeot-walk`.
