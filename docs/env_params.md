# 빛 외 파라미터 — 어디에 어떻게 끼우나

**2026-08-03 신설.** 온도·습도·물의 **설계는 이미 있다**(`env_difficulty_axis.md`).
이 문서는 그 설계를 **지금 코드의 어느 계산에 붙이는가**만 정한다.

> ⚠ **새 설계를 만들지 않았다.** `env_difficulty_axis.md` §2의
> *"생장률 = 빛계수 × 온도계수"* · *"마름속도 = f(빛, 온도, 습도)"* · *"물주기 = 유일한 능동 행동"*
> 세 줄이 전제이고, 이 문서는 그것을 **2026-08-03 에 바뀐 성숙 판정 구조**에 대입한 것이다.

# 0. ★★ 경계 — 스토리 모드에는 안 들어간다

**이 문서 전체가 스토리 모드 밖의 설계다.**

`story_arc.md` 확정: *"튜토 끝나고 이어지는 스토리 모드는 **초보 모드**인 거야. 금방 끝나는."*
그리고 `env_difficulty_axis.md` §1의 시뮬 깊이 축에서 **초보(=기본)는 빛 하나**다.

```
① 반지하 → ② 탈출 → ③ 원룸 → ④ 내 집 마련 엔딩      ← 빛만. 물·온도·습도 없음
                                    ↓
                              본편 — 직업을 고르고 시작
                                    ↓
                              시뮬 깊이를 고른다 ← ★여기부터가 이 문서다
```

| | 스토리(초보) | 표준 | 심화 | 실전 |
|---|---|---|---|---|
| 빛 | ✅ | ✅ | ✅ | ✅ |
| **물** | ❌ | ✅ | ✅ | ✅ |
| **온도** | ❌ | ❌ | ✅ | ✅ |
| **습도** | ❌ | ❌ | ❌ | ✅ |
| 잎 손실 | ❌ (`drop_enabled=false`) | 선택 | ✅ | ✅ |

★ `env_difficulty_axis.md` §1의 표에서 **「기본」에 있던 물을 「표준」으로 옮겼다.**
그 문서는 *"기본 = 빛 + 물"* 이라고 적었는데, 그 뒤 `story_arc.md` 가
**스토리 전체를 초보로 확정**했다. 스토리에 물이 있으면 튜토가 두 겹이 된다.

> **이건 기획 변경이 아니라 층위 정리다.** *"빛 + 물이면 게임이 성립한다"* 는 판단은 그대로다.
> 다만 **스토리는 그 게임의 앞 절반만** 쓴다. `env_difficulty_axis.md` 본문은 안 고쳤다.

## ★ 왜 물이 스토리에 없어야 하나 — 학습이 한 번에 하나여야 한다

첫 플레이의 학습 내용은 *"자리가 등보다 크다"* 하나다(`first_play.md`).
물을 같이 주면 **오늘 안 자란 게 어두워서인지 말라서인지**를 못 가린다.
`STATUS` core 가 이미 그 문제를 적어 두었다 — *"옮겼는데 며칠째 그대로"* 를
말 피드백이 설명해야 한다는 것. 원인이 둘이면 그 설명이 안 된다.

# 1. ★★ 어느 손잡이에 곱하나 — 이 문서의 핵심

2026-08-03 확정으로 성숙 판정의 손잡이가 둘이 됐다(`plan-to-growth.md`).

| 손잡이 | 정하는 것 | 지금 값 |
|---|---|---|
| **성숙 게이지 속도** | 기회가 **얼마나 자주** 오나 | `gauge_days 12` · 빛 계수 `0.6 ~ 1.4` |
| **굴림 확률** | 그 기회를 **잡을 가능성** | `10% ~ 90%` |

## 확정 — 3분할

```
온도  →  게이지 속도            (대사 속도)
물    →  게이지 속도 + 하한 게이트  (빛의 min 3.0 과 같은 구조)
습도  →  굴림 확률              (형태 품질)
```

### ① 온도가 **속도**인 이유

| 근거 | |
|---|---|
| **기존 문서와 일치** | `env_difficulty_axis.md` §2가 *"**생장률** = 빛계수 × 온도계수"* 라고 적었다. 생장률은 속도다. 그대로 옮기면 된다 |
| 물리 | 온도는 대사 **속도**를 정한다. 추우면 모든 게 느려지고, 아주 추우면 손상이다. 결과의 질이 아니라 진행의 빠르기다 |
| ★ **잠금 우회 방지** | 온도를 확률에 걸면 *"추운 데 두면 중간잎이 유지된다"* 가 성립한다. 2026-08-03 확정이 **3% 잠금을 환경 무관으로 못 박은 이유**가 바로 그런 농사를 막는 것이었다. 온도를 확률에 태우면 그 방어가 뚫린다 |

### ② 물이 **속도 + 게이트**인 이유

| 근거 | |
|---|---|
| ★ **능동 행동이 성립하려면** | `env_difficulty_axis.md` §2: *"물주기 = 유일한 능동 행동."* 안 하면 벌이 있고, 하면 즉시 돌아와야 행동이다. 속도만 깎으면 벌이 며칠 뒤에 보인다 — **게이트여야 "마른 날은 아예 안 자란다"가 그날 읽힌다** |
| ★ **새 구조가 아니다** | 빛에는 이미 `min 3.0` 게이트가 있다(growth BLOCKER 확정 — *저광이면 형태 진행이 멈춘다*). 물은 **같은 코드 자리**를 쓴다. 축이 하나 늘 뿐 구조가 안 는다 |
| 물리 | 완전 건조는 기공을 닫아 광합성 자체를 멈춘다. 「느려짐」이 아니라 「멈춤」이 맞다 |

### ③ 습도가 **확률**인 이유

| 근거 | |
|---|---|
| 물리 | 습도는 속도가 아니라 **형태의 질**에 관여한다. 건조하면 새순이 제대로 안 펴지고 가장자리가 갈변한다. 몬스테라 원산지가 열대우림(80%+)이고 한국 겨울 실내는 30~40%다 |
| ★ 축이 겹치지 않는다 | 온도·물이 속도를 잡았으니 습도는 결과를 잡는다. 셋이 같은 손잡이에 몰리면 **어느 변수가 뭘 했는지 못 가린다** |

## ★★ 확률에 곱하는 축은 **습도 하나뿐이다** — 하한 10%가 보장이 안 되기 때문

이게 3분할의 진짜 이유다.

2026-08-03 확정: *"**10% 하한. 0 이 아니다.** 0 이면 어두운 자리에 처박아 두는 것만으로
중간잎이 보장돼 운이 아니라 설정이 된다."*

축을 여러 개 곱하면 하한이 겹겹이 깎여 **실질 0에 가까워진다** — 막으려던 것이 돌아온다.

```
❌ p = p_light × f_temp × f_humid × f_water        0.10 × 0.6 × 0.7 × 0.5 = 0.021  ← 2%. 사실상 0
✅ p = clamp(p_light × f_humid, 0.10, 0.90)        하한을 ★맨 마지막에 건다
```

### 확정 — 계산 순서

```
1. p = 빛으로 10~90% 보간               (2026-08-03 규칙 그대로)
2. p = p × f_humidity                   (0.7 ~ 1.0)
3. p = p × over_max_mult                (과광일 때만. 기존 규칙)
4. ★ p = clamp(p, roll_lo, roll_hi)     하한·상한을 마지막에
```

★ **4번이 새로 필요해진 한 줄이다.** 지금은 보간이 이미 10~90 안에서 나오므로 clamp 가 없어도 되는데,
습도가 곱해지면 밖으로 나간다. **곱을 하나라도 붙이는 순간 clamp 가 필수**가 된다.

# 2. 물 — 유일한 능동 행동

## 확정 — 수분 게이지 하나

`leaf-to-plan.md` §4-① 의 요청에 대한 답이다. **횟수가 아니라 게이지**로 간다.

> *"하루 3~4번 물주기는 시간 모드에 안 맞습니다. 수분 게이지로 통일하는 것을 제안합니다."*

**동의한다.** 이유가 leaf 가 적은 그대로다 — 점핑·배속·1:1 에서 횟수는 성립하지 않는다.
게이지면 **모드와 무관**하다. 그리고 `time_modes.md` §0의 *"켜둔 시간만 간다"* 와도 맞는다.

## 확정 — 물은 **공통 시스템**이다

`leaf-to-plan.md` §4-② 의 요청에 대한 답이다. **동의한다.**

```
수분 게이지  0 ~ 100        모든 심긴 개체가 하나씩 갖는다
물주기       100 으로 채운다  ← 능동 행동
콩나물       ★게이지가 유난히 빨리 떨어지는 작물   (leaf 제안 그대로)
물꽂이       ★게이지 없음. 물속이다              (propagation.md §3)
```

★ 작물마다 따로 만들지 않는다. **마름속도 계수 하나가 작물 성격을 표현한다.**
`f_light` 가 종마다 `need_mult` 로 갈리는 것과 같은 방식이라 새 구조가 아니다.

## 밴드 — 넷

| 수분 | 상태 | 효과 |
|---|---|---|
| 100 ~ 85 | 갓 준 물 | 과습 위험 구간 (연속으로 채우면 누적) |
| **85 ~ 25** | **적정** | 계수 **1.0** |
| 25 ~ 0 | 마름 | 게이지 속도 **1.0 → 0** 선형 |
| **0** | 완전 건조 | ★ **게이트 — 진행 정지** |

★ **왜 25에서 경고가 시작되나.** 실제로 화분은 흙 위 2~3cm 가 마르면 줄 때다 — 게이지로 상위 1/4.
그리고 플레이어에게 **손 쓸 시간**이 있어야 한다. 마름속도가 하루 10%면 25%에서 **2.5일 여유**다.
배속에서도 놓치지 않는 폭이다.

## 마름속도 — `env_difficulty_axis.md` 의 "어두우면 안 마른다"를 숫자로

```
마름속도 = base × f(DLI) × f(온도) × f(습도)      ← 문서 원문 그대로
```

**후보값** (base = 하루 10%, 몬스테라 기준):

| 자리 | DLI | 마름속도 | 관수 간격 |
|---|---|---|---|
| 밝은 자리(등 + 좋은 칸) | 12.16 | 하루 **14%** | **7일** |
| 반지하 창턱 | 3.77 | 하루 **10%** | **10일** |
| 어두운 구석 | 0.5 | 하루 **6%** | **17일** |

★ **왜 이 폭인가** — 실내 몬스테라 관수 간격은 여름 7~10일, 겨울 14~20일이 실제다.
그 범위가 그대로 나온다. 억지로 벌리거나 좁히지 않았다.

## ★★ 그래서 과습이 **결과로** 나온다

```
어두운 자리에 두었다  →  안 마른다  →  ★평소 간격으로 주면 과습
```

`env_difficulty_axis.md` §2가 예고한 그대로다 —
*"「어두운 방에선 물을 덜 줘야 한다」가 규칙이 아니라 결과로 나온다. 이게 좋은 설계다."*
`hidden_depth.md` §2-③ 이 *"물이 들어오면 좋은 비밀이 하나 자동으로 생긴다"* 고 적은 것도 이것이다.

**규칙을 하나도 안 쓴다.** 마름속도가 빛의 함수이기만 하면 저절로 성립한다.

## 과습의 벌 — ⏸ 후보

| 후보 | | 판단 기준 |
|---|---|---|
| **㉮ 게이지 속도 감소가 며칠 지속** | 뿌리가 상해 회복에 시간이 걸린다. **죽지 않는다** | 표준 모드에 맞다 |
| ㉯ 잎 처짐 표시 + ㉮ | 화면에 보인다 | 새 렌더 상태가 하나 는다 |
| ㉰ 고사 | *"실내식물 사망 원인 1위가 과습"* 이 성립한다 | **고수 모드 전용.** 표준에 넣으면 벌이 과하다 |

**㉮를 기본으로 두고 ㉰는 고수 모드에서 켠다.** 잎 손실(`drop_enabled`)이 이미 그 구조다 —
같은 토글에 얹으면 축이 안 는다.

# 3. 온도 — 게이지 속도 계수

`env_difficulty_axis.md` §2의 표를 **그대로** 계수로 옮긴다. 경계를 안 바꿨다.

| 온도 | 문서의 상태 | 게이지 속도 계수 | 그 밖에 |
|---|---|---|---|
| **18 ~ 30℃** | **최적** | **1.0** | — |
| 15 ~ 18℃ | (최적 밖) | 0.6 | — |
| 10 ~ 15℃ | **정체** | **0.2** | — |
| 5 ~ 10℃ | **손상** | **0** | 고수 모드에서 잎 손상 |
| ~ 5℃ | **고사** | **0** | 고수 모드에서 고사 |

★ 15℃ 이하를 0 이 아니라 0.2 로 둔 이유 — 문서가 *"정체"* 라고 했지 *"손상"* 이라고 하지 않았다.
0 으로 두면 손상 구간과 화면에서 구분이 안 된다. **0.2 면 「거의 안 자란다」가 보이고 되돌아온다.**

## ★★ 온도가 들어오는 순간 깨지는 것 — 그게 목적이다

`env_difficulty_axis.md` §2:

| | 빛 | 온도 |
|---|---|---|
| 큰 창 | 유리함 | 겨울에 **춥다** |
| 온실 | 최상 | **난방비 폭발** |

**「창이 크면 무조건 좋다」가 깨진다.** 그리고 `hidden_depth.md` §2-① 이
*"⚠ 단 온도가 들어오면 바뀐다 — 계절별 배치가 진짜 비밀이 된다"* 고 예고해 두었다.

지금은 천공이 방향 무관 균일 휘도라 **모든 자리가 같은 계수로 어두워져 순위가 안 바뀐다.**
온도는 **자리마다 다르게** 걸리므로(창가는 겨울에 춥다) 순위가 실제로 뒤집힌다.
→ **여름 명당과 겨울 명당이 갈린다.** 이게 온도를 넣는 유일한 값어치다.

## ★ 난방은 **선택 설비**로 둔다 — 축을 지키기 위해

난방비는 **경제 항목**이라, 그냥 두면 환경 축이 경제 축을 건드려 §4의 직교가 깨진다.

```
식물등    안 사도 된다. 사면 빛이 보완된다   ← 이미 있는 선례
난방      안 사도 된다. 사면 겨울 계수가 회복된다
```

`story_arc.md` §4가 식물등을 *"정답이 아니라 선택"* 으로 확정한 구조를 그대로 쓴다.
**플레이어가 고른 만큼만** 환경이 경제에 닿는다.

⏸ 값은 미정 — 난방기 가격·소비전력. **식물등과 같은 방식으로 실측해서 잡는다**
  (값·전기세는 `src/game/tutorial.js §TUTORIAL_RULES` 가 정본).
  ⚠ 2026-08-23: 여기 «25,000원 · 23원/일»이라 적혀 있었다. **둘 다 낡았다** —
  값은 순서별(120k·80k·150k)로 바뀌었고 「23원/일」은 **둘째 등**의 값이었다(첫 등은 38원).
  ⇒ ★ **본보기로 든 값이라도 낡는다.** 그래서 값을 다시 안 적고 **정본을 가리킨다.**

# 4. ★★ 두 축의 직교를 지키는 방법

`env_difficulty_axis.md` §1이 이 문서의 핵심이라고 지정한 것이다.

|  | 축 | 무엇이 늘어나나 |
|---|---|---|
| 캐릭터 4종 | **경제 난이도** | 돈·목표 |
| 환경 설정 | **시뮬 깊이** | 관리 변수 개수 |

## 지키는 규칙 — 셋

### ① ★ 환경 축은 **경제 값을 안 건드린다**

```
온도를 켠다  →  월세·판매가·목표 금액·시작 자금이 ★그대로다
             →  같은 목표에 걸리는 ★시간만 늘어난다
```

★ **이 한 줄이 직교의 정의다.** 환경을 켰다고 목표가 바뀌면 그건 경제 난이도를 올린 것이다.

예외가 딱 하나 — **설비 구입**(식물등·난방)이다. 그건 플레이어가 고르는 것이라
**환경이 경제를 건드린 게 아니라 플레이어가 건드린 것**이다(§3).

### ② ★ 계수는 **곱해지기만** 하고 밴드를 안 만든다

온도가 새 밴드를 만들면 판정 축이 하나 는다. 계수로만 두면 **관리 변수만 늘고 판정은 그대로**다.

```
✅ 게이지 속도 = base × f_light × f_temp × f_water
❌ bandOf(온도) 를 따로 만들어 화면에 밴드를 하나 더 띄운다
```

★ 유일한 예외가 **물의 게이트**인데, 그건 새 밴드가 아니라 **빛의 `min` 게이트에 OR 로 얹는 것**이다(§5).

### ③ ★ 각 요소는 독립 on/off — `null` 이면 계수 1.0

`env_difficulty_axis.md` §1의 모듈화 규칙이고, **이미 코드가 그 모양이다.**
`growth-to-plan.md` §9의 `fCoef()` 가 `null`·`NaN`·음수·비수치를 전부 **1** 로 되돌린다.

```
fCoef(null) → 1        아직 안 재는 축
fCoef(3, ()=>-2) → 1   ★ 음수 계수도 1 (곱하면 확률이 뒤집힌다)
```

★ **새로 만들 게 없다.** 이 문서는 **어느 계수 자리에 붙는지**만 지정하면 된다.
계약 객체(`docs/engine/light_contract.md`)에 `temp`/`humidity` 자리도 이미 `null` 로 있다.
`water` 는 계약에 없으므로 **한 칸 추가가 필요하다** — §7.

## ⚠ 직교가 깨지는 자리 — 미리 표시해 둔다

| 위험 | 왜 | 처리 |
|---|---|---|
| **난방비** | 환경 → 경제 | §3 — 선택 설비로 |
| **온실** | 전기 무료(연구자)라 난방비가 0 → 연구자만 온도 면제 | `electricityWaived` 가 난방까지 덮는지 **⏸ 확인 필요** |
| **반지하** | 자연광이 0이라 온도 변동도 작다(반지하는 실제로 여름에 시원하고 겨울에 덜 춥다) | ★ 이건 **깨지는 게 아니라 보상**이다. `hidden_depth.md` #12(계절 변동 3%)와 같은 뿌리 |

# 5. 잎 건강 — 물이 마르면 어떻게 되나

지금 `growth_tuning.json` 의 `health` 는 **7일 평균 DLI 하나**만 본다.

```
7일평균 ≥ min(3.0)        정상 — recover_days(6일)에 걸쳐 되돌아온다
survive(1.2) ~ min(3.0)   정지 — 자라지도 잃지도 않는다
< survive(1.2)            fade_days(10일)에 걸쳐 바랜다
drop_enabled = false      ★스토리 내내 꺼져 있다 — 바랜 채로 유지
```

## ★ 확정 — 새 항이 아니라 **OR 하나**를 얹는다

```
현재   바램 시작 조건 =  dli7 < survive(1.2)
확장   바램 시작 조건 =  dli7 < survive(1.2)  ★OR  수분 = 0 이 이어진 날
```

`fade_days` · `recover_days` · `drop_hold_days` 는 **그대로 쓴다. 새 숫자를 안 만든다.**

## 왜 OR 인가 — 곱이 아니라

| 근거 | |
|---|---|
| **물리** | 빛 부족과 물 부족은 결과가 같다 — *"잎을 유지할 자원이 없다."* 원인이 둘이고 증상이 하나다 |
| ★ **판정 축을 안 늘린다** | 곱으로 하면 「어두운데 물도 없다」가 두 배로 빨리 바래는데, 그러려면 밴드가 둘로 늘어 화면이 복잡해진다. §4-② 위반이다 |
| **관리 변수는 는다** | 플레이어가 볼 것이 하나 늘긴 한다(물통). 그게 시뮬 깊이 축이 하는 일이고, **판정 축은 그대로** 유지된다 |

## ★ 그래서 화면에 "왜 바래는지"를 말해 줘야 한다

증상이 같아졌으므로 **원인을 화면이 갈라 줘야 한다.**
`STATUS` core 의 판단필요 3번(*A4 말 피드백 — 오늘 안 자란 게 날씨 탓인지 등을 안 켠 탓인지*)이
**물이 들어오면 선택이 아니라 필수**가 된다.

```
"빛이 모자라 잎이 바래고 있습니다"     ← dli7 < survive
"물이 말라 잎이 바래고 있습니다"        ← 수분 0
```

★ 계약이 `dli_daylight` / `dli_lamp` 를 나눠 주는 것과 같은 방식으로,
**원인을 구분할 수 있는 값이 계산 쪽에 남아 있어야** 한다.

## ⚠ `health` 와 `vigor` 를 섞지 않는다

| | |
|---|---|
| **`health`** | 잎의 색·낙엽. **살아 있다**(2026-08-03 박사님 지시로 되살림) |
| **`vigor`** | 개체 체력. **취소·보류다**(2026-08-02 박사님). 훅도 두지 않는다 |

★ 물을 붙일 자리는 `health` 이지 `vigor` 가 아니다. 여기서 헷갈리면
취소된 축이 물을 타고 되살아난다.

# 6. 습도 — 굴림 확률 계수

**후보값.** 실플레이 전에는 정밀화할 근거가 없다.

| 상대습도 | 계수 | 근거 |
|---|---|---|
| 60% 이상 | **1.0** | 몬스테라 원산지 대역(열대우림 80%+)에 가깝다 |
| 40 ~ 60% | 0.85 | 한국 실내 평상 |
| 40% 미만 | **0.7** | 한국 겨울 실내(30~40%). 새순이 제대로 안 펴진다 |

★ **왜 0.7 에서 멈추나** — §1의 하한 10% 때문이다. 더 깎으면 clamp 에 늘 걸려
**습도를 관리해도 결과가 안 바뀌는 구간**이 생긴다. 관리해도 안 바뀌면 변수가 아니라 소음이다.

★ **습도는 방의 속성이지 행동이 아니다.** 가습기는 설비(§3의 난방과 같은 구조)로 두고,
기본은 계절·방 종류의 함수다 — `env_difficulty_axis.md` §2의 *"전부 이미 있는 것들의 함수"* 그대로.

⏸ **가습기를 넣을지는 미정.** 설비가 셋(등·난방·가습)이면 「설비를 사면 다 풀린다」가 될 위험이 있다.
**판단 기준**: 습도를 방·계절로만 두었을 때 *"이 방에서는 못 한다"* 가 생기면 설비를 연다.
안 생기면 설비 없이 방의 성격으로 남긴다.

# 7. 계약에 필요한 것 — core·growth 로 넘어가는 것

`docs/engine/light_contract.md` 에 `temp`/`humidity` 는 **자리가 있다**(`null`).

```jsonc
"temp":     null,   // ✅ 자리 있음 — 표준(→ 심화)에서 채움
"humidity": null,   // ✅ 자리 있음 — 실전에서 채움
"water":    null    // ❌ ★ 없다. 한 칸 추가가 필요하다
```

## ⏸ 판단필요 — `water` 를 계약에 넣을지, 개체 상태로 둘지

| 후보 | | |
|---|---|---|
| **㉮ 계약에 넣는다** | `temp`·`humidity` 와 같은 자리 | 계약은 **방·환경**을 나르는 그릇인데 수분은 **개체마다** 다르다 — 결이 안 맞는다 |
| **㉯ 개체 상태로 둔다** | 잎별 성숙 게이지와 같은 층 | 2026-08-03 확정이 이미 *"잎마다 상태가 필요하다"* 로 개체 상태 층을 열었다. **그 층에 얹는 게 자연스럽다** |
| ㉰ 둘 다 | 계약은 `dryRate`(방이 정하는 마름속도), 개체는 `water`(게이지) | ★ **가장 정확하다.** 마름속도는 환경의 함수, 게이지는 개체의 것 |

**㉰를 권한다.** 다만 확정하지 않는다 — **개체 상태 층의 형식은 growth 소유**이고
(2026-08-03: *"`growthPhase()` 반환값 확장이 필요하면 growth 가 정해서 회신"*),
물이 착수될 시점에 growth 가 그 층을 어떻게 잡았는지 보고 맞추는 게 맞다.

## 넘기는 것

- [ ] **`water` 를 어디에 둘지** — ㉰ 권고. 형식은 growth (growth · core)
- [ ] **마름속도 base 10%/일** 이 실제 관수 간격 7~17일로 나오는지 재현 (growth)
- [ ] **`health` 의 OR 확장** — `fade` 트리거에 「수분 0 지속」을 더한다 (growth)
- [ ] **clamp 한 줄** — `p = clamp(p, roll_lo, roll_hi)` 를 계산 마지막에 (growth)
- [ ] **난방·가습 설비 값** — 가격·소비전력. 식물등과 같은 방식으로 실측 (house · plan)
- [ ] **`electricityWaived` 가 난방까지 덮는지** — 연구자만 온도 면제가 되면 축이 어긋난다 (plan)
