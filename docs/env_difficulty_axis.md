# 환경 요소 = "시뮬 깊이" 난이도 축 (설계 기록 · 미구현)

> 이 문서는 **기록만** 한 것이다. 여기 적힌 것 중 구현된 건 **빛**뿐이다.
> 계약 객체(`docs/light_contract.md`)에 `temp`/`humidity`/`weatherPattern` **자리만** 잡혀 있다.

---

## 1. 두 축은 직교한다

|  | 축 | 무엇이 늘어나나 |
|---|---|---|
| **캐릭터 4종** | 경제 난이도 | 돈·목표 |
| **환경 설정** | 시뮬 깊이 | **관리 변수 개수** |

곱해지는 난이도가 아니라 **독립 선택**이다.
반지하로 시작해도 "기본"이면 빛·물만 보면 되고, 아파트라도 "실전"이면 변수가 넷이다.

| 단계 | 관리 변수 |
|---|---|
| **기본** | 빛 + 물 ← *볕의 핵심. 이것만으로 게임 성립* |
| 표준 | + 온도 |
| 심화 | + 습도 |
| 실전 | + 지역 날씨 패턴 |

### ★ 이게 개발 순서이기도 하다
**기본부터 만들어 재미를 검증한 뒤 얹는다.** 온도를 먼저 넣으면 뭐가 재미없는지 못 가려낸다.

### ★ 모듈화 규칙
각 요소는 **독립 on/off**. **온도 코드가 빛 코드에 얽히면 안 된다.**
계약 객체에서 `temp: null`이면 생장 창은 온도 계수를 1.0으로 두고 그냥 넘어가야 한다.
(지금 구조가 그렇게 돼 있다 — 필드가 `null`로 존재하고, 없으면 무시)

## 2. 온도·습도·물 = 파생 설계 (새 시스템 아님)

전부 **이미 있는 것들의 함수**다. 새 시뮬레이터를 만드는 게 아니다.

### 온도 = f(계절, 방 종류, 창 크기·향, 난방)

여기서 **트레이드오프가 저절로 생긴다**:

| | 빛 | 온도 |
|---|---|---|
| 큰 창 | 유리함 | 겨울에 추움 |
| 온실 | 최상 | 난방비 폭발 |

이게 핵심이다. 온도를 넣는 순간 **"창이 크면 무조건 좋다"가 깨진다.**

몬스테라 기준:

| 온도 | 상태 |
|---|---|
| 18~30℃ | 최적 |
| 15℃ 이하 | 정체 |
| 10℃ 이하 | 손상 |
| 5℃ 이하 | 고사 |

**생장률 = 빛계수 × 온도계수**

→ *"식물등 켰는데 왜 안 자라지? …겨울이라 추워서."*
플레이어가 원인을 찾아내는 구조. 빛만 있을 땐 나올 수 없는 종류의 퍼즐이다.

### 물주기 = 유일한 능동 행동

빛·온도·습도는 **환경**(고르는 것)이고, 물은 **행동**(하는 것)이다.
실내식물 사망 원인 1위가 과습이다.

**마름속도 = f(빛, 온도, 습도)**

→ 반지하에서 **과습으로 죽이기 쉬운 게 물리적으로 성립한다.**
어두우면 증산이 적고 → 흙이 안 마르고 → 평소 간격으로 주면 과습.
"어두운 방에선 물을 덜 줘야 한다"가 규칙이 아니라 **결과로 나온다.** 이게 좋은 설계다.

## 3. 지역차 — 지금 안 넣음. 계수 자리만

국내 연간 일조시간:

| 지역 | 시간 |
|---|---|
| 영덕 | 2,550 |
| 전국평균 | 2,219 |
| 서울 | 2,143 |
| 제주 | 1,854 |

최대 차이 **37%**, 서울 기준 **±5%**.
계절(45%)·날씨(75%)·창향(수 배)보다 **작다** → 우선순위 낮음.

→ `daylight_lux.js`의 `REGION`에 계수 자리만 있고 전부 1.0이다.

### 나중에 확장한다면 — 난이도가 아니라 "성격"으로

| 지역 | 성격 |
|---|---|
| 제주 | 흐림 대비형 |
| 영남 | 여름 강광 대비형 |
| 강원 | 겨울 대비형 |

**전제**: 날씨 전략이 재미가 되려면 **예보 UI가 같이 있어야 한다.**
없으면 그냥 랜덤 불운이다. 플레이어가 대비할 수 없는 변동은 난이도가 아니라 소음이다.

## 4. ★ 앞 건물·층수 차폐 — 지역보다 우선순위 높음 (검토)

한국 주거환경에선 이게 결정적이다.

- 앞 동이 막으면 **남향도 북향보다 어두움**
- 저층 ↔ 고층 조도 **몇 배** 차이
- **반지하가 어두운 진짜 이유도 창 크기보다 지면·앞건물 차폐**

→ 이사 = **층·향 업그레이드**가 되면 자취생 서사와 정확히 맞는다.
지금 "이사 = 방이 커진다"보다 훨씬 체감이 크고, 실제 집 구하기의 감각과도 같다.

### 구현 난이도는 낮다
차폐 엔진(OBB ray-slab)이 **이미 있다**. 창 바깥에 가상 박스(앞 건물)를 하나 두고
occluder 목록에 넣으면 그대로 동작한다. 새 물리가 필요 없다.

### `house_rooms.json` 필드 제안 (의견 요청)

```jsonc
"exterior": {
  "floor": 2,              // 층수 — 창 높이 오프셋
  "orientation": "south",  // 창 향 (지금은 미사용, 방위 들어오면)
  "obstruction": {         // 앞 건물
    "distance": 8,         // m
    "height": 12,          // m
    "azimuth": 0           // 창 정면 기준 각도
  }
}
```

반지하는 `floor: -0.5` + 가까운 `obstruction`으로 표현하면,
지금처럼 창을 억지로 작게 만들 필요 없이 **어두운 이유가 물리적으로 설명된다.**
