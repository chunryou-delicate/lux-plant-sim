# 0. ★ 왜 적립이 아니라 잭팟인가 — 숫자가 그렇게 말한다

이사 자금 150만원을 **모아서** 만들 수 있는지 먼저 역산했다.

| | |
|---|---|
| 하루 지출 합 | 20,000원 (월세 10,000 + 공과·전기 2,500 + 식비 7,500) |
| 콩나물 풀가동 절감 | 5,000원/일 (하루 2끼 상한 · `food_economy.md` §4) |
| 씨앗 재투자 | 시루 3개 × 2,100원 ÷ 4일 = 1,575원/일 |
| **순 방어** | **3,425원/일** |

콩나물을 완벽히 돌려도 **하루 16,575원씩 줄어든다.** 반지하 방 칸(14) 전체를
콩나물로 채워도 하루 2끼 상한 때문에 절감이 5,000원에서 멈춘다 — **상한이 곧 천장**이다.

> **그래서 이사 자금은 "모으는 것"이 아니라 "한 번에 만드는 것"이다.**
> 콩나물은 그때까지 굶지 않게 버티는 수단이고, 실제로 **파산을 6일 늦추고 튜토 29일째에
> 64,300원을 더 남긴다**(재현 D-2).

# 1. ★★ 150만원 역산 — 무늬 잎이 몇 장이라야 하나

`propagation.md` §6 공식 그대로다.

```
값 = 단위기본가 × 크기 × (1 + 60·v²)
      v = 그 그루의 무늬 잎 비율 (무늬 잎 ÷ 전체 잎)
      크기 = 잎(마디) 수
      잎 1~2장 → 삽수 가격표(12,000/잎) · 잎 3장~ → 성체 가격표(10,000/잎)
```

`shop.varieLeavesNeededFor(1_500_000, {leaves})` 가 낸 표다(코드와 문서가 갈리지 않게 함수로 둔다).

| 잎 수 | 등급 | 필요 v | **필요 무늬 잎** | 그때 값 | v=1 일 때 최대 |
|---|---|---|---|---|---|
| 1 | 삽수 | 1.438 | **불가능** | — | 732,000 |
| 2 | 삽수 | 1.012 | **불가능** | — | 1,464,000 |
| 3 | 성체 | 0.904 | 3 | 1,830,000 | 1,830,000 |
| 4 | 성체 | 0.780 | 4 | 2,440,000 | 2,440,000 |
| 6 | 성체 | 0.632 | 4 | 1,660,000 | 3,660,000 |
| 9 | 성체 | 0.511 | 5 | 1,756,667 | 5,490,000 |
| 12 | 성체 | 0.438 | 6 | 1,920,000 | 7,320,000 |

## ★ 여기서 바로 나오는 두 가지

**① 삽수 한 개로는 150만이 절대 안 된다.** 잎 2장이 전부 무늬여도 1,464,000원이다.
`propagation.md` §7 의 *"성체 4그루냐 삽수 16개냐"* 가 ② 이사 단계에서 미리 한 번 나온다.

**② 그래서 실제 잭팟은 「무늬 삽수 + 남은 모주」다.**
무늬 잎 한 장을 품은 마디를 잘라 팔면 `12,000 × 1 × 61 = 732,000`원이고,
남은 모주(잎 5~6장 민무늬)를 60,000원에 같이 팔면 792,000원이 된다.
그동안 콩나물로 지킨 잔액(튜토 24일째 약 76만원)과 합쳐 **150만을 넘긴다.**
재현이 실제로 그 경로로 이사한다 — *"튜토 24일에 792,000원에 팔고 그날 이사"*.

## ⚠ 정본 안에서 `v` 가 두 뜻으로 쓰인다 — plan 판단 필요

`propagation.md` §6 **본문**은 *"v 는 그 그루에 실제로 난 무늬 잎의 비율"*이라고 못 박는다.
그런데 같은 절의 **검산표**는 「몬스테라 삽수(알보) 80,000」을 `12,000 × 6.667`(v = 0.307)로 맞춘다.
잎 1장짜리 삽수의 그 한 장이 무늬면 **잎 비율로는 v = 1.0** 이고 값이 732,000원이 된다.

| 읽는 법 | 무늬 삽수(잎1) 값 | 잭팟이 성립하나 |
|---|---|---|
| **㉮ 잎 비율** (본문 정의) | **732,000** | ✅ 성립한다 |
| ㉯ 라벨 짙기(알보 = 0.307) | 80,000 | ❌ 반지하에서 절대 불가능 |

**코드는 ㉮(본문 정의)를 따랐다.** 코어가 안 보이는 값을 지어내지 않는다는 원칙과도 맞고,
플레이어가 잎을 세어 값을 읽을 수 있다. 다만 ㉮면 **작은 그루의 값이 매우 커진다** —
잎 하나가 무늬인 삽수가 73만원이다. 크기 하한이나 소품 상한이 필요할 수 있다. **plan 확인 대기.**

# 3. 첫 시루는 공짜, 그 뒤는 주문

```
Day 0        콩나물 시루 하나를 받는다 (지금 그대로 · 공짜)
Day 4        첫 수확
그 뒤        씨앗을 주문한다 → 하루 뒤 도착 → 다시 심는다(resowCrop)
             시루를 늘리려면 용기를 주문한다 → 이틀 뒤 도착
```

★ **재파종은 씨앗 재고를 쓴다.** 재고가 없으면 `resowCrop` 이 던진다 —
*"공짜로 무한히 나오면 경제가 아니다"*. 그래서 **수확 전에 미리 시켜 두는 것**이 플레이가 된다.

★ **시루는 셋까지만 의미가 있다.** 하루 작물 끼니 상한이 2끼(`food_economy.md` §4)인데
시루 하나가 4일에 3끼라, 셋이면 2.25끼/일로 상한을 채운다. 넷째부터는 남아서 쉰다
(`first_play.advanceBeansproutDay` 가 `상한 × 회전일` 을 넘는 끼니를 버린다).
**규칙이 아니라 셈이 상한을 만든다.**

## ★★ 막다른 길이 없어진다

`cropDark`(어두운 자리에도 쓸모가 있다)는 수확 시 4일평균 DLI ≤ 0.3 으로 판정한다.
예전에는 시루가 **한 번뿐**이라 밝은 자리에서 첫 수확을 하면 영영 못 나갔다.
지금은 씨앗을 다시 주문해 **어두운 자리에 다시 심으면 배운다.**
자동으로 채워 주지 않는다 — 다시 심어도 밝은 자리면 여전히 안 켜진다(재현 C·C-2 가 둘 다 고정).

## 4-1. 먼저 — 재현이 대역을 버렸다. 잎 수가 절반 이하였다

`tools/test_banjiha_routes.mjs` 가 `plant_grow.html` 을 **헤드리스로 진짜 돌린다**
(`tools/test_cuttable.mjs` 와 같은 방식). 예전 대역은 `sale_economy.md` §0 의 **마디 표**를
잎 수로 읽고 있었는데, 실제로 살아 있는 잎은 그보다 훨씬 적다:

| | 예전 대역 | **실측** |
|---|---|---|
| 도착 개체(유효 143일) | 잎 6장 | **잎 2장** (마디 14개) |
| 튜토 구간(+30~90일) | 7~9장 | **3장** |
| +120일 | 12장 | 5장 |

값이 잎 수로 매겨지므로 이 차이가 이사 성립을 통째로 바꾼다. **잎은 축(가지)마다 한 장**이고
마디는 그보다 훨씬 많다 — 두 수를 섞어 쓰면 안 된다.

## 4-2. 꾸준수입 = 삽수 — 얼마에 · 얼마나 자주 · 남는가

```
병을 주문한다(7,000원 · 2일)  →  자른다  →  뿌리내린다(물꽂이 12일)  →  판다
```

| | |
|---|---|
| 값 | **12,000원** (잎 1장 민무늬 · `sale_economy.md` §3 「몬스테라 삽수(일반)」) |
| 한 바퀴 | **14일** (병 배송 2 + 뿌리 12). 직삽이면 26일(24 + 2) |
| 원가 | 유리 수경병 **7,000원**. ★**팔면 돌아온다** — 병째 보내지 않으므로 두 번째부터 공짜 |
| 빈도 | **모주가 잎을 새로 낼 때만**. 반지하 창턱에서 잎 하나가 30~40일 |
| 90일 실측 | 삽수 1개 12,000원 − 병값 7,000원 = **순 5,000원** (하루 56원) |

★ **하루 지출 20,000원의 0.3%다.** `sale_economy.md` §0 의 *"반지하에서 식물을 팔아 흑자를
내는 건 불가능하다"* 가 숫자로 다시 확인된다. 꾸준수입은 **버티는 수단이 아니라 배우는 수단**이고,
이사 자금은 확정 무늬가 만든다.

## 4-3. 무한 증식을 막는 것 — 총량 하나

growth 는 **잘라낸 것을 모른다**(형태를 되돌릴 창구가 없다). 그래서 `cuttableNodes()` 는
잘린 뒤에도 안 잘린 그루를 계속 낸다. 코어가 총량으로 막는다:

```
잘라낸 잎의 합(pot.pendingCutLoss.leaves) ≤ 모주의 잎 수(leafStats().leaves)
```

`propagation.cuttableNow(S, nodes)` 가 이 부등식으로 목록을 거르고, `takeCutting` 이
자기 안에서 한 번 더 돌린다(호출부가 잊어도 안 샌다). 같은 마디를 두 번 자르는 것도 막는다.
초보에서는 **모주에 잎이 한 장은 남는다**(예전의 "예비혹이 남나"를 잎 수로 바꿨다 —
마디 개수로 세면 이미 잘린 자리가 거짓말을 한다).

## 4-4. 튜토 확정 무늬 — 어디에 두었나

정본은 `src/game/tutorial.js` §확정 무늬 주석이다. 요약:

> 튜토 중 · **배움 넷 완료** · **모주에서 삽수를 한 번 잘라 봤다** ·
> **지금 가진 것을 다 팔아도 150만에 못 닿는다** · 마지막으로 준 지 **12일** 지났다
> → 모주의 잎 한 장을 무늬로 친다(잎이 제일 적은 마디부터).

- **확률을 안 건드린다.** growth 의 `calcVarieProb` 은 그대로 돈다. 코어는
  `ts.varieGrant.nodeIds` 라는 자기 상태를 갖고 `tutorial.varieView()` 로 **덧씌워 읽는다.**
  `plant_grow.html` 은 한 글자도 안 바뀌었다.
- **12일 간격**은 `propagation.METHODS.water.rootDays` 와 같은 수다 —
  받은 무늬를 잘라 뿌리내려 파는 데 걸리는 그 시간. 하루에 한 장씩 주면 튜토가 **이틀**에 끝났다.
- **"한 장만"이 아니라 "닿을 때까지"** 인 이유: 도착 개체의 잎이 두세 장이라 한 장만 무늬면
  v = 1/3~1/2 이고 값이 38만~83만에서 멈춘다. 한 장으로 걸었더니 **무늬는 났는데 못 나가는**
  판이 절반을 넘었다. 닿는 순간 멈추므로 수도꼭지가 아니다.
- **정식 모드에는 안 샌다** — 상태 자체가 튜토 것이고, 튜토가 꺼져 있거나 이사한 뒤에는
  판정도 덧씌우기도 통째로 지나간다. 재현 검사 H-2 가 셋을 다 확인한다.

## 4-6. ⏸ 판단필요 — 셋 다 **여름**에 끝난다

여름이다. 사유는 산수다:

```
시작 자금 100만  −  하루 약 7,700원(콩나물 풀가동 순지출)  −  튜토 30일 첫 월세 30만
→ 튜토 29일 잔액 약 77만 · 30일 잔액 약 47만
무늬 삽수(잎1·v=1) 732,000원을 팔아도 **튜토 30일을 넘기면 150만에 못 닿는다**
```

그래서 확정 무늬는 30일 안에 닿게 설계할 수밖에 없고, **가을 진입(45일)·식물등 해금이
튜토 안에 안 들어온다.** 바꾸려면 확정 수치(시작 자금·하루 지출·이사비·월세 유예) 쪽을
건드려야 한다 — 이 창은 그것을 못 바꾼다. 후보만 적어 둔다:

| 후보 | 효과 | 대가 |
|---|---|---|
| 월세 유예 30일 → 60일 | 튜토 60일까지 잔액이 버틴다 → 가을 진입이 들어온다 | 서사 장치를 한 번 더 쓴다 |
| 이사 자금 150만 → 100만 | 확정 무늬 한 장으로 여유 있게 닿는다 | plan 이 *"실비와 어긋남"* 이라고 이미 거부한 안 |
| 식물등 해금을 **여름 후반**으로 | 등이 튜토 안에 들어와 경로 B 가 실제로 갈린다 | 계절과 해금이 어긋난다 |
| 첫 개체를 잎 4~6장짜리로 도착 | 자를 것이 늘어 꾸준수입이 의미를 갖는다 | `arrivalGrowthDays` 를 올려야 한다(growth 곡선) |

## 4-7. ⏸ growth 요청 — 도착 개체가 무늬를 달고 온다

40개 시드 중 **13개(33%)** 에서 도착 개체가 이미 무늬 잎을 달고 있다. 잎 2장이 다 무늬면
그루 값이 1,464,000원이라 **받자마자 팔면 튜토가 첫날에 끝난다.**
`propagation.md` §7 의 *"첫 몬스테라는 normal 고정"* 과도 어긋난다.
사유·요청은 `docs/handoff/core-to-growth.md` 맨 끝에 적었다(코어가 못 고치는 자리다).

## ★ 삽수·확정 무늬 (2026-08-03 추가) — 화면이 **반드시** 거쳐야 하는 두 줄

```js
import { varieView } from './src/game/tutorial.js';
import { cuttableNow, cutBudgetOf, motherStatsNow, takeCutting } from './src/game/propagation.js';
import { sellCutting, sellPot, SELLABLE_CUTTING_STATUS } from './src/game/shop.js';

// ① growth 가 낸 날값
const raw = growth.cuttableNodes();      // [{nodeId, stem, leaves, variegatedLeaves, growthDays}]
const st  = growth.leafStats();          // {leaves, variegatedLeaves, matureLeaves, growthDays}

// ② ★ 코어의 확정 무늬를 덧씌우고, ③ ★ 잘라낸 만큼을 뺀다 — 둘 중 하나만 빼먹으면 값이 틀린다
const v      = varieView(S, { nodes: raw, stats: st });
const nodes  = cuttableNow(S, v.nodes);          // 지금 실제로 자를 수 있는 마디만
const mother = motherStatsNow(S, v.stats);       // 지금 모주에 남아 있는 잎 집계
const budget = cutBudgetOf(S, v.nodes);          // {motherLeaves, lostLeaves, leftLeaves, cutNodeIds}

takeCutting(S, { nodes, nodeId, container: 'jar', at, slots, log });  // ★용기 재고를 쓴다
sellCutting(S, cuttingId, { log });   // ★뿌리내린 것만 팔린다(SELLABLE_CUTTING_STATUS)
sellPot(S, { leaves: mother.leaves, variegatedLeaves: mother.variegatedLeaves, log });

// 확정 무늬는 하루 진행 안에서 자동이다 — turn.varieGrant = { granted, nodeId, detached, why }
// 이벤트 id 는 `varie_granted` 다(dialogue 가 붙일 자리).
```

★ 자르기 UI 는 `cuttableNow` 가 낸 목록만 보여 주면 된다. 왜 못 자르는지는
`propagation.cutBlockedReason(S, nodes, nodeId)` 가 한 줄로 낸다(회색 처리 사유).

## ⏸ growth 에 필요한 것 — `handoff/core-to-growth.md` 요청

- **`leafStats()`** → `{ leaves, variegatedLeaves }`. 값은 잎으로 매기는데 잎은 growth 소유다.
  이게 없으면 브라우저에서 **판매 화면을 못 연다**(코어가 잎을 지어내지 않기로 했다).
- **`cuttableNodes()`** — 이미 요청돼 있다(`propagation.md` §7-2). 마디별로
  `{nodeId, stem, leaves, variegatedLeaves, growthDays}` 가 나와야 무늬 삽수를 잘라 팔 수 있다.
- **판 뒤의 형태 정리** — `sellPot` 은 화분을 지우지만 growth 의 3D 는 코어가 못 지운다.
  반환값 `growthNeedsReset: true` 로 알린다. 화면이 정리해야 한다.
