# 0. ★ 왜 적립이 아니라 잭팟인가 — 숫자가 그렇게 말한다

이사 자금 150만원을 **모아서** 만들 수 있는지 먼저 역산했다.

| | |
|---|---|
| 하루 지출 합 | 20,000원 (월세 10,000 + 공과·전기 2,500 + 식비 7,500) |
| 콩나물 풀가동 절감 | 5,000원/일 (하루 2끼 상한 · `food_economy.md` §4) |
| 씨앗 재투자 | 시루 3개 × 2,100원 ÷ 4일 = 1,575원/일 |
| **순 방어** | **3,425원/일** |

콩나물을 완벽히 돌려도 **하루 16,575원씩 줄어든다.** 반지하 방 칸(14) 전체를
콩나물로 채워도 하루 2끼 상한 때문에 절감이 5,000원에서 멈춘다 — **상한이 곧 천장**이다.
즉 **반지하에는 흑자가 없다.** `sale_economy.md` §1 이 이미 낸 결론과 같다.

> **그래서 이사 자금은 "모으는 것"이 아니라 "한 번에 만드는 것"이다.**
> 콩나물은 그때까지 굶지 않게 버티는 수단이고, 실제로 **파산을 6일 늦추고 튜토 29일째에
> 64,300원을 더 남긴다**(재현 D-2).

# 1. ★★ 150만원 역산 — 무늬 잎이 몇 장이라야 하나

`propagation.md` §6 공식 그대로다.

```
값 = 단위기본가 × 크기 × (1 + 60·v²)
      v = 그 그루의 무늬 잎 비율 (무늬 잎 ÷ 전체 잎)
      크기 = 잎(마디) 수
      잎 1~2장 → 삽수 가격표(12,000/잎) · 잎 3장~ → 성체 가격표(10,000/잎)
```

`shop.varieLeavesNeededFor(1_500_000, {leaves})` 가 낸 표다(코드와 문서가 갈리지 않게 함수로 둔다).

| 잎 수 | 등급 | 필요 v | **필요 무늬 잎** | 그때 값 | v=1 일 때 최대 |
|---|---|---|---|---|---|
| 1 | 삽수 | 1.438 | **불가능** | — | 732,000 |
| 2 | 삽수 | 1.012 | **불가능** | — | 1,464,000 |
| 3 | 성체 | 0.904 | 3 | 1,830,000 | 1,830,000 |
| 4 | 성체 | 0.780 | 4 | 2,440,000 | 2,440,000 |
| 6 | 성체 | 0.632 | 4 | 1,660,000 | 3,660,000 |
| 9 | 성체 | 0.511 | 5 | 1,756,667 | 5,490,000 |
| 12 | 성체 | 0.438 | 6 | 1,920,000 | 7,320,000 |

## ★ 여기서 바로 나오는 두 가지

**① 삽수 한 개로는 150만이 절대 안 된다.** 잎 2장이 전부 무늬여도 1,464,000원이다.
`propagation.md` §7 의 *"성체 4그루냐 삽수 16개냐"* 가 ② 이사 단계에서 미리 한 번 나온다.

**② 그래서 실제 잭팟은 「무늬 삽수 + 남은 모주」다.**
무늬 잎 한 장을 품은 마디를 잘라 팔면 `12,000 × 1 × 61 = 732,000`원이고,
남은 모주(잎 5~6장 민무늬)를 60,000원에 같이 팔면 792,000원이 된다.
그동안 콩나물로 지킨 잔액(튜토 24일째 약 76만원)과 합쳐 **150만을 넘긴다.**
재현이 실제로 그 경로로 이사한다 — *"튜토 24일에 792,000원에 팔고 그날 이사"*.

## ⚠ 정본 안에서 `v` 가 두 뜻으로 쓰인다 — plan 판단 필요

`propagation.md` §6 **본문**은 *"v 는 그 그루에 실제로 난 무늬 잎의 비율"*이라고 못 박는다.
그런데 같은 절의 **검산표**는 「몬스테라 삽수(알보) 80,000」을 `12,000 × 6.667`(v = 0.307)로 맞춘다.
잎 1장짜리 삽수의 그 한 장이 무늬면 **잎 비율로는 v = 1.0** 이고 값이 732,000원이 된다.

| 읽는 법 | 무늬 삽수(잎1) 값 | 잭팟이 성립하나 |
|---|---|---|
| **㉮ 잎 비율** (본문 정의) | **732,000** | ✅ 성립한다 |
| ㉯ 라벨 짙기(알보 = 0.307) | 80,000 | ❌ 반지하에서 절대 불가능 |

**코드는 ㉮(본문 정의)를 따랐다.** 코어가 안 보이는 값을 지어내지 않는다는 원칙과도 맞고,
플레이어가 잎을 세어 값을 읽을 수 있다. 다만 ㉮면 **작은 그루의 값이 매우 커진다** —
잎 하나가 무늬인 삽수가 73만원이다. 크기 하한이나 소품 상한이 필요할 수 있다. **plan 확인 대기.**

# 2. 상점 — 품목·값·배송

## 마진과 배송 규칙

| | |
|---|---|
| **살 때** | 정가 × **1.4** (`sale_economy.md` §3 머리말 — "정가. 살 때는 ×1.4 = 상점 마진"). 100원 단위 올림 |
| **팔 때** | 정가(= §1 공식이 낸 값). 변동가 없음(`sale_economy.md` §5) |
| **배송** | 가벼운 것(씨앗 봉투) **1일** · 부피가 있는 것(용기·화분) **2일**. 박사님 *"하루 이틀 뒤"* |

★ **결제는 주문한 날, 물건은 나중.** 도착 때 결제하면 *"일단 다 시켜 놓고 돈 생기면 받는"*
무한 예약이 된다. 지금 돈이 나가야 **"이번에 뭘 시킬까"** 가 결정이 된다. 취소는 없다.

### ★ 용기값 5,000원 — 이 문서가 새로 정한 유일한 값

정본 어디에도 용기값이 없다(`food_economy.md` §3 은 씨앗 1,500원만, `propagation.md` §4 는
용기의 **슬롯 수와 에셋**만 정했다). 지어내지 않기 위해 **정본에 있는 가장 싼 완제품**에 맞췄다 —
`sale_economy.md` §4 의 **묘목 5,000원**이다. 그것이 이 게임에서 "제일 싼, 손에 잡히는 물건"의
가격대이고, 용기 셋은 전부 그 자리에 있다(0.12~0.36m 소품).

검산: 시루 하나가 4일에 3끼(7,500원어치)를 내므로 **용기값을 사흘이 안 되어 뽑는다.**
비싸서 못 사는 물건이 아니고, 공짜도 아니다. **⏸ plan 확인 대기** —
`data/balance/` 에 `shop` 항목을 만들 때 이 세 값을 옮기면 된다(이 창은 `data/balance/` 수정 금지).

# 3. 첫 시루는 공짜, 그 뒤는 주문

```
Day 0        콩나물 시루 하나를 받는다 (지금 그대로 · 공짜)
Day 4        첫 수확
그 뒤        씨앗을 주문한다 → 하루 뒤 도착 → 다시 심는다(resowCrop)
             시루를 늘리려면 용기를 주문한다 → 이틀 뒤 도착
```

★ **재파종은 씨앗 재고를 쓴다.** 재고가 없으면 `resowCrop` 이 던진다 —
*"공짜로 무한히 나오면 경제가 아니다"*. 그래서 **수확 전에 미리 시켜 두는 것**이 플레이가 된다.

★ **시루는 셋까지만 의미가 있다.** 하루 작물 끼니 상한이 2끼(`food_economy.md` §4)인데
시루 하나가 4일에 3끼라, 셋이면 2.25끼/일로 상한을 채운다. 넷째부터는 남아서 쉰다
(`first_play.advanceBeansproutDay` 가 `상한 × 회전일` 을 넘는 끼니를 버린다).
**규칙이 아니라 셈이 상한을 만든다.**

## ★★ 막다른 길이 없어진다

`cropDark`(어두운 자리에도 쓸모가 있다)는 수확 시 4일평균 DLI ≤ 0.3 으로 판정한다.
예전에는 시루가 **한 번뿐**이라 밝은 자리에서 첫 수확을 하면 영영 못 나갔다.
지금은 씨앗을 다시 주문해 **어두운 자리에 다시 심으면 배운다.**
자동으로 채워 주지 않는다 — 다시 심어도 밝은 자리면 여전히 안 켜진다(재현 C·C-2 가 둘 다 고정).

# 4. ⏸ ★★ 판단필요 — 지금 데이터로는 잭팟이 중앙값 안에 안 난다

재현(`tools/test_banjiha_routes.mjs`, 시드 40판)이 낸 실측이다.

| 경로 | 이사 성공 | 중앙값 | 최선 / 최악 |
|---|---|---|---|
| **A** 등 없이 | **15%** (6/40) | 못 나감 | 튜토 24일 / 96일 |
| **B** 등 사고 | **15%** (6/40) | 못 나감 | 튜토 24일 / 96일 |
| **C** 겨울까지 | **20%** (8/40) | 튜토 96일 | 24일 / 323일 |

## 사유는 하나다 — **반지하는 등을 켜도 무늬 대역에 못 들어간다**

무늬 확률은 `plant_grow.html` `calcVarieProb` = `varieProb(0.20) × fLight × fStable` 이고,
`fLight` 의 **무늬 최적 대역은 DLI 7.0~15.4** 다(`light_thresholds` best_lo 5 · best_hi 11 × need_mult 1.4).

| 반지하 창턱 | DLI | fLight | **잎당 무늬 확률** |
|---|---|---|---|
| 등 없음 | 3.77 | 0.5 | **13.0%** |
| 등 1개 | 5.61 | 0.5 | **13.0%** |
| 등 2개 | 5.76 | 0.5 | **13.0%** |
| (참고) 대역 안 | 8.0 | 1.5 | **39.0%** |

★ **식물등을 사도 무늬 확률이 1%도 안 오른다.** `sale_economy.md` §2 가 이미
*"클립등 1개면 6.71로 fLight 경계 7.0에 0.29 못 미친다"* 고 짚었던 바로 그 자리인데,
지금 프로파일의 등은 그보다도 약해서 두 개를 켜도 5.76이다.
그리고 반지하 체류 동안 **새로 나는 잎이 3~5장**뿐이라(마디 하나에 30~40일),
13%로는 필요한 무늬 잎이 중앙값 안에 안 나온다.

## 손잡이 하나만 돌려 보면

같은 재현에서 **"등이 창턱을 7.0까지 올려 준다면"** 만 바꿔 돌렸다.

| 경로 | 지금 | 등이 대역에 닿으면 |
|---|---|---|
| B (등 사고) | 15% | **48%** (중앙값 튜토 96일 = 가을 51일째) |
| C (겨울까지) | 20% | **65%** (중앙값 튜토 168일) |

**등 하나로 3배가 된다.** 다만 그래도 B 가 48%이고 중앙값이 가을 끝자락이라,
`story_arc.md` §2 의 *"A 는 등 없이 **가을 안에** 이사"* 는 여전히 성립하지 않는다.

## 그래서 plan 이 골라야 할 것 (하나 이상)

| 후보 | 효과 | 대가 |
|---|---|---|
| **㉮ 반지하 식물등 출력을 올린다** (`data/lighting_presets.json` · `light_sources.json`) | 창턱 5.61 → 7.0+ · B 48% · C 65% | 등이 "안정성"만이 아니라 밝기도 사게 된다 |
| ㉯ 무늬 대역 `need_mult` 1.4 → 1.2 (`data/growth_tuning.json`) | 대역이 6.0~13.2 로 내려와 등 1개(5.61)가 거의 닿는다 | 무늬가 전체적으로 흔해진다 |
| ㉰ 첫 몬스테라 소질을 `normal` → `potential` | 잎당 13% → 32.5% · 등 없이도 성립 | `propagation.md` §7 의 "normal 고정"을 뒤집는다 |
| ㉱ 몬스테라 씨앗 선발을 반지하에 연다 | 여러 그루에서 골라 뽑는다 | **다개체 엔진이 필요하다**(`promoteToPot` 이 지금 던진다) |
| ㉲ 잎이 나는 속도를 반지하 구간에서 올린다 | 굴림 횟수가 는다 | 캐논(`ageOf`)을 건드린다 — 권하지 않는다 |

**㉮ 를 권한다.** `data/` 한 곳만 바뀌고, 캐논·정체성·확정 수치를 하나도 안 건드리며,
*"등은 자리를 못 이기지만 자리를 한 칸 올려 준다"* 는 `story_arc.md` §4 의 성격과도 맞는다.
⚠ 이 창은 `data/` 를 못 고친다 — **제안만 한다.**

# 5. `game.html` 이 부를 공개 API

```js
import {
  catalogList, buyPriceOf, orderItem, pendingOrders, stockOf, incomingOf,
  shopStatus, priceOf, varieLeavesNeededFor, sellPot, sellCutting
} from './src/game/shop.js';
import { resowCrop } from './src/game/state.js';

catalogList();                       // 상점 화면 목록 (id·ko·정가·살때·배송일)
orderItem(S, 'bean_seed', 3, {log}); // 결제 즉시 · 1일 뒤 도착. events 를 storyteller 에 넘긴다
shopStatus(S);                       // { stock, orders:[{...,daysLeft}], spentWon, earnedWon }

resowCrop(S, { sirus: 3, at: 'banjiha-dresser:1', slots });   // 씨앗·용기 재고를 쓴다

priceOf({ leaves, variegatedLeaves });          // "지금 팔면 얼마" 미리보기 (순수 함수)
varieLeavesNeededFor(1_500_000, { leaves });    // "몇 장 더 무늬여야 하나"
sellPot(S, { leaves, variegatedLeaves, log });  // ★잎 수는 growth 가 낸 값을 넘겨야 한다
sellCutting(S, cuttingId, { log });             // 삽수는 코어가 다 안다
// 배송·도착은 loop.nextDay 안에서 자동이다 — turn.shop 에 { events, arrived }
```

## ⏸ growth 에 필요한 것 — `handoff/core-to-growth.md` 요청

- **`leafStats()`** → `{ leaves, variegatedLeaves }`. 값은 잎으로 매기는데 잎은 growth 소유다.
  이게 없으면 브라우저에서 **판매 화면을 못 연다**(코어가 잎을 지어내지 않기로 했다).
- **`cuttableNodes()`** — 이미 요청돼 있다(`propagation.md` §7-2). 마디별로
  `{nodeId, stem, leaves, variegatedLeaves, growthDays}` 가 나와야 무늬 삽수를 잘라 팔 수 있다.
- **판 뒤의 형태 정리** — `sellPot` 은 화분을 지우지만 growth 의 3D 는 코어가 못 지운다.
  반환값 `growthNeedsReset: true` 로 알린다. 화면이 정리해야 한다.
