# 화면의 빛 — 모델과 이번 라운드에 고친 것

> **원칙: 보이는 것 = 계산되는 것.**
> 조도 엔진과 화면이 갈리면 플레이어는 "그늘인데 왜 밝다고 나오지"가 된다.
> 이번 라운드 사고 다섯 건이 전부 이 원칙이 깨진 자리였다.

---

## 1. 지금의 광원 — 셋뿐이다

| 광원 | 무엇 | 계산 쪽 대응 |
|---|---|---|
| **해** (DirectionalLight) | 방위·고도로만 정한다. 타깃은 방 중심 | 직사광 — 조도 엔진의 `weather`·`season` 계수 |
| **창 확산광** (SpotLight × 창 토막) | 창마다, 넓은 창은 2.2m씩 토막 | 천공 면광원 — `luxWins` 의 면적 × τ × evScale |
| **조명 기구** (`lightRigs`) | 방에 실제로 놓인 스탠드·펜던트·식물등 | `lums` — `pointIllum` 이 같은 기구를 쓴다 |

**이 셋 말고는 없다.** 환경광(hemi/ambient)은 바닥 채움이라 방향이 없다.

> `winLight1`(창 보조 스팟)·`ceilingBulb`(가상 천장등)는 **껐다.**
> 계산에 없는 광원이라 화면만 밝히고 있었다.

---

## 2. 이번 라운드에 고친 것

### ① 해가 "첫 창 → 하드코딩 타깃"이었다

```js
// 전
const wp = ctx.winPos;                              // 첫 창
sunLight.position.set(wp.x + sin(az)*5, ...);
sunLight.target.position.set(1.2, 0.5, 1.5);        // 하드코딩
```

해가 무한히 먼 광원이 아니라 **첫 창에서 특정 점을 겨누는 조명**이었다.
**창이 하나면 우연히 맞고, 여럿이면 첫 창만 맞는다.**
투룸(창 둘 + 칸막이)에서 처음 드러났다 — 왼쪽 작은방 창빛이 오른쪽으로 쏠려 칸막이에 막혔다.

→ 방위·고도만으로 방향을 정하고 타깃은 방 중심. 그림자 카메라는 ±12(아파트 대각 15.6m).

### ② 천장이 빛을 안 막았다

`visible=false` 로 감추면 three.js 가 **그림자 패스에서도 뺀다.** 해가 천장을 뚫고 들어왔다.
→ `colorWrite`/`depthWrite` 만 꺼서 안 보이되 그림자는 던지게 (`hidden-but-blocks`).

그런데 그 뒤 **내 리팩터가 같은 걸 다시 깨뜨렸다** — `box(...,false)`(그림자 렌더 생략)를
`transparent`(빛 통과)로 잘못 매핑해서 바닥·천장·걸레받이가 전부 빛을 통과시켰다.
→ `box()` 는 항상 `blocker`. 빛을 안 막는 건 유리뿐이고 명시적으로 붙인다.

### ③ 유리가 그림자를 던졌다

"껍데기 6면 모두 그림자 던지게" 하는 일괄 루프에 **칸막이 유리(베란다 전창)가 걸렸다.**
통유리가 불투명 그림자를 던져 거실·안방이 캄캄했다.
창틀은 이 이유로 이미 `trims` 로 빼놨는데 **칸막이 유리만 빠져 있었다.**

→ 예외를 목록이 아니라 **속성**으로. `src/render3d/shadow_policy.js`

```js
userData.shadowRole = 'blocker' | 'transparent' | 'hidden-but-blocks'
```

**`applyShadowPolicy` 만 `castShadow` 를 쓴다.** 빌더는 역할만 붙인다 —
`buildWindowFrame` 이 내부에서 켜고 있어서, 정책 루프가 그 뒤에 안 돌면 그대로 샜다.
실제로 정책을 `trims` 붙기 전에 돌려 **전 방 유리 72개**가 빛을 막고 있었다. **순서가 곧 버그였다.**

### ④ 감사가 한 방향만 봤다

③을 잡은 감사가 ②는 **0/0/0 으로 통과시켰다.**

```
✅ 유리가 그림자를 던지나   (막으면 안 되는데 막음)   ← 위양성만
❌ 천장이 그림자를 던지나   (막아야 하는데 안 막음)   ← 위음성은 안 봄
```

→ `auditShadowCoverage()` 추가. 바닥·천장·외벽 4면·칸막이가 각각 빛을 막는 메시를
하나라도 갖고 있어야 하고, `hidden-but-blocks` 는 실제로 `castShadow=true` 여야 한다.

### ⑤ 계산엔 있는데 화면엔 없던 빛

거실이 실제로 받는 건 **확산광**이다. 조도 엔진은 하늘을 "창 면적을 가진 램버시안 면광원"으로
봐서 거실 DLI 1.36 을 낸다. 그런데 렌더러엔 해 + 균일 환경광뿐이라 그 분포가 없었다.
"발코니엔 볕이 드는데 거실엔 아무것도 안 들어온다"로 보였다.

> 한낮에 볕이 발코니에서 멈추는 것 자체는 **맞다** — 고도 66°면 창 상단(2.3m)에서
> 볕이 1.03m 만 들어오는데 발코니 깊이가 1.72m다. 아침·오후엔 거실까지 든다.

→ 창마다 확산광. 그리고 **넓은 창은 토막 낸다** — 11.2m 통창을 점광원 하나로 두면
창 한가운데(거실)만 밝고 안방·방1 은 어둡다. 면광원을 점 하나로 줄인 게 원인이다.

| 방 | 포털 수 | 위치 |
|---|---|---|
| 반지하·원룸 | 1 | |
| 투룸 | 2 | 창마다 |
| 학원교실 | 4 | 7.2m 반전창이 3토막 + 교사방 1 |
| 아파트 | 5 | 발코니 통창 4토막(x −4.2/−1.4/1.4/4.2) + 부엌 1 |
| 온실 | 16 | 3면 유리 + 천창 |

## 4. ★ 계산 ↔ 화면 자동 대조 — `_render_vs_calc.html`

**픽셀을 읽지 않는다.** 그림자맵의 차폐는 결국 `castShadow=true` 인 메시가 정하므로,
**같은 메시에 레이를 쏘면 같은 판정을 재현**할 수 있다.
오프스크린 렌더·`readPixels` 가 필요 없고, 해상도·bias 에도 안 흔들리며 결정적으로 돈다.

```
A 외피 무결성  해 쪽 광선이 아무것도 안 만나고 탈출했는데 계산은 그 점이 0 이면
               → 창이 아닌 곳으로 새고 있다 (천장 사고가 정확히 이것)
B 차폐 일치    점 → 창중심 광선을 양쪽이 똑같이 막나
               계산만 막음 / 화면만 막음 을 갈라서 센다 (양방향)
```

### 이 검사가 실제로 찾아낸 것

처음 돌렸을 때 **586건**. 원인을 갈라 보니 절반 이상이 진짜였다.

| 찾은 것 | 건수 | 조치 |
|---|---|---|
| **유리벽·천창 격자살이 그림자를 던짐** | 343 | 창틀과 같게 `transparent` 로. 조도 엔진은 창틀을 모델링하지 않는다 |
| **도려낸 경계 벽(cutwall)이 조도 차폐체에 없음** | 39 | `occluders.push` 추가. 화면은 막는데 계산은 통과였다 |
| 고체 안에서 출발하는 점 | ~50 | 검사 결함 — 레이캐스터는 메시 안에서 시작하면 앞면을 못 만난다 |
| 도려낸 구역(집 밖)의 점 | ~40 | 검사 결함 — 방 안이 아니다 |

> ★ **`markShadow` 가 덮어쓰지 않는 성질이 여기선 역효과였다.**
> `buildWindowFrame` 이 이미 `BLOCK` 을 붙여놔서 `tileGlassFrames` 의 `CLEAR` 가 무시됐다.
> `{force:true}` 가 필요했다. "덮어쓰지 않는다"는 기본값이 항상 안전한 건 아니다.

### 남은 185건 — 알고 있는 모델 차이

| 갈래 | 건수 | 무엇 |
|---|---|---|
| **계산만 막음 ← furniture** | 113 | ★ **조도 엔진은 가구를 통짜 상자로 본다.** 다리만 있는 책상·선반 밑을 화면은 통과시키는데 계산은 막는다 |
| 화면만 막음 ← 칸막이 | 33 | 문틀 케이싱 등 `rectMinus` 조각에 없는 장식 부재 |
| 화면만 막음 ← 벽걸이 장식 | 9 | 액자·게시판. 조도 엔진은 `mount:'wall'` 을 차폐체에서 뺀다 |

**`furniture` 113 이 제일 크고 실제 영향도 있다.** 공간 기준 측정에서 책상 밑이
실제보다 어둡게 잡힌다. 다만 화분은 가구 **위**에 놓이므로 슬롯 값에는 영향이 없다.
→ 고치려면 가구 프리셋마다 "속이 빈 부분"을 표시해야 한다. **비용 대비 효과 판단 필요.**

### 회귀 감시로 쓰기

갈래별 **기준선**을 넣어 뒀다. 넘으면 새 불일치가 생긴 것이다.

```
furniture 120 · part 40 · decor 12 · cutwall 12 · etc 0
A(외피 무결성)는 0 이어야 한다
```

지금 A 는 **투룸 1건**만 남았는데, 그것도 가구 통짜 상자 문제와 같은 뿌리다
(계산은 가구가 창을 다 가린다고 보는데 화면은 가구 위로 빛이 넘어온다).

## 5. ★ 남은 사각지대

**계산과 화면을 자동으로 대조하는 검사가 없다.**
조도 엔진은 창만 광원으로 쓰고 화면은 지향광 + 확산광 + 기구를 쓴다.
둘이 어긋나도 자동으로 안 잡힌다 — 이번 사고 다섯 건 중 셋이 그 유형이었다.

**→ §4 로 해결했다.** 오프스크린 렌더가 필요할 줄 알았는데, 그림자맵의 차폐가
`castShadow` 메시로 결정된다는 걸 이용하면 레이캐스트로 충분했다.

**아직 안 보는 것**
- **밝기의 크기**는 안 본다. "막히나 안 막히나"(이진)만 본다.
  창 확산광의 세기 계수(0.30)가 조도 엔진과 얼마나 맞는지는 여전히 눈으로 봐야 한다
- 조도맵(높이 슬라이더)이 그 용도의 유일한 수단이다
