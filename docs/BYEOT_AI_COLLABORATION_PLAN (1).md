# 볕(byeot) — AI 협업·검토 운영안

**작성일: 2026-08-01**  
**상태: 합의안 / 단계적 도입**  
**목적: 복붙 부담을 줄이면서도, AI 조직 정비가 첫 플레이 완성을 방해하지 않도록 운영 구조를 정한다.**

---

## 0. 최종 결론

볕 프로젝트의 주 개발 체계는 **Claude 중심으로 유지**한다.

다만 같은 모델 계열이 기획·구현·검토까지 모두 맡을 때 생길 수 있는 집단 맹점을 줄이기 위해,  
**Codex/GPT를 독립 리뷰어로 단계적으로 참여**시킨다.

현재 우선순위는 자동화 조직을 크게 만드는 것이 아니라 다음 두 가지다.

1. **Claude Code 조율창을 최소 기능으로 도입해 복붙을 줄인다.**
2. **자취생 첫 플레이 가능 상태를 완성하고 재미를 직접 확인한다.**

Codex는 지금부터 상시 자동 리뷰어로 넣지 않는다.  
먼저 **자취생 첫 플레이 마일스톤에서 전체 감사를 한 번 수행**하고, 실제 발견 가치와 관리 비용을 확인한 뒤 확대 여부를 결정한다.

---

# 1. 운영 원칙

프로젝트의 기존 헌법을 유지한다.

> 얕게 누구나 / 깊게 덕후  
> 엔진 먼저, 게임 항상 염두  
> 데이터는 깊게, 기본 플레이는 단순  
> **한 번에 하나씩, 재미 확인 후 다음**

AI 협업 구조도 이 원칙을 따른다.

- 조직 설계가 게임 구현보다 앞서지 않는다.
- 새 문서를 만들기 전에 기존 정본과 중복되는지 확인한다.
- 자동화는 반복 비용이 실제로 확인된 부분부터 붙인다.
- 코드가 돌아가는 것과 결과가 타당한 것을 분리해서 검증한다.
- 재미 판단은 자동 시뮬레이션이나 코드 리뷰로 대체하지 않는다.
- 같은 모델이 만들고 같은 모델이 승인하는 폐쇄 구조를 피한다.

---

# 2. 현재 프로젝트에 이미 있는 기반

다음 구조는 새로 만들 필요가 없다.

| 목적 | 기존 정본 |
|---|---|
| 프로젝트 진입점 | `docs/INDEX.md` |
| 기획 정본 | `docs/GAME_PLAN.md` |
| 캐릭터별 플레이 흐름 | `docs/game_flow.md` |
| 게임 루프 명세 | `docs/game_loop_spec.md` |
| 창별 최신 상태 | `docs/handoff/STATUS.md` |
| 창 간 작업 인계 | `docs/handoff/{보내는창}-to-{받는창}.md` |
| 밸런스 근거 | `docs/balance_decisions.md` 및 `data/balance/*` |
| 실패·사고 기록 | `docs/silent_failures.md` |
| 자동 측정·감사 도구 | `_dli_probe`, `_space_probe`, `_shadow_audit` 등 |
| 수치 판정 범위 | `data/balance/acceptance.json` |

따라서 당장은 다음 문서를 별도로 추가하지 않는다.

- `CURRENT_STATE.md`
- `GAME_DESIGN.md`
- 별도 `DECISIONS.md`
- 범용 `task_queue.md`
- 별도 `SPRINT.md`

필요한 상태와 인계는 기존 `STATUS.md`와 `docs/handoff/*`를 우선 사용한다.

# 3. 역할 구조

## 3-1. 사용자 — 게임 총괄 및 최종 결정자

담당:

- 프로젝트 방향
- 재미와 감정적 체감
- 캐릭터 정체성
- 시스템 추가·삭제
- 서로 타당한 대안 사이의 선택
- 최종 승인

AI는 자료와 대안을 만들 수 있지만, 다음 판단은 사용자가 담당한다.

- 재미있는가
- 기다리는 시간이 지루한가
- 보상이 체감되는가
- 캐릭터의 서사가 살아 있는가
- 물리적 사실을 게임적으로 살릴 것인가, 완화할 것인가

---

## 3-2. Claude 앱 — 게임 디렉터

현재 대화형 Claude 창은 유지한다.

담당:

- 사용자와 기획 대화
- 게임 방향 탐색
- 캐릭터별 게임 구조 정리
- 시스템 간 의미 해석
- 시뮬레이션 결과의 게임적 해석
- 사람이 판단해야 할 질문 정리

Claude 앱은 파일 구현자가 아니라 **방향·재미·의미를 다루는 대화 공간**이다.

---

## 3-3. Claude Code 조율창 — 프로덕션 코디네이터

새로 추가할 우선순위가 가장 높은 역할이다.

조율창은 다음 네 가지만 담당한다.

1. `STATUS.md`와 모든 handoff를 읽는다.
2. 완료·대기·누락·충돌을 정리한다.
3. 다음 담당 창에 보낼 handoff를 직접 작성한다.
4. 사람 판단이 필요한 질문만 추출한다.

### 조율창 소유 범위

권장:

```text
docs/handoff/*
reports/coordination/*
agent/*
STATUS.md의 조율자 전용 섹션
```

### 조율창 금지 사항

```text
src/engine/* 직접 수정 금지
src/game/* 직접 수정 금지
plant_grow.html 직접 수정 금지
assets/* 직접 수정 금지
data/balance/* 직접 수정 금지
GAME_PLAN.md 임의 변경 금지
STATUS.md 전체 재작성 금지
남의 소유 파일을 대신 구현하는 행위 금지
```

조율창은 **일곱 번째 구현창이 아니라 전달·검증·정리 전용 창**이어야 한다.

---

## 3-4. 기존 Claude Code 작업창 — 구현팀

현재 구조를 유지한다.

| 창 | 역할 |
|---|---|
| `plan` | 기획 정본·밸런싱 데이터 |
| `core` | 게임 루프·게임 상태·게임 화면 |
| `house` | 집·방·조도 엔진·렌더링 |
| `growth` | 생장 시뮬레이션 |
| `leaf` | 잎·줄기·작물 에셋 |
| `char` | 캐릭터 에셋 |

각 창은 자기 소유 파일만 수정하고, 다른 창 작업은 handoff로 요청한다.

---

## 3-5. Codex — 독립 기술·수치 리뷰어

Codex는 Claude 위의 팀장이나 상시 공동 구현자로 두지 않는다.

권장 역할:

- 코드 diff 검토
- 문서와 구현의 불일치 탐지
- 데이터 계약 검증
- 테스트·측정 도구 실행
- NaN·누락·silent fallback 탐지
- 회귀 검사
- 시뮬레이션 결과의 통계적 타당성 검토
- 기존 감사 도구의 사각지대 제안

초기에는 읽기·실행·보고만 허용한다.

### 허용

```text
저장소 읽기
diff 분석
테스트 실행
측정·시뮬레이션 실행
리뷰 보고서 작성
재현 명령 제시
수정 후보 제안
```

### 금지

```text
구현 파일 직접 수정
GAME_PLAN.md 직접 수정
밸런스 계수 자동 변경
main 자동 병합
다른 창 handoff 임의 수정
사람 승인 없이 기획 방향 변경
```

---

## 3-6. GPT/ChatGPT — 독립 기획 감사자

GPT는 상시 작업창보다 **마일스톤 단위 외부 검토자**로 활용한다.

담당:

- 캐릭터별 플레이 구조 비교
- 경제 구조의 의미 분석
- 성립하지만 지루한 흐름 탐지
- 기획 문서 간 논리 충돌
- 과도한 복잡도 점검
- Claude 조직 전체가 공유한 전제에 대한 반론
- 대안 구조 제시

GPT 검토는 매 작업마다 호출하지 않는다.  
큰 의사결정이나 마일스톤에서 사용한다.

# 4. 단계별 도입 순서

## 단계 1 — 지금

목표:

> **복붙을 줄이고 자취생 첫 플레이 가능 상태를 완성한다.**

수행:

1. Claude Code 조율창을 만든다.
2. 기존 `STATUS.md`와 `docs/handoff/*`만 사용한다.
3. 작업창 완료 보고에 근거 형식을 적용한다.
4. 새로운 대규모 자동화 체계는 만들지 않는다.
5. Codex 상시 리뷰는 보류한다.
6. 자취생 A1~A4 플레이 루프를 우선 완성한다.

현재 성공 기준:

- 게임을 시작할 수 있다.
- 다음 날을 진행할 수 있다.
- 날씨와 DLI가 식물에 전달된다.
- 식물의 상태·성장 변화가 보인다.
- 말 피드백으로 변화의 이유를 전달한다.
- 좋은 자리와 나쁜 자리 차이가 체감된다.
- 첫 플레이에서 무엇을 해야 하는지 이해할 수 있다.

## 단계 2 — 자취생 첫 플레이 완성 시

Codex에 첫 마일스톤 전체 감사를 맡긴다.

검토 범위:

- `GAME_PLAN.md`와 구현의 일치
- `game_loop_spec.md`의 실행 순서 준수
- 빛 → 생장 → 경제 데이터 흐름
- `slotId`와 `daily_light/1` 계약
- `peak`, `avg7`, `space`, `slots` 혼용 여부
- silent fallback
- NaN·누락
- 파일 소유 침범
- 테스트·감사 도구의 사각지대
- 문서상 완료와 실제 연결 상태의 차이

동시에 사용자가 직접 플레이한다.

직접 확인할 항목:

- 첫 10분에 해야 할 일이 보이는가
- 다음 날을 누를 이유가 있는가
- 식물의 반응을 이해할 수 있는가
- 좋은 자리와 나쁜 자리 차이가 화면에서 느껴지는가
- 피드백이 과하거나 부족하지 않은가
- 기다리는 구간이 지루하지 않은가
- 실패가 억울한 버그가 아니라 선택 결과로 느껴지는가

## 단계 4 — 초기 플레이 검증 후

다개체 생장과 UI 없는 게임 루프가 준비되면 헤드리스 밸런스 시뮬레이터를 만든다.

흐름:

```text
시나리오 정의
→ 캐릭터·전략·난이도·랜덤 시드 설정
→ N일 또는 목표 도달까지 실행
→ 결과 JSON/CSV 생성
→ Codex가 수치·회귀 검토
→ GPT가 게임적 의미 검토
→ Claude 앱과 사용자가 최종 판단
```

초기에는 AI가 밸런스 값을 직접 변경하지 않는다.

```text
허용: 결과 분석, 원인 후보, 수정 후보 제안
금지: 목표값에 맞춰 계수 자동 수정·커밋
```

물리 엔진에서 우연히 발견되는 독특한 게임 메커니즘을 자동 최적화가 지워버릴 수 있기 때문이다.

# 5. 리뷰 표준

모든 AI 리뷰는 아래 형식을 기본으로 한다.

## 판정

```text
PASS
PASS_WITH_WARNINGS
BLOCK
```

## 중요도

```text
BLOCKER
- 게임 결과가 틀림
- 데이터 손실
- 계약 위반
- 파일 소유 침범
- 실행 불가 또는 진행 불가

MAJOR
- 수치 근거 부족
- 누적 판정 오류
- 회귀 가능성
- 문서·구현 불일치
- 플레이 흐름에 큰 부작용

QUESTION
- 둘 이상의 설계가 타당함
- 사람의 방향 판단이 필요함
- 정본 변경이 필요함
```

## 근거

문제 제기에는 가능한 한 다음을 포함한다.

```text
관련 파일 및 위치
실행 또는 재현 명령
입력 조건
실제 결과
기대 결과
영향 범위
```

근거 없이 “이상해 보인다”는 의견은 채택하지 않는다.

단, 화면 체감이나 재미처럼 숫자로 증명하기 어려운 문제는 `QUESTION`으로 올리고  
스크린샷·플레이 순서·관찰 내용을 근거로 첨부한다.


# 8. 자동화 확장 시 필요한 구분

## 하트비트

작업자가 현재 상태를 기록하는 신호다.

```text
running
done
blocked
failed
needs_human
```

하트비트만으로 다른 작업자가 자동 실행되지는 않는다.

## 디스패처

하트비트를 읽고 다음 작업을 실제로 실행하는 주체다.

```text
작업 완료 감지
→ 리뷰 실행
→ PASS/BLOCK 판정
→ 다음 handoff 확인
→ 해당 작업자 실행
```

따라서 장시간 자동 순환은 다음이 모두 있어야 한다.

```text
상태 파일
+ Hooks
+ 리뷰 규칙
+ 디스패처
+ 중단 조건
```

이 체계는 첫 플레이 완성 전에 만들지 않는다.

---

# 9. 자동 순환 중단 조건

향후 디스패처를 도입하더라도 다음 조건에서는 자동 작업을 멈춘다.

```text
needs_human = true
```

중단 대상:

- 게임 방향을 바꾸는 결정
- 정본 문서 변경
- 두 설계가 모두 타당한 경우
- 파일 소유 충돌
- 경제·성장 목표 범위 자체의 변경
- 예상하지 못한 물리 결과
- 재미와 체감에 관한 판단
- 기존 헌법과 충돌하는 확장
- 자동 리뷰어 사이의 결론 불일치

---

# 10. 밸런스 시뮬레이션 원칙

시뮬레이션은 “게임이 재미있는가”가 아니라 “수치가 성립하는가”를 검증한다.

## 자동 검증 가능

- 파산 확률
- 첫 수입 시점
- 목표 달성일
- 이사 시점
- 논문 완성 기간
- 희귀 무늬 발현 분포
- 식비 방어율
- 조명 투자 회수 기간
- 캐릭터별 난이도 편차
- 전략별 성과 차이

## 자동 검증 불가

- 지루한가
- 답답한가
- 보상이 기쁜가
- 실패가 납득되는가
- 캐릭터가 매력적인가
- 플레이어가 무엇을 해야 할지 이해하는가

최종 판정:

```text
자동 시뮬레이션 통과
+ 직접 플레이 재미 확인
```
