## 1. 무엇이 문제였나 (실측)

밝기가 **품질(갈라짐·무늬)만** 정하고 속도는 켜짐/꺼짐 두 값이었다.
7일평균이 `min`(3.0) 위면 달력 하루가 그대로 생장 하루, 아래면 0.
그래서 DLI 3.77 과 12.0 이 둘 다 "잎당 72일"이었고, 세 경로가 **바이트 단위로 같았다.**

```
A 등 없이 — 이사 189일 · 유효생장 249 · 잎 4장
B 등 1개  — 이사 189일 · 유효생장 249 · 잎 4장   ← 25,000원이 사는 것은 잔액 −25,000원뿐
C 늦게+등 — 이사 189일 · 유효생장 249 · 잎 4장
```

## 2. 어디를 골랐나 — 「곡선」이 아니라 「걷는 속도」

곡선은 유효 생장일 `GROWTH` 의 함수다. 그 함수는 그대로 두고,
**달력 하루가 생장일 몇 일어치인가**만 밝기가 정하게 했다.
자리는 `src/game/loop.js` 의 `advanceTo(달력+1)` 를 부르는 그 한 줄이다.

왜 여기인가:

- `advanceTo` 를 부르는 곳이 코어 전체에 여기 하나뿐이다.
- 하루를 통째로 다르게 다루는 길이 **이미 있다** — 머리공간 정지(`if (!headBlocked)`).
  새 개념을 만든 게 아니라 이미 있는 자리를 밴드로 넓힌 것이다.
- `setDailyLight` → `S.dliHist.push` 가 여기서 1:1 로 쌓인다. 그 짝이 곧
  세이브 재생(`save.restoreGrowth`)의 입력이라, **여기서 늘리면 재생도 같이 늘어난다**(§4).

밴드 판정은 **베끼지 않았다.** 조도 정본인 `judgeDLI`(`src/engine/daily_light.js`)를 그대로 쓴다.
`test_growth_speed C` 가 0~20 DLI 를 0.05 간격 401점 전수로 `plant_grow.bandOf` 와 대조한다.

## 3. ★왜 「빠르게」이고 「느리게」가 아닌가 — 이게 제일 중요한 판단이다

박사님 권고는 `slow` 를 내리고 `best` 를 1.0 에 두는 것이었다.
**그대로 먼저 만들어서 재 봤고, 두 군데가 깨졌다.**

`slow 0.7 · best 1.0` (= 어두우면 열흘에 이레를 걷는다) 실측:

| 검사 | 결과 |
|---|---|
| `test_balance_routes ①-1` | PASS (A 123일 vs B 204일) |
| **`test_banjiha_routes G-2b`** | **FAIL — A 이사 성공률 78% → 21%** |
| **`test_save H`** | **FAIL — 저장 53일 → 복원 57일** |
| `test_dialogue_coverage` | FAIL 4건 (이사 대사가 안 나온다 = 못 나간다) |
| `test_headroom F·G·H` | FAIL 3건 |

두 가지가 구조적이다.

**① 세이브가 안 맞는다.** `save.restoreGrowth` 는 `dliHist` **한 칸당 `advanceTo` 한 번**으로
되밟는다(save.js §growth). 코어가 하루를 삼켜도 재생은 안 삼키므로 형태가 어긋난다.
삼킨 하루를 이력에 남길 방법이 없다 — 그건 "빛이 없던 날"이 아니기 때문이다.
**늘리는 쪽은 반대다.** `setDailyLight` 를 한 번 더 부르는 것이 곧 이력 한 칸이라,
재생이 저절로 같아진다. 코어가 아무것도 더 저장하지 않아도 된다.

**② A 경로가 죽는다.** 반지하 창턱이 곧 `slow` 밴드이고 그 자리가 첫 플레이 자리다.
느리게 하면 튜토 전체가 같이 느려진다. `story_arc §2` 가 A 를 "표준"이라 부르는 한 못 쓴다.

그래서 **기준선을 `slow` 에 뒀다.** 지금까지의 속도가 곧 "겨우 자라는 속도"였다고 읽고,
밝은 자리에서 그보다 빨라지게 한다. **A 는 한 걸음도 안 바뀌고 B 만 빨라진다.**

> `loop.js` 는 1 미만 계수를 **안 받는다**(`source:'unsupported'`).
> 받으려면 `save.js` 의 재생도 같은 규칙을 알아야 하고, 그 파일은 이 창 소유가 아니다.

### 왜 1.25 인가 — 세 가지가 같은 답을 가리킨다

1. **작은 쪽에서 첫 번째로 결과가 바뀌는 값**이다. 1.15 는 속도만 바뀌고 이사 성공률은
   83% 그대로다 — 플레이어가 "등이 뭘 했지"를 못 읽는다. 1.25 에서 83% → **100%** 로 넘어간다.
   그 위는 전부 "더 커진 같은 답"이라 더 살 이유가 없다.
2. **빛의 실제 차이와 맞는다.** 창턱 DLI 는 등 0개 4.80 → 등 1개 6.64 로 **+38%** 다
   (tau 0.70 기준. tau 0.55 옛 값으로는 3.77 → 5.61 = +49%). 광합성은 포화 곡선이라
   생장 이득은 광량 증가보다 **작아야** 한다. +38% 빛에 +25% 생장이면 지수 약 0.65 —
   1.5 는 거의 선형이고 2.0 은 초선형(물리적으로 불가능)이다.
3. **A 가 안 죽는다.** A 는 83% · 189일 · 유효생장 249 · 잎 4장으로 **고치기 전과 완전히 같다.**

## 6. `plant_grow.html` 을 왜 안 건드려도 됐나

곡선은 **유효 생장일 `GROWTH` 의 함수**다. `143` 에서 `spear_ready`,
`146` 에서 `spear_furled` — 이건 "달력 며칠"이 아니라 "유효 며칠"에 걸려 있다.
코어가 바꾼 것은 **몇 달력일 만에 그 유효일에 닿는가**뿐이다.

`test_growth_speed` 가 그것을 두 방향으로 못 박는다:

- **D (회귀)** — `slow` 밴드(계수 1.0)에서 루프로 산 40일의 유효 생장일 열이,
  엔진을 하루씩 직접 굴린 40일과 **완전히 같다.** 계수가 1 이면 옛 코드와 한 걸음도 안 다르다.
- **E (곡선 불변)** — `143 → 3걸음 → 146 spear_furled`. `test_maturation G` 와 같은 안전선을
  이 파일에서도 다시 못 박는다.
- **F** — `best` 밴드 40일이 정확히 `floor(40 × 1.25) = 50`일. 계수만큼이고 그 이상도 이하도 아니다.

## 8. 못 한 것 / ★박사님 판단이 필요한 것

### ① `①-2` 와 `③-b` 는 이 손잡이로 못 고칩니다 — 밝기 문제가 아닙니다

```
FAIL ①-2   A 가 20판 중 5판만 가을에 끝난다 (중앙값 189일 = 겨울)
FAIL ③-b   튜토 완주가 게임 219일 — balance_decisions §D 목표 80일의 2.7배
```

둘 다 "튜토가 통째로 길다"는 **한 가지 문제**다. A 는 `slow` 밴드이므로,
이걸 고치려면 `slow` 를 1 위로 올려야 하는데 그러면 **어두운 자리도 같이 빨라져서**
"밝기가 속도를 바꾼다"가 성립하지 않는다. 실제로 재 봤다 — `slow 2.0 · best 2.0` 이면
①-2 는 PASS 지만 ①-1 이 다시 FAIL 이다(§4 아래 표).

잰 값으로는 `slow 1.5 · best 2.0` 이 A 126일 · B 107일로 ①-1·①-2 를 **둘 다** PASS 시킨다.
다만 `test_save` 와 `test_headroom` 이 깨진다(§3 ①과 같은 이유 + 머리공간 도달일 이동).
**전체 페이스를 2/3 로 줄이는 결정**이라 이 창이 혼자 내릴 값이 아니다 — 판단 부탁드립니다.
줄인다면 손잡이는 여기가 아니라 **생장 곡선의 총 길이**(`plant_grow` 소유)나
**이사 자금 150만원**(tutorial 소유) 쪽이 맞다고 봅니다.

### ② `good` · `over` 계수는 **안 정했습니다** (둘 다 1.0 / good 만 best 와 맞춤)

```json
"slow": 1, "best": 1.25, "good": 1.25, "over": 1
```

반지하 튜토는 `good`(11~16 DLI)·`over`(16 초과) 밴드를 **한 번도 안 지난다.**
못 재는 값을 지어내지 않았다. 다만 `good` 만은 `best` 와 같게 뒀다 —
1.0 으로 두면 DLI 13 인 식물이 DLI 3.5 인 식물과 같은 속도라는 뜻이 되어,
**빛이 늘수록 느려지는 구간**을 새로 만드는 셈이기 때문이다. 없는 차이를 만들지 않는 쪽을 골랐다.
`over` 는 1.0(예전 그대로) — 과광 벌칙은 이미 갈라짐·무늬 쪽에 있고,
속도까지 내리는 것은 재지 않은 새 벌칙이다.

→ **원룸·아파트 밸런싱 때 재서 채울 자리**입니다. 그 방들이 `good` 밴드를 실제로 씁니다.

### ③ ★`save.js` 에 한 줄 필요합니다 (그 파일은 이 창 소유가 아닙니다)

밝은 날은 `dliHist` 가 하루에 **두 칸** 쌓인다(빛 한 칸 = 하루 한 걸음이라야 재생이 같아지므로).
`save.js` 의 문서화된 계약 — *"`S.dliHist` 는 `setDailyLight` 와 1:1 로 쌓인다"* — 은 그대로지만,
거기서 파생된 교차검증 한 줄이 그걸 이상으로 읽는다:

```js
// save.js restoreGrowth
if (hist.length !== p.daysPlanted)
  warnings.push(`빛 이력 ${hist.length}일 ≠ 돌본 날 ${p.daysPlanted}일 — 중간에 깨진 턴이 있어…`);
```

**재생 자체는 정확하다**(`test_growth_speed H` 가 밝은 자리 왕복을 확인한다).
틀린 것은 진단 문구뿐이다 — 밝은 방에서 저장하면 복원 때마다 "깨진 턴" 경고가 한 줄 뜬다.
`hist.length < p.daysPlanted` 로 부등호를 좁히거나, 문구에 "밝은 날은 하루 두 칸"을 적으면 된다.
`tools/test_save.mjs` 의 `assert.equal(S.dliHist.length, 12)` 도 같은 이유로 언젠가 손봐야 한다
(지금은 그 검사가 창턱=`slow` 밴드라 안 걸린다).

### ④ 밴드는 계단입니다 — DLI 5.1 과 11.0 이 같은 1.25 입니다

`best` 밴드가 5~11 로 넓다. 지금은 그 안이 평평하다.
연속 함수로 바꾸는 것은 어렵지 않지만(계수를 DLI 로 보간),
**잴 데이터가 없어서 안 했다** — 반지하는 5.61·6.64 두 점밖에 안 지난다.
원룸·아파트가 붙어 밴드 안의 여러 점을 실제로 지나게 되면 그때 재는 것이 맞다고 봅니다.

### ⑤ 이 창은 `main` 보다 10 커밋 뒤에 있었습니다

작업 시작 시점에 이 워크트리에 `tools/test_balance_routes.mjs` 가 없었다(그 파일은 `main` 에 있다).
`git show main:tools/test_balance_routes.mjs` 로 가져와 돌렸고, **박사님이 말씀하신 FAIL 3건이
그대로 재현됐다**(189일 · 249 · 4장 · 271,500/246,500원까지 일치). 그래서 그대로 진행했다.
`data/window_presets.json` 의 tau 0.70 과 `data/profiles/room_profile.banjiha.json` 재생성분도
이 워크트리에는 없어서, **공유 체크아웃에서 잠깐 가져다 재고 되돌렸다**(§5 의 tau 확인).
내 커밋에는 그 두 파일이 **안 들어간다.**

## 인터페이스 (다른 창이 읽을 것)

```js
// src/game/loop.js
import { growthSpeedOf, GROWTH_STEPS_MAX } from './loop.js';

growthSpeedOf(dli7, th)
//   → { band, mult, source }
//     band   'critical'|'poor'|'stagnant'|'slow'|'best'|'good'|'over'|null
//     mult   달력 하루당 생장일. 1.0 이 바닥, GROWTH_STEPS_MAX(2) 가 천장
//     source 'tuning'      정본(data/growth_tuning.json)에서 읽었다
//            'default'     표가 없거나 그 밴드에 값이 없다 — 예전 그대로 돈다
//            'unknown'     빛·임계값을 못 읽었다
//            'unsupported' 표에 1 미만이 적혀 있다 — 안 받는다(세이브 재생이 못 따라온다)

// 턴에 실려 나가는 칸 (화면·검사용)
turn.growthSpeed   // 위 객체 그대로
turn.growthSteps   // 오늘 실제로 간 걸음 수 = 오늘 growth 에게 넘긴 빛 칸 수. 1 이면 예전과 같은 하루
```

`turn.growthSpeed` 는 `growthBlocked`(빛 부족)·`headroomBlocked`(머리공간)과 **다른 칸**이다.
처방이 다르기 때문이다 — 앞의 둘은 "등을 켜라 / 자리를 옮겨라"이고,
이건 **아무것도 막힌 게 아니다**("지금도 자라고 있고, 밝을수록 빠르다").
화면에 띄운다면 그 톤이어야 한다.
