## 2. 실측 — 세 곳을 나란히 재 봤다

켠 것: 반지하 · 첫 플레이(튜토리얼) · 등 0개 · 콩나물 3회전으로 도착 · 시드 92158 ·
**도착 직후**(Day 16, 아직 [다음 날]을 안 누른 순간) · 화분은 책상(`banjiha-desk:0`)에 자동으로 선다.

| 재는 곳 | 유효 생장일 | 잎 | 마디·줄기 메시 | 키 |
|---|---|---|---|---|
| **코어**(`io.growth`) | **45** | 1장 (`leaf_young`) | — | — |
| 도착 규격 `ARRIVAL.growthDays` | **45** | — | — | — |
| **확대창**(정본 iframe) | **45** | 1장 (`leaf_young`×1 · `sheath_young`×1) | 축 1 · 마디 2 | 로컬 1.010 (화분지름 0.901 기준) |
| ★ **방**(`room_view` → `plant_assemble`) | **365** | **5장** (`leaf_mid1`×2 · `leaf_mid2`×3) | `__stem`×5 · `stem_thick`×8 | **0.6679 m** |

**같은 순간, 방이 그린 그루가 확대창 그루의 3배다.**

### 무엇이 다른가 — 높이도 잎 크기도 화분도 아니다

| | |
|---|---|
| 화분 지름 | 방 **0.200 m** = 확대창 로컬 0.9009 × 배율 0.22201 → **한 자리도 안 어긋난다** |
| 잎 하나의 크기 | 같은 유효일이면 방과 확대창이 **같다**(아래) |
| 통째 배율 | `plant_assemble.assemble` 이 「화분 지름 = potD」로 맞춘다 — **맞게 돌고 있다** |
| ⇒ **다른 것** | **그리는 날짜뿐이다.** 45 대 365 |

**하루만 지나면 저절로 맞는다** — [다음 날]을 한 번 누른 뒤 다시 재니:

| | 코어 | 확대창 | 방 |
|---|---|---|---|
| 유효 생장일 | 46 | 46 | **46** |
| 잎 | 1 | 1 | 1 (`leaf_young`) |
| 키 | — | 로컬 1.048 | **0.2312 m** |

⇒ 어긋남은 **한 순간짜리가 아니라 「코어가 진행도를 못 넘겨 준 순간」 전부**다. 둘 있다.

### ★★ 그 순간이 둘이다 — 도착 때만이 아니다

| 언제 | 코어 | 확대창 | 방 |
|---|---|---|---|
| **도착 직후**(거두기에서 온다) | 45 | 45 | **365** |
| [다음 날] 뒤 | 46 | 46 | 46 |
| ★ **저장한 판을 다시 연 직후** | 45 | 45 | **365** |
| 그 판에서 [다음 날] | 46 | 46 | 46 |

**세이브를 다시 열 때마다 방의 몬스테라가 한 해 묵은 그루로 서 있다가,
[다음 날]을 누르는 순간 쪼그라든다.** 도착보다 이쪽이 더 자주 보이는 얼굴이다.

### 왜 365 인가 — 아무도 안 정한 값이다

`game.html §syncRoom` 이 방에 넘기는 진행도가 셋인데 **셋 다 `lastTurn` 에서 온다**:

```js
      phaseId:     lastTurn && lastTurn.growthPhase && lastTurn.growthPhase.phaseId,
      progress01:  lastTurn && lastTurn.growthPhase && lastTurn.growthPhase.progress01,
      growthDays:  lastTurn && lastTurn.effectiveGrowthDays,      // ← 5990행
```

`lastTurn` 은 **[다음 날]을 눌러야 생긴다**(`game.html:3770` 이 그렇게 적어 두었다).
그런데 **몬스테라는 [거두기]에서 온다**(`siruHarvest` → `harvestCrop` → `r.arrived`) —
그 순간 `lastTurn` 은 아직 화분이 없던 어제 턴이라 `effectiveGrowthDays` 가 `null` 이다.
새로 연 판은 아예 `lastTurn = null` 이다.

그러면 `room_view.growthDaysOf` 의 **셋째 길**로 떨어진다:

```js
    return Math.round(clamp(spec.progress01 ?? 1, 0, 1) * DEMO_SPAN_DAYS);   // DEMO_SPAN_DAYS = 365
```

`progress01` 도 없으니 `?? 1` 이 걸려 **1 × 365 = 365**. 그 길은 주석이 스스로
*"둘 다 없으면(데모·수동 조작)"* 이라 적어 둔 **데모의 길**인데, **게임이 매일 그 길로 가고 있었다.**

⇒ 이 저장소가 열넷째로 밟은 「조용히 짐작하는 자리」다. 짐작한 값이 하필 **그럴듯해서**
   (한 해 묵은 몬스테라는 진짜 그렇게 생겼다) 아무도 못 봤다.

### 어느 쪽이 맞나 — **작은 쪽이 맞다**

| 근거 | |
|---|---|
| 도착 규격 | `state.ARRIVAL.growthDays = 45` |
| 화분이 스스로 적은 값 | `pot.arrivalGrowthDays = 45` |
| 코어·확대창 | 둘 다 45 |
| 대사 | *"작은 걸 하나 줄 테니"* |
| 캐논 | 유효 45일 = 잎 **한 장**(`leaf_young`) |

**다섯이 45 를 가리키고, 365 를 가리키는 것은 아무것도 없다.**

### 고친 값도 쟀다 (START-HERE §2 넷째 규칙)

방에 코어의 유효일을 그대로 넘겨 봤다(런타임으로 §3 의 한 줄과 **같은 값**을 먹였다):

| | 유효일 | 잎 | 키 |
|---|---|---|---|
| 전 | 365 | 5 (`leaf_mid1`×2 `leaf_mid2`×3) | 0.6679 m |
| **후** | **45** | **1** (`leaf_young`×1) | **0.2227 m** |
| 확대창(같은 순간) | 45 | 1 | 로컬 1.010 |

검사로도 못 박았다 — `test_monstera_canon §H`:

```
    유효  45일 — 정본 잎 1 · 방 잎 1 · 방 키 0.2242m
    유효 150일 — 정본 잎 3 · 방 잎 3 · 방 키 0.5742m
    유효 365일 — 정본 잎 5 · 방 잎 5 · 방 키 0.6596m
```

⇒ **조립기는 받은 날짜대로 정확히 그린다.** 범인은 조립기가 아니라 **넘겨 주는 쪽**이다.

## 3. ⛔ 고칠 자리 — 붙일 코드 (내 쓰기 영역 밖)

### ① `game.html` §syncRoom · **5990행 한 줄** (이거 하나면 화면이 맞는다)

```js
      /* ⚠ lastTurn 은 [다음 날]을 한 번 눌러야 생긴다. 그런데 몬스테라는 **거두기**에서
         오고(siruHarvest → harvestCrop), 세이브를 다시 연 직후에도 lastTurn 이 없다.
         그 순간 유효일이 null 로 가면 방이 데모 기본값(365일)으로 짐작해 그린다 —
         도착 대사는 「작은 걸」인데 화면에는 잎 다섯 장짜리 한 해 묵은 그루가 섰다.
         코어는 그 값을 늘 갖고 있다. 못 받을 때는 코어에게 직접 묻는다.
         (실측·그림 docs/handoff/monsterasize-to-plan.md §2) */
      growthDays: (lastTurn && lastTurn.effectiveGrowthDays) ??
                  (() => { try { return io.growth.growthDays(); } catch { return null; } })(),
```

⚠ `??` 라야 한다. `||` 로 쓰면 **유효 0일(씨앗)이 코어 값으로 덮인다.**

### ② `src/game/room_view.js` §growthDaysOf (약 1467행) — **짐작을 그만두게**

①만으로 화면은 맞는다. 다만 **짐작하는 자리를 그대로 두면 다음 호출부가 또 밟는다.**

```js
    /* ★ 셋째 길은 **데모의 길**이다 — 0..1 슬라이더를 첫 해(365일)에 펼친다.
       ⚠ 게임이 여기로 떨어지면 조용히 「한 해 묵은 그루」가 선다. 실제로 그랬다:
         도착(유효 45일)과 세이브를 다시 연 직후에 방이 365일짜리를 그렸다
         (monsterasize-to-plan.md §2). 진행도를 **하나도** 안 준 spec 은 데모가 아니라
         「모르는 것」이다. 모르면 짐작하지 말고 그렇게 말한다. */
    if (spec.progress01 == null)
      throw new Error('몬스테라 진행도를 못 받았습니다 — growthDays·phaseId·progress01 이 셋 다 없습니다');
    return Math.round(clamp(spec.progress01, 0, 1) * DEMO_SPAN_DAYS);
```

⚠ **던지면 그 화분이 안 그려진다**(호출부가 `console.warn` 으로 받는다). 조용히 틀린 그루를
  세우는 것보다 낫다고 봤지만 **화면이 비는 쪽이 나쁘다면 ②는 빼고 ①만 붙여도 된다.**
  `tools/room_view_demo.html` 은 언제나 `progress01` 이나 `growthDays` 를 주므로 안 깨진다(확인함).

## 4. ★ 부팅이 렉 걸리던 이유 — **확대 iframe 이 437MB 를 받고 있었다**

### 다시 쟀다 (남의 숫자를 안 믿는다)

390×844 dpr2 · `localStorage.clear()` 뒤 새로 부팅 · `__rv` 준비 뒤 12초 더 기다린 시점 ·
`performance.getEntriesByType('resource')` 를 **본문과 iframe 에서 따로**.

| | **전** | **후** |
|---|---|---|
| 본문 `game.html` | 84개 · **20.07 MB** (GLB 15개 16.29MB · JS 2.36MB) | 84개 · 20.08 MB (**안 건드렸다**) |
| ★ 확대 iframe `plant_grow.html` | **118개 · 437.62 MB** (GLB **113개 436.66MB**) | **18개 · 14.71 MB** (GLB **13개 13.74MB**) |
| **합계** | **457.7 MB · 202개** | **34.8 MB · 102개** |
| JS 힙 | **72.6 MB** | **43.5 MB** (다른 판에서는 33.1MB) |
| `window.__rv` 준비까지 | **11,847 ms** | **6,768 ms** |
| 확대창(=iframe) 준비까지 | (이미 다 받은 뒤라 잼) | **9 ms** |

⇒ **iframe 이 받는 것이 96.6% 줄었다**(436.66 → 13.74MB). 전체로는 **457.7 → 34.8MB**.
제일 크던 것들(`mon_zebra_v1.glb` 7.10MB · `mon_zebra.glb` 6.44MB · `mon_zebra_v2.glb` 6.32MB …)
은 **전부 무늬 잎 스킨**이었고, 지금은 한 장도 안 받는다.

### 왜 다 받고 있었나

`plant_grow.html §loadAssets` 가 2026-08-03 에 **두 단계**로 나뉘어 있었다 —
기본을 먼저 받고 `ASSETS_READY` 를 켠 다음, **그 뒤에 `skins/` 를 전부** 받았다.
즉 **순서만 뒤로 밀렸고 받는 양은 그대로였다.** 주석은 *"뒤에서 무늬를 채운다"* 라고
적혀 있어서 읽는 사람이 「조금씩 받는다」로 읽게 되어 있었다(열다섯째 낡은 주석).

### 어떻게 고쳤나 — **그 잎이 그 무늬를 쓸 때 그 한 장만 받는다**

★ 고른 까닭: **변이는 잎마다 독립 판정**이라(캐논) **한 그루가 쓰는 무늬는 몇 장뿐**이고,
안 난 무늬는 화면에 한 픽셀도 안 나온다. 그러니 「열 때 다 받기」보다 **「쓸 때 한 장」**이 더 적다.
그리고 `pickLeafKey`·`drawLeafStage` 가 **예전부터** `if(ASSETS[k])` 로 없으면 기본잎으로
내려앉게 돼 있었다 — 그 자리에 한 줄만 더하면 되는 구조였다.

```js
function wantSkin(k){ if(!ASSETS[k]) ensureSkin(k); return !!ASSETS[k]; }
```

- `ensureSkin(k)` — 그 한 장만 받는다. 이미 있거나·받는 중이거나·한 번 실패했으면 아무 일도 안 한다.
  도착하면 **모아서 한 번** `redraw()`(잎마다 부르면 한 프레임에 여러 번 다시 짓는다).
- `skinsReady()` 의 뜻을 바로잡았다 — 「100장 다 받았나」로 두면 **영영 참이 안 된다**.
  지금 뜻은 **「지금 쓰려는 것을 다 받았나」**다. `skinsPending()`·`skinsLoaded()` 를 같이 냈다.
- **방 조립기는 아무것도 안 바뀐다** — `plant_assemble.js` 가 `ASSET_FILES` 에서 `skins/` 를
  아예 지우고 오므로 `ensureSkin` 이 그 자리에서 거짓을 돌려준다.
- ⚠ **파일을 지우거나 줄이지 않았다.** 바뀐 것은 **받는 시점과 개수**뿐이다.

### ⚠ 받는 동안 **말을 한다**

이 저장소의 지병이 「조용한 실패」다. 무늬 잎이 몇 초 동안 기본잎으로 그려지면
그 화면은 「무늬가 안 나온다」와 구별이 안 된다. 그래서 확대창 왼쪽 위에 한 마디를 띄운다:

> **🎨 무늬 잎을 받는 중… (11장)**

다 받으면 스스로 사라진다. 확대창(`.embed`)에서도 보이도록 **직접 만든 노드**라
패널을 감추는 `display:none` 에 안 걸린다. `docs/engine/shots/monstera_size/varie_loading_tip.png`
(2Mbps 로 늦춰서 찍었다 — 로컬에서는 너무 빨라 안 찍힌다).

### ★★ 무늬가 **실제로 나오는 것**을 보고 썼다

「안 받고 안 그리면 그건 고친 게 아니라 지운 것」이라 여기까지 봤다.
`P.varieProb` 을 **1.0**(plant_grow.html 이 *"튜닝용"* 이라 적어 둔 값)으로 켜고 400일 키웠다:

|---|---|
| 그려진 무늬 잎 | `leaf_mat7` · `leaf_mat46` · `leaf_mat4` · `leaf_mat10` · `leaf_mat1` — **다섯 장 전부 다른 무늬** |
| 받은 무늬 | **11장**(단계마다 갈아입어서 그렇다). 100장이 아니다 |
| 그때 누적 | GLB 24장 · 50.0 MB (최악의 경우다. 캐논값 0.20 에서는 실측 **잎 5장 중 1장** · 무늬 3장) |
