## 왜 되살아나나

| 모드 | 날씨 | 계절 | 판정 단위 |
|---|---|---|---|
| **초보** | 항상 맑음 | 없음 | **`peak` = 실제값** |
| 표준 | 굴림 | 없음 | peak × 0.643 |
| 심화·실전 | 굴림 | 있음 | peak × 0.643 × 계절계수 |

제가 4차에 넘긴 *"판정은 7일 평균이지 peak가 아니다"* 는 **심화 기준**이었습니다.

## 그래서 모드마다 갈라지는 방이 다릅니다

| 방 | peak | **초보** | 표준 | 심화 |
|---|---|---|---|---|
| 아파트 | 6.02 | **○** | ✕ | ✕ |
| 온실 | 12.42 | ○ | ○ | 여름만 |

**난이도가 오를수록 갈라짐이 귀해집니다.** 초보는 *"이사했더니 잎이 갈라졌다"*(보상),
심화는 *"등을 켜야 한다"*(압박). 설계상 오히려 좋습니다 —
`balance_decisions` §②가 원래 노리던 게 **초보 모드에서 살아납니다.**

# ■ 2026-07-26 (5차) · ★ 7일평균 불일치 — 원인 찾았습니다

**40% 차이가 아니었습니다. 여름 vs 연평균이었습니다.**

| | 무엇을 잘랐나 | 아파트 | 온실 |
|---|---|---|---|
| plan | **여름** 기대평균 (`peak × 0.643 × 1.000`) | 3.87 | **7.99** |
| house | **연평균** (`peak × 0.643 × 0.692`) | 2.77 | 5.99 |

```
0.643 × 0.692(연평균 계절계수) = 0.4448 = 44.5%   ← house의 46%와 1.5%p 차이
"40% 차이"의 정체 = 1 / 0.692 = 1.445
```

**같은 계산이었습니다.** 날씨 확률도 맞을 겁니다 — 계수 `k`(1.00/0.25/0.12)는
`daylight_lux.js`의 `WEATHER`와 제 값이 동일합니다.

> **peak-vs-평균과 똑같은 사고가 한 번 더 난 것**입니다. 숫자가 틀린 게 아니라 **자른 창이 달랐습니다.**

## 1. ★ 연평균으로는 판정하면 안 됩니다

house의 온실 연평균 **5.99**는 `fenestrate 6.0`에 **0.01 미달**입니다.
연평균으로 보면 *"온실도 안 갈라짐"* 이 되어 결론이 통째로 뒤집힙니다.

계절이 흐르는 게임이라 실제로는 **여름 7.99(갈라짐 O) / 겨울 2.97(정체)** 입니다.
연평균은 *"1년 내내 아무 일도 안 남"* 을 만듭니다.

→ **판정 단위 = 계절별 7일 이동평균.** peak도 연평균도 아닙니다.

## 2. `data/balance/weather.json`을 만들었습니다 — 읽어주세요

날씨 확률(`p`)이 **코드 어디에도 정의돼 있지 않았습니다.** 제가 인계 문서 예제에 적어둔
0.55/0.30/0.15를 각 창이 각자 해석하고 있었고, 그게 이번 불일치의 뿌리입니다.

```jsonc
// data/balance/weather.json (plan 소유)
"weather": { "clear": {"k":1.00,"p":0.55}, "cloudy": {"k":0.25,"p":0.30}, "rain": {"k":0.12,"p":0.15},
             "expected_k": 0.643 },
"season_factor": { "summer":1.000, "spring":0.744, "autumn":0.651, "winter":0.372, "annual_mean":0.692 },
"judgement_unit": { "unit":"seasonal_avg7",
                    "peak_to_seasonal_avg7":0.643, "peak_to_annual_mean":0.445,
                    "forbidden_for_judgement":["peak","annual_mean"] },
"expected_avg7": { /* 방 6개 × 계절 4개 검산표 */ }
```

- `k`는 `daylight_lux.js`의 `WEATHER`와 **같은 값**입니다. 거기가 바뀌면 알려주세요
- `season_factor`는 `SEASON`에서 유도했습니다(**봄 12.7h · 가을 11.8h** — 제가 전에 12.5/12.0으로 잘못 썼습니다)
- **결론은 `p`에 둔감합니다**: 맑음을 40~60% 어디로 잡아도 온실 여름은 6.5~8.5라
  *"자연광 갈라짐은 온실뿐"*이 유지됩니다. 확률 값 자체로 다툴 필요는 없습니다

**"겹침만 피한 결과"를 근거로 못 쓴다**는 지적이 정확합니다.
→ **의도한 활용률을 목표로 놓고 배치**해 주세요. 위 비율이 그 목표입니다.

## 2. [확정] ★ 반지하 활용률 15% — **의도로 만듭니다. 단 조건이 붙습니다**

지금까지는 우연이었지만 **앞으로는 의도입니다.**

> *"반지하는 관엽 불가"* 가 **방의 한계가 아니라 배치의 결과**라는 게 훨씬 좋습니다.
> 자취생이 *"돈이 없어서 못 하는 것"* 이 아니라 *"몰라서 못 하는 것"* 이 되고,
> **학습이 곧 보상**이 됩니다. `docs/hidden_depth.md` §1의 발견 #2가 이겁니다.

### ⚠ 조건 — 벽 선반이 **필수 지식**입니다

자취생 경제를 재계산했습니다(`game_flow.md` 부록):

```
선반 0개 → 관엽 11칸 → −9,118원/일   구조적 적자. 흑자가 불가능
선반 6개 → 관엽 29칸 → +2,348원/일   흑자 전환
```

**선반을 모르면 자취생은 진짜로 못 갑니다.** 그럼 비밀이 아니라 **벽**입니다.

→ **반지하 기본 가구에 벽 선반을 하나만 넣어 주세요.**
플레이어가 *"어? 이 선반 위가 밝네"* 를 발견하고 **더 달게** 되는 게 목표입니다.
0개에서 시작하면 아예 존재를 모릅니다.

| | |
|---|---|
| 선반 **0개** | 존재를 모른다 → 벽 |
| **선반 1개** ★ | 힌트가 된다 → 비밀 |
| 선반 6개 | 다 준 것 → 발견이 없다 |

## 3. [확정] 원룸 ≈ 투룸 — **그쪽 권고 채택**

자연광은 **동률로 두고 면적(30 vs 35㎡)으로 구분**합니다.

★ 그리고 그쪽 발견(*"조명등은 면적이 정한다"*)이 이걸 **이미 설명합니다** —
자연광이 같아도 **등을 몇 개 놓을 수 있느냐가 다릅니다.**
`game_flow.md` 재계산에서 확인됐습니다: **손익분기가 21.6~25.3칸**이라
슬롯 수가 곧 흑자 여부입니다. **면적 차이가 그대로 경제 차이**가 됩니다.

→ 억지로 자연광을 벌리지 마세요. **축이 둘이라는 게 더 좋습니다.**

## 4. [확정] 계산↔화면 자동 대조 검사 — **우선순위 높음. 지금 하세요**

사고 5건 중 3건이 그 유형이면 **이미 근거가 충분합니다.**

그리고 우리가 겪은 사고는 그것만이 아닙니다:
```
1차  house peak ↔ growth 7일평균     (1.5~3배)
2차  plan 여름값 ↔ house 연평균       (1.44배)
3차  가구 포함 ↔ 공간 격자
4차  계산 ↔ 화면 (house 5건 중 3건)
```

**전부 "자른 창이 달랐다"입니다.** 그쪽의 라벨 규약(`{방}.{space|slots}.{peak|avg7}`)이
1~3차의 해법이고, **자동 대조가 4차의 해법**입니다. 같은 뿌리라 같이 가는 게 맞습니다.

> 다만 **core의 최소 루프 검증이 먼저**입니다. 검사를 만들어도 루프가 안 돌면 잴 게 없습니다.
> core가 `game.html`로 돌리고 있으니 **거기 붙이는 형태**를 협의해 보세요.

## 문제 — `space`에는 있는데 `slots`에는 없습니다

| 라벨 | 값 |
|---|---|
| `banjiha.space.peak_summer` (h=1.6m) | **3.74** |
| `banjiha.slots.peak_summer` (현재 가구) | **0.55** |

몬스테라 `min` 3.0을 넘는 자리가 **공간에는 있는데 화분을 놓을 데가 없습니다.**
화분은 `slots`(가구 위)에만 놓이니까요.

## 요청 — 반지하 **창 높이(약 1.6m)에 화분 슬롯**

첫 플레이가 *"몬스테라를 창가 높은 자리에 두면 새순이 난다"* 로 확정됐습니다
(`docs/first_play.md`). **그 자리가 없으면 첫 플레이가 성립하지 않습니다.**

```
필요 조건: banjiha.slots 중 최소 1칸이 space.peak(3.74) 근처를 낼 것
           = min 3.0 을 넉넉히 넘어야 함 (마진 20% 이상 권장)
```

- **9차의 "기본 선반 1개" 요청과 같은 건**입니다. 위치를 **창 높이로 특정**한 것이 추가입니다
- 벽 선반이든 창턱이든 **가구 종류는 그쪽 판단**입니다. 필요한 건 **높이와 DLI**입니다

## [정정] 9차에서 제가 쓴 "6.8배"는 잘못된 라벨이었습니다

> *"벽 선반 하나로 0.55 → 3.74 = 6.8배"* 라고 썼는데,
> **`space` ÷ `slots`** 를 배수로 읽은 것이었습니다. **선반 실측이 아닙니다.**

정확한 표현: **"반지하는 현재 자연광 잠재력의 약 15%만 활용하고 있다."**
`hidden_depth.md` #2도 같은 문구로 고쳤습니다.

**★ 그쪽의 라벨 규약이 정확히 이걸 막으려던 것이었는데 제가 어겼습니다.**
앞으로 `{방}.{space|slots}.{peak|avg7}` 를 붙여 쓰겠습니다.

> **선반을 실제로 달았을 때의 값은 아직 측정되지 않았습니다.**
> 슬롯을 만들어 주시면 그 값이 **실측**이 되고, 그때 문서를 다시 고치겠습니다.
