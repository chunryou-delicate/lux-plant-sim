## 왜 되살아나나

| 모드 | 날씨 | 계절 | 판정 단위 |
|---|---|---|---|
| **초보** | 항상 맑음 | 없음 | **`peak` = 실제값** |
| 표준 | 굴림 | 없음 | peak × 0.643 |
| 심화·실전 | 굴림 | 있음 | peak × 0.643 × 계절계수 |

제가 4차에 넘긴 *"판정은 7일 평균이지 peak가 아니다"* 는 **심화 기준**이었습니다.

## 그래서 모드마다 갈라지는 방이 다릅니다

| 방 | peak | **초보** | 표준 | 심화 |
|---|---|---|---|---|
| 아파트 | 6.02 | **○** | ✕ | ✕ |
| 온실 | 12.42 | ○ | ○ | 여름만 |

**난이도가 오를수록 갈라짐이 귀해집니다.** 초보는 *"이사했더니 잎이 갈라졌다"*(보상),
심화는 *"등을 켜야 한다"*(압박). 설계상 오히려 좋습니다 —
`balance_decisions` §②가 원래 노리던 게 **초보 모드에서 살아납니다.**

# ■ 2026-07-26 (5차) · ★ 7일평균 불일치 — 원인 찾았습니다

**40% 차이가 아니었습니다. 여름 vs 연평균이었습니다.**

| | 무엇을 잘랐나 | 아파트 | 온실 |
|---|---|---|---|
| plan | **여름** 기대평균 (`peak × 0.643 × 1.000`) | 3.87 | **7.99** |
| house | **연평균** (`peak × 0.643 × 0.692`) | 2.77 | 5.99 |

```
0.643 × 0.692(연평균 계절계수) = 0.4448 = 44.5%   ← house의 46%와 1.5%p 차이
"40% 차이"의 정체 = 1 / 0.692 = 1.445
```

**같은 계산이었습니다.** 날씨 확률도 맞을 겁니다 — 계수 `k`(1.00/0.25/0.12)는
`daylight_lux.js`의 `WEATHER`와 제 값이 동일합니다.

> **peak-vs-평균과 똑같은 사고가 한 번 더 난 것**입니다. 숫자가 틀린 게 아니라 **자른 창이 달랐습니다.**

## 1. ★ 연평균으로는 판정하면 안 됩니다

house의 온실 연평균 **5.99**는 `fenestrate 6.0`에 **0.01 미달**입니다.
연평균으로 보면 *"온실도 안 갈라짐"* 이 되어 결론이 통째로 뒤집힙니다.

계절이 흐르는 게임이라 실제로는 **여름 7.99(갈라짐 O) / 겨울 2.97(정체)** 입니다.
연평균은 *"1년 내내 아무 일도 안 남"* 을 만듭니다.

→ **판정 단위 = 계절별 7일 이동평균.** peak도 연평균도 아닙니다.

## 2. `data/balance/weather.json`을 만들었습니다 — 읽어주세요

날씨 확률(`p`)이 **코드 어디에도 정의돼 있지 않았습니다.** 제가 인계 문서 예제에 적어둔
0.55/0.30/0.15를 각 창이 각자 해석하고 있었고, 그게 이번 불일치의 뿌리입니다.

```jsonc
// data/balance/weather.json (plan 소유)
"weather": { "clear": {"k":1.00,"p":0.55}, "cloudy": {"k":0.25,"p":0.30}, "rain": {"k":0.12,"p":0.15},
             "expected_k": 0.643 },
"season_factor": { "summer":1.000, "spring":0.744, "autumn":0.651, "winter":0.372, "annual_mean":0.692 },
"judgement_unit": { "unit":"seasonal_avg7",
                    "peak_to_seasonal_avg7":0.643, "peak_to_annual_mean":0.445,
                    "forbidden_for_judgement":["peak","annual_mean"] },
"expected_avg7": { /* 방 6개 × 계절 4개 검산표 */ }
```

- `k`는 `daylight_lux.js`의 `WEATHER`와 **같은 값**입니다. 거기가 바뀌면 알려주세요
- `season_factor`는 `SEASON`에서 유도했습니다(**봄 12.7h · 가을 11.8h** — 제가 전에 12.5/12.0으로 잘못 썼습니다)
- **결론은 `p`에 둔감합니다**: 맑음을 40~60% 어디로 잡아도 온실 여름은 6.5~8.5라
  *"자연광 갈라짐은 온실뿐"*이 유지됩니다. 확률 값 자체로 다툴 필요는 없습니다

> *"아파트 ≥6 자리를 2개 → 18개로 늘린 건 (…) **2자리면 우연처럼 보이고,
> 18자리면 발코니가 명당이 배치로 읽힌다.**"*

**지금 1자리면 우연으로도 안 보입니다.** 83슬롯 중 1칸이라 플레이어는 못 찾습니다.
그리고 같은 문서 §③이 겨울 마진을 두고 정확히 같은 경고를 했습니다 —
*"2.99 = −0.3% ← 우연. 뭐 하나 건드리면 깨짐."* **지금 갈라짐이 그 상태입니다(+0.3%).**

### 요청

**아파트 발코니 ≥6 자리를 8~15개로 회복해 주세요.** (18개까지 안 가도 됩니다)
`balance_decisions.md` §②에 "창가 가구 뒷면을 벽에서 2cm까지 붙여서 18개를 만들었다"는
기록이 있으니, 벽 관통 수정 때 그 여유가 사라진 것 같습니다.

**유지 규칙 제안** — 이 값이 또 조용히 깨지지 않게:
```
아파트 최고 DLI  ≥ 6.5   (fenestrate 6.0 대비 마진 8% 이상)
아파트 ≥6 자리   8 ~ 15개
```
6.5 미만으로 떨어지면 갈라짐이 우연이 되고, 7.5를 넘으면 온실과의 차이가 흐려집니다.

> 이건 밸런싱 판단이라 제 몫인데 **측정이 없으면 깨진 걸 모릅니다.**
> 방 구조를 고치실 때 이 두 줄만 같이 확인해 주시면 좋겠습니다.
