## 1. ① 붉은 띠 — 「막혔다」가 아니라 「방이 아니다」였다

### 1-1. 앞 워커가 §9 에 적어 둔 진단이 맞았다

방 치수(`roomSize`)는 **바깥 치수**다. 벽(두께 0.2m)이 그 선을 **걸치고** 서 있어서
(`house.js blockLine`: `at=±CW/2` 에 두께 `WT`) 반지하 5×4m 의 벽 안쪽 면은 ∓2.40 / ∓1.90 이다.
그런데 격자는 바깥 치수 위에 20×16칸을 통째로 깔았다. 제일 바깥 한 줄은 **절반이 벽 속**이고,
화분 반지름 0.101 을 얹으면 **언제나** 막힌다. 그 붉은 띠는 "여기 놓지 마세요"가 아니라
**"여기는 벽입니다"**였다 — 뜻이 다른 것을 같은 색으로 말하고 있었다.

⇒ **그 칸은 아예 안 그린다**(§9 ㉯안). 판정은 **한 줄도 안 건드렸다.**

### 1-2. 잰 값 — 여섯 방 전부

`showGrid(true, { potD: 0.202 })` 를 방마다 켜서 셌다.

| 방 | 바깥 칸 | **그린 칸** | 안 그린 칸 | 놓을 수 있는 칸 | 막힌 칸 | 방 안쪽[m] |
|---|---|---|---|---|---|---|
| 반지하 | 20×16 = 320 | **255** | 65 | 178 → **178** | 142 → **77** | 4.8×3.8 |
| 원룸 | 24×20 = 480 | **398** | 82 | 294 → **294** | 186 → **104** | 5.8×4.8 |
| 아파트 | 48×40 = 1920 | **1748** | 172 | 1249 → **1249** | 671 → **499** | 11.8×9.8 |
| 교실 | 44×24 = 1056 | **927** | 129 | 643 → **643** | 413 → **284** | 10.8×5.8 |
| 온실 | 40×48 = 1920 | **1752** | 168 | 1538 → **1538** | 382 → **214** | 9.8×11.8 |
| 투룸 | 28×20 = 560 | **471** | 89 | 307 → **307** | 253 → **164** | 6.8×4.8 |
| **합계** | **6256** | **5551** | **705** | 4209 → **4209** | 2047 → **1342** | |

★ **안 그린 칸 705 = 줄어든 막힌 칸 705.** 여섯 방 전부에서 정확히 같다.
즉 **안 그리게 된 칸은 하나도 빠짐없이 「막힌 칸」이었다.** 놓을 수 있는 칸은 한 칸도 안 줄었다.

### 1-3. 「안 그리는 것」과 「못 놓는 것」을 갈랐다 — 문 자리가 그 시험지였다

처음에는 **사각형으로** 잘라내려 했다(방 안쪽 4.8×3.8m 에 드는 칸만). 재 보니 그러면
반지하에서 **놓을 수 있는 칸 3개가 사라졌다**(178 → 175). 문 자리였다 —
문에는 벽 조각이 없어서 그 앞은 **진짜 바닥**이고 실제로 화분을 놓을 수 있다.

⇒ 규칙을 「사각형 밖」이 아니라 **「바깥 벽 조각에 물리는 칸」**으로 바꿨다. 문 자리는 남는다.

걸음(0.125m) 배수 자리를 **전수로** 훑어 실제 판정(`surfaceAt`)에 물어본 결과:

| 방 | 바닥에 놓을 수 있는 걸음 자리 | 그중 제일 바깥 줄(=안 그린 줄)에 드는 것 | 그것들이 있는 곳 |
|---|---|---|---|
| 반지하 | 688 | 10 | 전부 **문 자리**(z=1.875·2.0, x −1.875~−1.375) |
| 원룸 | 1091 | 10 | 전부 문 자리 |
| 아파트 | 3106 | **0** | — |
| 교실 | 2365 | 14 | 전부 문 자리 |
| 온실 | 5804 | 14 | 전부 문 자리 |
| 투룸 | 951 | 12 | 전부 문 자리 |

**바깥 줄에서 놓을 수 있는 자리는 전부 문 자리 하나뿐이고, 그 칸은 그리고 있다.**
문 자리를 뺀 나머지 바깥 줄에는 걸음 자리가 **0개**다 — 그래서 안 그려도 잃는 것이 없다.

> 왜 0 인가(반지하 x축으로 셈): 안 그리는 칸은 x −2.5~−2.25 다. 벽 안쪽 면이 −2.4 이므로
> 화분(반지름 0.101)이 설 수 있는 곳은 −2.299 부터다. 그 칸 안의 걸음 자리는 −2.5·−2.375
> 둘뿐이고 둘 다 벽에 걸린다. −2.25 는 **그린 칸의 테두리 선**이라 그대로 남아 있다.

### 1-4. 검사를 어떻게 고쳤나 — **자를 안 낮췄다**

- **Z-2** 예전 자(`cols===20 && rows===16`)를 **그대로 두고** 두 가지를 더 잰다:
  방 안쪽이 4.8×3.8m 인가 · 그린 칸이 255인가. 재는 항목이 1개 → 3개로 **늘었다.**
- **Z-4** 합계를 `20*16`(=320) 에서 **`room.cells`**(=255)로 바꿨다. 세는 대상이
  「방 바깥 치수의 칸」에서 「실제로 그린 칸」으로 바뀐 것이다. 그리고 이 파일 주석에
  **왜 줄어드는 것이 맞는지**(위 표: 줄어든 칸 = 줄어든 막힌 칸)를 적어 뒀다.
- 255 가 `18×14=252` 가 아닌 이유도 주석에 있다 — **문 앞 칸 3개**다.

### 1-5. 값이 아니라 셈이 바뀐 곳

- 격자 선은 이제 **그리는 칸의 테두리만** 긋고, 이어지는 선은 한 토막으로 합친다.
  선 토막 수는 오히려 **줄었다**: 반지하 38→35 · 아파트 90→86 · 온실 90→87.
- 「어느 칸이 벽 속인가」는 **방마다 한 번만** 센다(`spanCache`, 방을 다시 지으면 버린다).
  격자 한 번 만드는 시간 0.8~5.4ms → **1.2~8.6ms** (여섯 방·헤드리스 소프트웨어GL).
  드로우콜은 그대로 2개다. `test_roomview_perf`·`test_perf_budget` 은 그대로 통과한다.
- 벽 두께를 **0.2 로 적어 두지 않았다.** `built.colliders` 에서 **재서** 쓴다
  (`perimeterWalls`). house.js 가 두께를 바꿔도 여기가 조용히 안 맞는 일이 없다.

### 1-6. 새로 읽을 수 있게 된 값

```js
roomView.grid().room
// { w:5, d:4, cols:20, rows:16,            ← 바깥 치수(뜻이 안 바뀌었다)
//   cells: 255,                            ← ★ 실제로 그린 칸. free+blocked 과 같다
//   inner: { w:4.8, d:3.8, x0:-2.4, x1:2.4, z0:-1.9, z1:1.9 } }   ← 벽 안쪽 면
```

## 2. ② 가구를 「밝히는」 창구

박사님: *"가구 클릭 시 옮기기 이런 선택창이 밑에가 아니라 **가구가 살짝 밝아지면서**
활성화된 것처럼 되면서 그 옆으로 선택 가능 메뉴들이 뜨게."*

**메뉴는 game.html 몫이다.** 여기서 한 것은 「밝히는 것」과 「메뉴를 띄울 화면 좌표」뿐이다.

### 2-1. 윤곽선이 아니라 **밝기**다

말씀이 "살짝 밝아지면서"라 윤곽선(테두리)을 안 썼다. 재질을 **복제해서** emissive 를 얹는다.

- 무늬(`map`)가 있으면 **그 무늬를 `emissiveMap` 에 그대로 물려 준다.** 흰빛을 통으로
  얹으면 나뭇결이 사라져 「밝아졌다」가 아니라 「하얘졌다」가 된다.
- 무늬가 없으면 제 색을 emissive 로 쓴다 — 색은 그대로고 밝기만 오른다.
- 세기 기본값 `0.16`. `{ strength: … }` 로 바꿀 수 있다.
- **원본 재질은 안 건드린다.** 공유 재질이라 건드리면 방 전체가 같이 밝아진다.
- **스스로 빛나는 부품(전구·갓)은 건너뛴다.** 그 재질의 `emissiveIntensity` 는 등을 켜고 끄는
  코드가 따로 만진다 — 갈아 끼우면 되돌리는 순간 켜짐 상태가 옛날로 돌아간다.

### 2-3. 창구

```js
const h = roomView.highlightFurniture(uid);       // 밝힌다(한 번에 하나)
roomView.highlightFurniture(null);                // 끈다 — 원래 재질로 정확히 되돌린다
roomView.highlightFurniture(uid, { strength: 0.24 });
roomView.highlightedFurniture();                  // 지금 밝은 uid (없으면 null)

// h = furniture() 한 줄(uid·name·size·x·y·z·rot·moved) + 다음 셋
//   h.lit     밝힌 메시 수
//   h.screen  가구 **발밑**의 화면 좌표 { x, y }
//   h.top     가구 **머리 위**의 화면 좌표 { x, y }   ← 메뉴는 대개 이 옆이다
```

**좌표계는 캔버스 기준 CSS 픽셀**이다(`screenPosOf` 와 같은 규약 — 뷰포트가 아니다).
`canvas.getBoundingClientRect()` 의 left/top 을 더해야 마우스 좌표와 같은 자가 된다.

그리고 **`screenPosOf` 가 이제 가구 uid 도 받는다.** 시점을 돌리면 메뉴가 따라가야 하므로
프레임마다 이걸로 다시 물으면 된다(자리 열쇠로 못 풀면 가구에서 찾는다. 카메라 뒤면 `null`).

```js
roomView.screenPosOf('banjiha-desk')   // → { x, y } 가구 **발밑**(캔버스 기준)
```

## 3. ③ 「상대 이동」 포인터 모드

박사님: *"클릭을 터치 또는 그 커서를 **상대 이동**으로 움직이게 설정에서 고를 수 있게."*

### 3-1. 먼저 무엇이 상대이고 무엇이 아닌지를 **재 봤다**

인계 지시에는 *"지금 화분 끌기·걷기는 손가락 자리로 바로 간다"* 고 적혀 있었다.
**재서 확인한 결과 그건 틀렸다.** 반박한다 — 화분 끌기와 걷기는 **예전부터 상대**다.

재는 자: 그 조작의 기준점을 잡고 **손가락을 하나도 안 움직였을 때**(dx=dy=0) 물건이 튀는 거리.
상대라면 0 이어야 한다.

| 조작 | 기준점을 누가 잡나 | 튀는 거리 |
|---|---|---|
| 걷기(walkDrag) | **방뷰가 스스로** — 캐릭터 발밑 | **0 m** |
| 화분 끌기 | game.html 이 `screenPosOf(slotId)` 로 | **0 m** (창턱·책상·서랍장 자리 4곳 전수) |
| 시점 회전 | 방뷰 — 각도를 끈 만큼 더한다 | (원래 상대다) |
| **가구 끌기** | game.html 이 **손가락이 눌린 자리**(`tapX`)로 | **0.25~0.91 m** ← 여기가 문제였다 |
| **등 끌기** | 같음(`tapX`) | 같음 |

즉 상대로 **바꿀 것이 남아 있는 곳은 가구 끌기·등 끌기 둘뿐**이고, 그 둘은 **game.html 이
기준점을 잡는다.** 그래서 방뷰는 **모드와 기준점**을 내주고, game.html 이 한 줄로 받아 간다.

가구가 튀는 것은 일부러 그렇게 둔 것이다 — 2026-08-06 에 *"마우스는 가구를 안 가린다,
그러면 직접 집는 게 맞다"* 고 정했다. **폰은 손가락이 가구를 가린다.** 그래서 「고르게」가 맞다.

### 3-2. 잰 값 — 가구를 발자국 모서리에서 잡았을 때 (반지하)

| 가구 | direct(기본·지금 그대로) | relative |
|---|---|---|
| 싱글 침대 | 0.913 m | **0.001 m** |
| 책상 | 0.537 m | **0.001 m** |
| 의자 | 0.249 m | **0.000 m** |
| 서랍장 | 0.402 m | **0.001 m** |
| 선반 | 0.309 m | **0.001 m** |

남는 1mm 는 화면 픽셀을 되쏘는 반올림이다(390px 폭에서 1px 이 약 1.4cm).

### 3-3. 창구

```js
roomView.setPointerMode('direct' | 'relative');   // 기본은 'direct'
roomView.pointerMode();                           // 지금 모드
roomView.pointerModes();                          // ['direct','relative']
roomView.dragOrigin(id, tapX, tapY);              // → { x, y, mode, from:'tap'|'object' }
```

- **기본값은 `direct` 다.** 검사 P-1 이 못 박는다. 모르는 모드는 거절하고 모드도 안 바뀐다(P-4).
- `dragOrigin` 의 좌표는 **뷰포트 CSS 픽셀**이다(`clientX/clientY`·`surfaceAt` 과 같은 자).
  `screenPosOf` 만 캔버스 기준이라는 예전 규약은 안 건드렸다.
- `id` 는 가구 uid · 자리 열쇠 · 화분 id · 캐릭터 id 를 다 받는다.
- relative 인데 그 물건이 화면 뒤에 있으면 **손가락 자리로 물러난다**(`from:'tap'`).
  그래야 "아무 반응이 없다"가 안 생긴다.
- ⚠ **화분 끌기에는 쓰지 마라.** 화분은 이미 상대다 — `dragOrigin` 을 끼우면 direct 모드에서
  화분이 **오히려 손가락으로 순간이동한다.** 지금 손버릇이 바뀐다.

## 4. `game.html` 이 붙일 코드

### 4-0. ① 은 붙일 게 없다

붉은 띠는 방뷰 안에서 끝났다. `freePlace.grid(true, …)` 는 그대로 두면 된다.

### 4-1. ② 가구를 누르면 밝아지고, 메뉴가 그 옆에 뜬다

`furnPicked.select` / `furnPicked.clear` 에 각각 한 줄씩이다(지금 4652·4670줄 언저리).

```js
  select(f, px, py) {
    if (drag.on || picked.mode || this.mode) return;
    picked.clear();
    this.uid = f.uid; this.base = { x: f.x, z: f.z, rot: f.rot || 0 };
    this.tapX = px; this.tapY = py;
    /* ★가구를 **살짝 밝힌다**(박사님 2026-08-08). 메뉴가 아니라 가구가 골라진 것으로 보여야 한다.
       돌려주는 값에 메뉴를 띄울 화면 좌표가 들어 있다(h.top = 가구 머리 위·캔버스 기준). */
    let h = null; try { h = roomView.highlightFurniture(f.uid); } catch { }
    this.anchor = h && (h.top || h.screen);      // 캔버스 기준 CSS 픽셀
    placeFurnMenu(this.anchor);
    …
  },
  clear() {
    if (!this.uid && !this.mode) return;
    try { roomView && roomView.highlightFurniture(null); } catch { }   /* ★ 반드시 끈다 */
    this.uid = null; this.mode = null; this.ghost = null;
    …
  },
```

메뉴를 **가구 옆**에 놓는 것은 이렇게 하면 된다. 좌표가 캔버스 기준이라 rect 를 더해야 한다.

```js
/* ★ 가구 옆 메뉴 — 화면 좌표는 방뷰가 준다. 시점을 돌리면 따라가야 하므로
   프레임마다 screenPosOf(uid) 로 다시 묻는다(같은 규약·같은 점이다).
   ⚠ screenPosOf 는 **캔버스 기준**이다. 마우스 좌표와 섞으려면 rect 를 더해야 한다.
   ⚠ 카메라 뒤로 넘어가면 null 이 온다 — 그때는 메뉴를 감춘다(0 으로 메꾸면 왼쪽 위로 튄다). */
function placeFurnMenu(p) {
  const el = $('furnMenu');                       // ← 새로 만드는 떠 있는 메뉴 상자
  if (!p) { el.classList.remove('on'); return; }
  const r = $('roomCanvas').getBoundingClientRect();
  const x = r.left + p.x, y = r.top + p.y;
  el.classList.add('on');
  el.style.left = Math.max(8, Math.min(innerWidth - el.offsetWidth - 8, x + 12)) + 'px';
  el.style.top  = Math.max(8, Math.min(innerHeight - el.offsetHeight - 8, y - 8)) + 'px';
}
/* 시점이 돌아가는 동안 따라가게 — 방뷰의 프레임에 얹는 것이 제일 싸다 */
function tickFurnMenu() {
  if (!furnPicked.uid) return;
  let p = null; try { p = roomView.screenPosOf(furnPicked.uid); } catch { }
  placeFurnMenu(p);
}
```

`tickFurnMenu` 는 이미 있는 프레임 훅(카메라가 움직일 때 부르는 자리)에 얹으면 된다.
없으면 `requestAnimationFrame` 한 줄로 돌려도 된다 — 하는 일이 투영 한 번이라 싸다.

⚠ **밝히기를 끄는 것을 빠뜨리면 가구가 계속 밝다.** `clear()` 말고도 방을 바꾸거나
가구를 옮겨 놓은 뒤에도 `clear()` 가 불리는지 확인하시라. (방뷰 쪽은 방을 다시 지을 때
스스로 되돌린다 — `assemble` 이 `clearFurnHighlight()` 를 먼저 부른다.)

### 4-2. ③ 상대 이동 — 두 줄

`furnPicked.beginMove` (지금 4700줄 언저리):

```js
    this.mode = 'move';
    /* ★기준점을 **포인터 모드**에 맡긴다(2026-08-08).
       direct(기본)  = 지금 그대로 — 손가락이 눌린 자리
       relative      = 가구 제자리 — 손가락을 안 움직이면 가구도 안 움직인다
       ⚠ dragOrigin 은 **뷰포트 좌표**를 받고 준다(clientX/clientY 와 같은 자). */
    const o = roomView.dragOrigin(this.uid, this.tapX, this.tapY);
    this.originX = o.x; this.originY = o.y;
```

`furnPicked.beginLampMove` (지금 4741줄) 도 같은 두 줄이다.

```js
    const o = roomView.dragOrigin(this.uid, this.tapX, this.tapY);
    this.originX = o.x; this.originY = o.y;
```

말도 모드에 맞춰 갈라 주는 편이 낫다(지금은 마우스/손가락으로만 가른다):

```js
    $('dropLabel').textContent =
      roomView.pointerMode() === 'relative' ? '아무 데나 잡고 끈 만큼 움직입니다'
      : isMousePointer() ? '가구를 잡고 끌어 놓으세요' : '아무 데나 잡고 끌어 보세요';
```

설정 UI·저장은 조정 창 몫이다. 방뷰는 값을 안 저장한다 — 켤 때 한 번 넣어 주시라.

```js
roomView.setPointerMode(S.opt.pointerMode || 'direct');
```

⚠ **화분 끌기(`picked.beginMove`)와 걷기는 손대지 마라.** §3-1 표대로 이미 상대다.

## 5. 못 한 것 · 박사님 판단이 필요한 것

1. **칸막이 위 칸은 여전히 붉다.** 이번에 뺀 것은 **바깥 벽**뿐이다. 아파트·투룸·교실·온실의
   방 안 칸막이에 물리는 칸은 예전대로 「막힌 칸」으로 붉게 나온다. 같은 논리를 대면 그것도
   「방이 아니다」지만, 칸막이는 두께가 0.14m 라 물리는 칸을 지우면 **놓을 수 있는 자리가
   지워질 수 있다**(칸막이 선에서 0.171~0.25m 사이). 재 보지 않고는 못 지운다 —
   **하실지 말씀해 주시면 그때 재서 한다.**
2. **문 자리 칸은 남겨 뒀다.** 거기는 실제로 놓을 수 있는 바닥이라 그렇다. 다만 그림으로는
   격자 한 귀퉁이가 문 쪽으로 톡 튀어나온 모양이 된다. "문 앞에는 아예 못 놓게 하자"는
   **판정** 이야기지 격자 이야기가 아니다 — 그러길 원하시면 판정 쪽에 얹어야 한다.
3. **밝기 세기 0.16 은 눈으로 안 골랐다.** 숫자로만 골랐다(1.0 이면 전구처럼 탄다).
   폰에서 보시고 "너무 약하다/세다" 하시면 `FURN_HL_K` 한 줄이다.
4. **밝히기는 그 가구 하나만 밝힌다.** 책상을 밝혀도 책상 위 클립등·화분은 안 밝아진다.
   「얹힌 것까지 같이 밝힐까」는 `ridersOf` 가 있으니 한 줄이지만, 무엇이 골라진 건지
   흐려질 것 같아 **안 했다.**
5. **relative 모드를 폰에서 손으로 안 만져 봤다.** 숫자로는 0.001m 이지만 "끌리는 느낌"은
   못 쟀다. 특히 **가구를 멀리 옮길 때** 상대 이동은 손가락이 화면 밖으로 나가기 쉽다
   (direct 는 한 번에 간다). 만져 보시고 "가구는 direct 가 낫다" 하시면 모드에서
   가구만 빼는 것도 한 줄이다.
6. **`game.html` 은 안 고쳤다.** ②③ 은 §4 를 붙이기 전까지 **아무 일도 안 일어난다.**
   붙이는 것은 조정 창 몫이다.
7. **눈으로는 헤드리스 화면 한 장씩만 봤다.** 반지하를 화분 격자로 켜서 예전/지금을 찍어
   견줬다 — 예전 그림에는 네 벽을 따라 붉은 띠가 한 줄 돌고, 지금 그림에는 **없다.**
   가구·상판 근처의 붉은 칸은 그대로 남아 있다(그건 진짜로 막힌 칸이다).
   다만 **폰 실물에서는 못 봤다.** 밝기가 「살짝」으로 보이는지도 **박사님이 보셔야 한다.**
