## 1. 먼저 잰 것 — **잎이 화면에서 몇 픽셀인가**

「512면 충분하다」를 짐작으로 정하지 않았다. 잎 한 장이 화면에서 차지하는 **기기 픽셀**을
먼저 쟀다(`tools/test_skinsize.mjs measure` · `zoom`). 월드 바운딩박스 여덟 꼭짓점을
카메라로 투영하고 dpr 을 곱한 값이다.

| 화면 | 캔버스 | 제일 큰 잎 | 2048 텍스처면 화면 1픽셀당 |
|---|---|---|---|
| **방** · 폰 390×844 dpr2 | 682×1130 그리는 버퍼 | **41 기기px** | **49.8 텍셀** |
| **방** · 데스크 1280×900 | 920×900 | 52 기기px | 39.8 텍셀 |
| **확대창** · 폰 390×844 dpr2 | 390×844 CSS · dpr 2 | **367 기기px** | **5.6 텍셀** |
| 확대창 · 데스크 1280×900 | 1280×900 | 196 기기px | 10.5 텍셀 |

⇒ **방에서는 2048이 50배 낭비다.** 해상도를 정하는 자리는 방이 아니라 **확대창**이고,
  거기서도 잎은 367픽셀이다.

★ 잎 UV 는 텍스처 전체를 쓴다(실측 uv span 0.98~1.00). 다만 앞뒤 두 면이 한 장을 나눠 쓰므로
  보이는 면이 쓰는 것은 대략 그 절반이다. 그래서 1024 면 확대창에서 **화소당 약 1.4 텍셀**이 된다.

⚠ 확대창은 휠·핀치로 **최대 8배**까지 당길 수 있다(`plant_grow.html:2549`). 8배로 당기면
  잎이 약 2,900픽셀이 되는데, 그건 **원본 2048로도 모자라는 배율**이다. 그래서 해상도를
  고르는 기준으로 안 썼다. **못 잰 것**: 사람이 실제로 얼마나 당겨 보는지는 안 쟀다.

## 2. 그래서 고른 것 — **1024 × 1024 · JPEG 품질 88 · 4:4:4**

### 알파부터 확인했다 (JPEG 를 쓸 수 있나)

`tools/shrink_skins.py --scan` 으로 GLB 104장 안의 이미지 **116장을 전부** 열어 봤다.
**전부 2048×2048 RGB 이고 알파가 한 장도 없다.** ⇒ JPEG 를 쓸 수 있다.
(그래도 도구에는 안전장치를 뒀다 — 알파가 실제로 쓰이면 JPEG 대신 WebP 로 돌린다)

### 왜 1024인가 — 512 는 **눈으로 보고 물렸다**

`docs/handoff/img/skinshrink/tex_2048_1024_512_256.png`
(세 갈래를 2048 · 1024 · 512 · 256 으로 나란히, 전부 **잎이 화면에서 차지하는 367px** 로 키워서)

| | 보이는 것 |
|---|---|
| 1024 | 2048과 **구별이 안 된다** |
| 512 | **제브라의 가는 줄무늬**가 뭉개지기 시작한다. 크림 바탕의 잔점도 옅어진다 |
| 256 | 제브라가 통째로 죽는다. 갤럭시의 잔별이 사라진다 |

제브라·갤럭시가 제일 잔 무늬라 여기서 갈렸다. **무늬가 메인이라 하셨으니 여기서 아끼지 않았다.**
1024 와 512 의 값 차이는 전체 100장에 **약 14MB**(0.32 vs 0.19MB/장)뿐이라 아낄 값어치가 없다.

### 왜 JPEG 인가

| 형식 | 1024 로 만든 크기(차콜/스페클/제브라) | PSNR | 골랐나 |
|---|---|---|---|
| PNG(무손실) | 1.37 / 1.61 / 2.24 MB | ∞ | ✗ 너무 크다 |
| **JPEG q88 4:4:4** | **0.28 / 0.46 / 0.73 MB** | 42.9 / 38.1 / 33.8 | **○** |
| WebP q86 | 0.20 / 0.30 / 0.52 MB | 41.5 / 35.3 / 31.4 | ✗ (§6 판단필요) |

WebP 는 **브라우저에서 실제로 실어 봤다** — `THREE.GLTFLoader` 가 1024×1024 ImageBitmap 으로
멀쩡히 받는다(크롬). 40% 더 작지만 **안 골랐다**: 무늬가 메인인데 형식 하나로 옛 사파리에서
안 보일 위험을 지고 갈 값이 아니고, JPEG 로도 이미 12.7배가 줄었다. 더 줄일 여지는 남겨 뒀다(§6).

⚠ **4:4:4 로 저장한다**(`subsampling=0`). 무늬는 **색으로 나뉘는 것**이라 기본 4:2:0 으로
  크로마를 반으로 줄이면 핑크·라임 경계가 번진다. 그건 무늬를 줄이는 것이다.

⚠ **법선맵·거칠기맵은 JPEG 로 안 만졌다.** 그건 색이 아니라 방향이라 뭉개면 빛이 이상해진다.
  512 무손실 PNG 로 따로 줄인다(해당되는 것은 하프문 줄기 계열 4장뿐이고 원래도 작다 — 0.04·0.45MB).

## 5. ★★ 무늬가 안 뭉개졌나 — 이게 제일 중요한 자다

### ① 색 가짓수 (§2.9-③ 이 준 자) — **한 갈래도 안 무너졌다**

표1의 「색 가짓수 전→후」가 전부다. 57판 중 **절반 밑으로 떨어진 판이 하나도 없다.**

⚠ **이 자에는 함정이 하나 있다 — 색 가짓수는 줄이면 오히려 는다.**
  LANCZOS 로 줄이면 없던 중간색이 생기기 때문이다. 실제로 제브라 135,078 → 198,809,
  하프문 25,748 → 48,760 처럼 **늘어난 갈래가 넷** 있다. 그래서 이 숫자만으로는
  「살았다」를 못 말한다. 그래서 자를 **두 개 더** 댔다:

- **굵은색 가짓수** (채널마다 위 5비트만 보고 센다 — 잡티를 버리고 색의 갈래만 센다).
  까만 그림은 여기서도 한 가지로 무너지므로 자로서의 성질은 그대로다.
  57판 전부 유지된다(제일 많이 준 것이 차콜 1,579 → 1,307 = 83%).
  ★ 차콜이 준 것은 **JPEG 때문이 아니다** — 같은 자리를 **무손실 PNG 1024** 로 만들어도
    884 → 586 이 된다(단품 실측). 즉 어두운 잎의 잔결이 **줄이기 자체**로 무뎌지는 것이고,
    JPEG q88 은 오히려 672 로 더 남긴다. 형식 탓으로 읽지 말 것.
- **PSNR** — 텍스처끼리 37.2~44.2 dB. 제일 낮은 제브라도 37.2 dB 다.

### ② 화면으로 — **57판을 전부 다시 렌더해서 짝지어 봤다**

## 8. 박사님 판단이 필요한 것

| | 무엇 | 잰 값 |
|---|---|---|
| ① | **원본 428.4MB 를 저장소에 남길까** | 지금 `_orig/` 에 두었다. 그러면 저장소가 428.4 + 33.8MB 를 같이 진다. 원본을 저장소 밖 아카이브로 빼면 33.8MB 만 남는다. ⚠ 「생성물은 묻지 말고 assets 에」가 있어 **안 뺐다** |
| ② | **`skins/*_base_color.png` 101장 511.1MB** | **코드가 한 줄도 안 읽는다**(전 저장소 grep 결과 참조가 0건). GLB 안에 이미 들어 있는 텍스처의 원판이다. 저장소에서 제일 큰 덩어리인데 **내려받는 사람은 0바이트도 안 받는다** — 둘 것인지 아카이브로 뺄지 |
| ③ | **`_rejected/` 45개 121.6MB** | 같은 성질. 안 쓰이고 안 내려간다 |
| ④ | **WebP 로 더 줄일까** | 1024 WebP q86 이면 33.8MB → **약 23MB**(30% 더). 브라우저 로딩은 확인했다. 다만 무늬가 메인이라 형식 위험을 안 지려고 JPEG 로 뒀다 |
| ⑤ | **확대창에서 8배까지 당길 수 있는 것** | 8배로 당기면 잎이 약 2,900px 이라 **원본 2048로도 모자란다.** 지금 1024는 기본 배율(367px)에 맞춘 값이다. 크게 당겨 보는 놀이가 중요하면 그 갈래만 2048을 따로 두는 길이 있다 |
