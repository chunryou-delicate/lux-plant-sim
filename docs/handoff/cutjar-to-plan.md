# 삽수를 방에 그린다 — 유리 수경병 · 검은 모종포트 (2026-08-16)

> 고친 파일은 **`src/game/room_view.js` 하나**다. `game.html` 은 한 글자도 안 건드렸다.
> 새로 만든 것은 `tools/probe_cutjar.mjs`(재는 자)와 `docs/handoff/img/cutjar_*.png`(사진) 뿐이다.

## 0. 무엇이 잘못돼 있었나

박사님 원문:

> *"삽수 결과가 드래그 안 해도 자동으로 화분으로 옮겨져서 추가 화분이 생겨버렸네.
> 저렇게 되면 안 되지. **유리수경병으로 보여야지.**"*

`game.html` 은 삽수를 방에 세울 때 `kind:'monstera'` 를 넘기고 있었다. 그쪽 주석이
까닭을 적어 두었다 — *"room_view.buildPlantGroup 은 모르는 kind 를 던지고, 그 파일은
다른 작업자 것이라 손대지 않는다."* 그래서 **삽수가 작은 몬스테라 화분으로 보였다.**
안 고친 게 아니라 **고칠 수 없는 자리에 있었다.**

이제 그 파일에 두 갈래를 뒀다.

| kind | 무엇 | 코어의 이름 | 그림 |
|---|---|---|---|
| `cutjar` | **유리 수경병** — 병 + 물 + 잘린 줄기 + 물속의 흰 뿌리 | `CONTAINERS.jar` | `assets/pots/pot_glassjar.glb` |
| `cutpot` | **검은 모종포트** — 포트 + 흙 + 잘린 줄기 | `CONTAINERS.soil` | `assets/pots/pot_nursery_black.glb` |

## 1. ★★ game.html 이 넘겨야 하는 spec — **최종 계약**

> 2026-08-16 저녁 갱신 — 박사님 *"기존에 자랐던 거 가지 그대로 잘라서 넣어줄래?"* 를 받아
> **잎별 칸 셋**과 **줄기 칸**이 늘었다. 아래가 최종이다.

```js
const cont = CONTAINERS[c.container] || {};
const seed = (S.sim && S.sim.seed) || 0;
const spec = {
  kind:       c.container === 'jar' ? 'cutjar' : 'cutpot',
  potId:      c.id,
  potD:       cont.realMaxM || 0.12,
  rooted:     c.status !== 'rooting',      // 뿌리가 났나 — 병 속에 보인다

  /* ★ 잘라 온 그 가지 그대로 — 셋은 **같은 자리의 같은 잎**이다(아래→위) */
  leafVarie:  c.leafVarie,                 // [false, true, …]  ← 길이가 잎 수의 정본
  leafGrades: c.leafGrade,                 // ['plain'|null, 'halfmoon', …]
  leafSkins:  c.leafVarie.map((v, i) =>    // 화분이 그 잎에 쓰는 **바로 그 그림**
    v ? (leafSkinsFor(c.leafGrade[i], seed, c.id, i) || {}).midSkin || null : null),

  stem:       c.source && c.source.stem    // 'pink' | 'thick' | 'main'
};
roomView.setPlantAt(c.id, c.at, spec);     // 또는 setPlant(c.slotId, spec)
```

칸마다의 규약:

| 칸 | 받는 값 | 안 주면 | 그림에 어떻게 나오나 |
|---|---|---|---|
| `kind` | `'cutjar'` · `'cutpot'` | — (필수) | 모르는 이름이면 **던진다**(일부러 그렇게 뒀다) |
| `potId` | 삽수 id | null | `free:{id}` 열쇠·이동·탭이 이 값을 탄다 |
| **`leafVarie`** | `c.leafVarie` (참/거짓 배열) | 아래 옛 길 | **길이가 잎 수다.** 아래(오래된 잎)→위(생장점) |
| **`leafGrades`** | `c.leafGrade` (등급 id·null) | null | 그 자리 잎을 **그 등급의 무늬 그림**으로 그린다 |
| **`leafSkins`** | `leafSkinsFor(...).midSkin` (또는 `.matSkin`) | null | **있으면 이게 이긴다** — 화분과 같은 그림이 된다 |
| **`stem`** | `c.source.stem` | `thick` 과 같음 | 줄기 굵기 (pink 0.9cm · thick 1.2cm · main 1.5cm) |
| `rooted` | true/false | false | **병에서만** 보인다 — 물속에 흰 뿌리 6가닥 |
| `potD` | `CONTAINERS[*].realMaxM` | 0.13 / 0.12 | 자리 지름 상한 |
| `leaves` · `variegated` | 숫자 · 참/거짓 | 1 · false | **옛 길.** `leafVarie` 가 있으면 안 본다 |

★ **`leafSkins` 는 `midSkin` 을 권한다** — 까닭은 §7-2 에 재서 적었다. `matSkin` 을 줘도
  받아 준다(방뷰가 그 등급의 중간잎으로 옮겨 그린다). 둘 다 없으면 등급 대표로 떨어진다.
★ **`growthDays` 는 안 넘겨도 된다.** 삽수는 날짜로 안 자란다 —
  `game.html:8771` 의 `Math.min(120, 34 + c.days)` 는 몬스테라 조립기를 달래려던 임시 값이고
  새 갈래는 그 칸을 아예 안 읽는다.
★ **셋 다 없어도 안 던진다.** 옛 세이브(`leafGrade` 가 없는 판)는 예전 그림으로 조용히 떨어진다.
  이상한 값 아홉 가지를 넣어 봤고 **하나도 안 던졌다**(§7-4 표).

⚠ **잎 수 상한은 6장이다**(2 에서 늘렸다 — 삽수는 자란다). 넘으면 **화면이 덜 그린다** —
  `userData.cut.leavesTrue` 에 진짜 수가 남고 재는 자가 그 어긋남을 말한다.
  잎 한 장이 **4천 삼각형**이라 그 위는 폰에서 값이 안 맞는다. 지금 넘을 길은 사실상 없다.
⚠ **병은 코어가 잎 1장까지만 받는다**(`METHODS.water.maxLeaves === 1`). 여러 장은 흙 포트 몫이다.
⚠ **잎별 칸이 바뀌면 방이 다시 짓는다** — `needsRebuild` 의 `cutLookKey` 가 배열까지 통째로 본다.
  개수만 봤으면 「두 장인데 **위 잎만** 무늬가 됐다」가 화면에 안 온다 — 삽수가 자라면서
  실제로 일어나는 일이다. `sown`(무순)·`count`(시루)가 겪은 그 함정과 같은 자리다.

| | 렌더 중앙값 | 드로우콜 | 화면 |
|---|---|---|---|
| **투명 + 불투명도**(고른 길) | 0.6 ms | 27 | 유리·물·물속 줄기·뿌리가 다 보인다 |

## 3. 그림을 어떻게 만들었나 — **있는 GLB 를 썼다**

§2.7 의 *"그림이 없다고 하기 전에 GLB 부터 찾아라"* 를 그대로 따랐다. 넷 다 manifest 에 있다.

| 쓴 것 | 무게 | 왜 |
|---|---|---|
| `pots/pot_glassjar.glb` | **360삼각형 · 텍스처 0장** | 노드가 `glass`·`water` 둘이라 **물까지 들어 있다.** 물 높이를 GLB 에 물어서 쓴다 |
| `pots/pot_nursery_black.glb` | 3,591삼각형 | 검은 모종포트 그 물건 |
| `monstera/monstera_leaf_young.glb` | 3,993삼각형 | plant_grow 의 `leaf_young` 과 **같은 파일** |
| `monstera/skins/monstera_leaf_young_albo.glb` | 3,983삼각형 · 253KB(그림 내장) | `leaf_young_albo` 와 같은 파일. 확대창의 무늬와 **같은 그림** |

**그 자리에서 만든 것은 셋뿐이다** — 잘린 줄기(원기둥) · 자른 자리(원반) · 물뿌리(원기둥).
까닭: **「잘린 줄기」 에셋이 없다.** `stem_early.glb` 는 뿌리에서 올라오는 온전한 줄기라
«자른 자리»가 없고 951KB 다. 2cm 짜리 조각에서 그 차이는 안 보인다.
물뿌리개가 쓰는 것과 같은 구조다(§ensureCanAsset) — GLB 를 못 실으면 원기둥으로 떨어진다.

### 크기를 어떻게 정했나

- **용기 지름**은 코어 값이다(0.13 / 0.12). 지어낸 숫자가 아니다.
- **잎은 실물보다 작게 그린다.** manifest 의 어린 잎은 `real_max_m 0.18` 인데, 그대로 세우면
  잎(0.18)이 병(0.13)보다 커서 **화면에서 병이 안 읽힌다.** 박사님이 보고 싶다 하신 것은
  «유리 수경병»이다. ⇒ **0.12m 로 줄여 그린다.** 무순 재배판을 0.4327 → 0.20 으로 줄여
  그린 것과 **같은 사고**다(§MUSUN_D): 에셋은 안 건드리고 그릴 때 줄인다.

### 사진 보고 세 번 고친 것 (「고쳤다」를 화면 확인 없이 안 썼다)

1. **잎이 병목을 뚫고 나왔다.** 줄기 길이를 «물 면 위 5.5cm» 로 잡았더니 줄기 끝이
   병 안에서 끝났다. ⇒ **아가리 높이를 GLB 에 물어서** 그보다 5.5cm 위까지 세운다.
2. **검은 포트에 «흰 흙»이 담겼다.** 흙을 5mm 아래 → 1.4mm 아래 → 아가리에 딱 맞춰
   세 번 옮겨도 그대로였다. 장면에서 메시를 훑어 재 보니 이 GLB 는 **실사 스캔이라
   안쪽 바닥이 크림색으로 막혀 있고 그 뚜껑이 bbox 꼭대기와 같은 높이**였다 —
   z-싸움에서 크림이 이겼다. ⇒ 흙을 **아가리 위로 조금 봉긋하게** 올렸다.
3. **그 흙이 이번엔 날아갔다.** 흙 윗면은 해를 정면으로 받는 면이라 `0x4b3a2c` 가
   화면에서 크림색이 됐다. 잎은 세워져 있어 같은 빛에서도 안 날아간다 —

## ★ 8. 물뿌리개 손잡이가 손에서 12.38cm 떠 있었다 (2026-08-16 저녁 · 셋째 판)

### 8-1 무엇이 얼마나 떠 있었나 — **두 겹이었다**

**⓵ 손에 붙는 것이 손잡이가 아니라 «원점»이었다.**
`runAct` 가 `can.position.copy(손)` 을 했는데, 이 물뿌리개의 원점은 **몸통 밑면 한가운데**다
(§생김새 규약). 손잡이는 거기서 **뒤로 6.4cm · 위로 10.6cm** 떨어져 있다.

| | |
|---|---|
| 손잡이 로컬 자리 | `(-0.064, 0.106, 0)` m |
| 주둥이 로컬 자리 | `(0.193, 0.138, 0)` m |
| ⇒ **원점에서 손잡이까지** | **12.38 cm** — 캐릭터 키 1.40m 의 **8.8%** |

★ 이 값은 **각도와 무관하다**(회전은 길이를 안 바꾼다). 그래서 붓든 안 붓든 늘 12.38cm 였다.

**⓶ 그걸 고쳐도 6.07cm 가 남았다 — 그리고 그게 진짜 원인이었다.**
처음에는 「돌린 뒤에 손잡이가 실제로 어디 갔는지 재서 그만큼 옮기는」 길로 고쳤다.

| 잰 것 | 값 |
|---|---|

### 8-2 그래서 어떻게 고쳤나 — **베끼기를 그만두고 매달았다**

물뿌리개를 방(`houseGroup`)에 두고 매 프레임 손 자리를 베끼던 것을 **손 뼈의 자식**으로 바꿨다.

- 손잡이 점(`__can_grip`)에 이름을 달고, 그 점이 뼈 원점에 오도록 물뿌리개를 뒤로 물린다 —
  **원점이 어디에 있든 상관없어진다**(GLB 로 갈아 끼워도 그대로 산다)
- 각도는 손을 따라 돌면 안 되므로(화분을 겨눠야 한다) **월드로 원하는 각을 만들고 손의 각을 나눈다**
- 뼈에 실린 배율은 되돌려서 실물 크기를 지킨다

  자리는 구조적으로 정확하고, 각도 오차는 **몇 도**라 눈에 안 띈다. 박사님이 말씀하신 것은 자리다.
- 기존 검사는 고치기 전과 **같다**: `test_pots` 69/70 · `test_roomview_place` 67/74 ·
  `test_musun_view` 17/21 (전부 이 일과 무관한 옛 상수 문제다).

## 6. ⚠⚠ 이 일의 코드는 **엉뚱한 커밋에 실려 있다** — `357c2c4`

내 파일을 `git add` 로 올려 두고 커밋하기까지의 몇 초 사이에, **다른 창이 `git add .` 로
내 색인까지 통째로 쓸어 담아 제 커밋으로 만들었다.** 그래서 이 일의 코드·사진·재는 자가

```
357c2c4  오늘 배운 것을 못 박았다 — 커밋 확인 · 재는 자가 거짓말하는 길 셋
```

라는 **전혀 다른 제목** 밑에 들어가 있다(그 커밋 13개 파일 중 11개가 이 일 것이다).
`git log --oneline -- src/game/room_view.js` 로 찾으면 그 줄이 나오는데,
제목만 보고는 **삽수 일이 여기 있다는 것을 아무도 못 찾는다.**

- 되돌리지 않았다. 다른 창이 이미 그 커밋 위에서 일하고 있어 역사를 고치면 그쪽이 깨진다.
- 대신 **여기 적어 둔다.** 이것이 이 저장소의 `git add .` 금지 규칙이 막으려던 바로 그 일이고,
  실제로 났다는 기록이 있어야 규칙이 산다.
- ★ 하필 그 커밋의 제목이 *"커밋 확인"* 이다.
