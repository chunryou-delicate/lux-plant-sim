## 2.5 ★ 놓을 자리(노란 칸) — 내가 틀리게 옮긴 걱정을 여기서 지운다

**「칸을 잘게 나누면 큰 화분이 갈 곳을 잃는다」는 틀렸다.** 2026-08-11 에 내가 그렇게 보고했고
박사님이 바로잡으셨다: *"큰화분이 왜 갈곳을잃어? 1개반 2개칸 4칸 차지하먄되자나"*

맞는 말이고, **그 계통이 이미 `src/game/place.js` 에 다 있다.**

| | |
|---|---|
| `GRID_UNIT = 0.05` | 크기를 세는 최소 칸 |
| `unitsFor(m)` | 길이 → **칸 수**(`ceil`) |
| `snapSpan(center, size)` | **앞 모서리**를 격자선에 맞춘다 — 중심에 맞추면 짝수 칸짜리가 반 칸 어긋나 정수 점유가 깨진다 |
| `cellBox(rect)` | 발자국이 차지하는 **칸 상자** `{i0,j0,ni,nj}` — 「겹침 판정을 정수로 만든다」 |
| `snapAngleDeg` | 90° 단위 (45°면 정수 점유가 무너져서) |

0.25 격자로 치면 무순 재배판(0.43)은 **2×2 = 4칸**, 콩나물 시루(0.24)는 1칸, 시루 무리(0.97)는 16칸이다.

⚠ **그런데 이걸 가구에만 쓴다.** `snapFurniture → snapSpanStep` 으로 가구는 이미 정수 칸 점유로
겹침을 판정한다(`room_view.js:2695`). 화분 쪽만 옛 모델 —— **자리 하나 = 점 하나 + `maxPotD` 한도 +
찼나/비었나** —— 에 남아 있다. 그래서 책상 윗면 0.72㎡ 에 점이 둘뿐이다.

⇒ **할 일은 새로 짓는 게 아니라 「가구가 이미 쓰는 자를 화분에도 쓰는 것」이다.**

진짜로 남는 걸림돌은 둘뿐이다:

1. **검사 9개가 「14칸」을 박아 두었다** — DLI 표까지 슬롯 이름별로 얼려 놨다. 다시 뽑아야 한다
   (`test_banjiha_profile:70` · `test_lampaim:138` · `test_lampswitch:284` · `test_headroom:97` ·
    `test_floorlight:148` · `test_musun_view:146` · `test_multisiru:159,418` · `test_lampmove:100` · `test_oneroom_room:108`)
2. **세이브가 `banjiha-desk:1` 같은 이름을 저장한다**(`save.js` 여섯 곳) — 번호 뜻이 바뀌면
   **옛 판의 화분이 조용히 다른 자리로 간다.** 없는 이름은 옮겨 주지만 **뜻만 바뀐 경우는 아무도 못 잡는다**

밝기 계산이 느려지는 건 걱정거리가 아니다 — 온실 창턱이 이미 112칸으로 돈다.

## 8. 창을 어떻게 굴리나

**VS Code 의 옛 여섯 창(growth·leaf·char·house·plan·core)은 깨우지 않는다.**
그 구조는 조각을 따로 만들던 때의 것이고, 지금은 조각들이 서로 물려 있어 나눌 금이 없다.
게다가 08-01~04 에 멈춰 있어 깨우면 **낡은 믿음으로 판단한다.**

**마스터 창 하나 + 워커**로 간다. 워커 규칙 넷:

1. **보고를 짧게 받는다** — 상세는 인계 문서, 나에게는 「바뀐 것 · 실측 · 판단필요 · 못 한 것」만
2. **동시에 둘까지** — 합치는 건 어차피 직렬이다
3. **마스터는 큰 파일을 안 든다** — 작은 수술은 직접, 파일 하나를 통째로 뜯는 일은 워커
4. **차기 전에 넘긴다** — 꽉 차서 급히 넘기지 말고 이 파일을 갱신해 두고 넘긴다
