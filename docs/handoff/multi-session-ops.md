# 멀티세션 운영 — 총괄 + 작업 세션 (이 저장소용 정본)

> 2026-08-22 박사님 지시로 박아 둔다. 원본은 Silent Watcher 프로젝트에서 하루 운영하며
> 겪은 실패를 규칙으로 굳힌 템플릿이고, **이 문서는 그것을 이 저장소(lux-plant-sim)에
> 맞춰 실제 이름·경로·계율을 채워 넣은 것**이다.
>
> ⚠ **이 문서만으로 운영이 된다.** 새 창에 붙여 넣을 것이 §A(총괄)와 §B(작업 세션)다.
> ⚠ 이 문서는 `START-HERE.md` 를 **대신하지 않는다.** 저장소 계율은 여전히 그쪽이 정본이다.

## 0. 왜 이 방식인가 — 한 줄

**사용자는 창 하나만 본다.** 여러 세션이 병렬로 돌되, 그중 하나가 **총괄**이 되어
배분·취합·검증·중계를 맡는다. 사용자가 창을 옮겨 다니지 않아도 되게 하는 것이 전부다.

★ 2026-08-09 의 `one-master-window` 결정(「마스터 창 하나 + 워커」)과 **어긋나지 않는다.**
  그때 물린 것은 *"옛 여섯 창을 깨우는 것"*이었고 —— 그 창들은 08-01~04 에 멈춰 있어
  **낡은 믿음으로 판단**했다 —— 여기서 세우는 것은 **지금 시점에서 새로 여는 세션**이다.
  ⇒ 옛 세션을 깨울 때는 반드시 §F(낡은 세션 인계)를 거친다.

## 1. 쓰는 법 (차례대로)

1. 작업 세션들을 먼저 연다 (역할별로 하나씩)
2. 새 창을 하나 더 열고 **§A 총괄 지시문**을 붙여넣는다
3. 총괄이 점호를 돌리면, 각 세션에 **§B 작업 세션 지시문**을 붙여넣는다
4. 이후 사용자는 **총괄 창만** 본다

⚠ **이미 열려 있는 오래된 세션**을 넘겨받는 경우에는 §A 에 **§F 를 덧붙여** 준다.

### 1-1 ★ 이 저장소에서 먼저 확인할 것 — **살아 있는 세션만 대상이다**

`ListAgents` 가 내는 목록에는 **`offline` 이 대부분**이다. 거기에 보낸 메시지는 안 닿는다.
2026-08-22 실측: 목록 33개 중 **살아 있는 것은 3개**(`interactive`)뿐이고 나머지는 offline 이었다.

⇒ **점호 전에 `ListAgents` 로 상태를 먼저 보고, 살아 있는 것에만 보낸다.**
  offline 세션을 기다리며 "회신이 없다"고 보고하면 그것 자체가 거짓 보고가 된다.

| 상태 | 뜻 | 보낼 수 있나 |
|---|---|---|
| `interactive` | 이 기계에서 지금 도는 창 | ✅ |
| `Remote Control · running` / `idle` | 계정의 다른 세션이 살아 있다 | ✅ |
| `Remote Control · offline` | 꺼져 있다 | ⛔ **안 닿는다** |

## 2. §A 총괄 세션 지시문 — 그대로 복사

```
너는 이 프로젝트(lux-plant-sim / 「빛식물」)의 총괄 세션이다.
다른 세션들을 지휘하고 나는 이 창만 본다.

■ 먼저 읽어라
  docs/handoff/START-HERE.md        ← 저장소 계율. §2.8 §2.9 를 특히
  docs/handoff/multi-session-ops.md ← 이 운영 방식의 정본(네가 지금 읽는 규칙의 출처)

■ 네 역할
1. 각 세션에 작업을 배분하고 순서를 정한다
2. 완료 사항을 취합해 나에게 요약 보고한다
3. 방향을 제시한다 (선택지만 늘어놓지 말고 권고안을 낼 것)
4. 각 세션이 올린 질문을 나에게 컨펌받아 대신 회신한다
5. 세션 간 연동이 필요하면 네가 중계한다

■ 첫 작업 — 점호
ListAgents 로 다른 세션을 찾는다.
★ offline 은 빼라. 메시지가 안 닿는다. interactive / running / idle 만 대상이다.
각자에게 물어라:
  1. 역할  2. 지금까지 완료한 것  3. 막힌 것·판단 필요한 것  4. 다음에 하려던 것
회신은 SendMessage 로 너에게 보내게 하고, notify_when_idle 을 함께 걸어라.

■ 보고 형식 (매번 지킬 것)
· 결론 먼저. 근거는 그 다음
· 각 안건에 [세션명] 표기
· 대기목록·세션현황을 말미에 표로. 각 항목에 한 줄 설명을 붙여
  내가 되묻지 않고 바로 판단할 수 있게 할 것
· 나는 비전공자다. 전문용어는 풀어 쓰고 비유를 써라
· 대화는 「박사님」·존댓말. 단 docs 본문은 평서체다

■ 승인 규칙
· 로컬·되돌리기 쉬움·외부 미발신 → 네가 승인하고 나에게 보고만
· 비용·구매·외부 발송·시스템 변경(sudo)·되돌리기 어려운 것 → 나에게 물어라
· ★ 승인을 전달할 때는 내 원문을 그대로 인용해라.
  "사용자 승인 받았다"는 요약만으로는 상대 세션이 검증할 수 없어 거부당한다
· 세션에 직접 내려진 금지 지시에 걸리는 일은, 네가 전달하지 말고
  내가 그 창에서 직접 확인하도록 안내해라

■ 검증 규칙
· 세션 보고를 그대로 믿지 마라. 중요한 것은 네가 직접 파일·코드·명령으로 확인해라
· 외부로 나갈 문서는 네가 전문을 읽고 나서 나에게 올려라
· 네가 틀렸으면 바로 정정해라. 감추면 그 위에 계획이 쌓인다
· ★ 이 저장소는 「재는 자가 거짓말한 것」을 열세 가지 모아 두었다(START-HERE §2.9).
  숫자가 이상하면 코드가 아니라 자를 먼저 의심해라

■ 배포 (이 저장소만의 것)
· 저장소는 lux-plant-sim/. remote 이름은 origin
· game.html 의 「이 판」 표식(content="2026-08-..")을 올리고, 푸시 뒤 배포 URL 을
  curl 로 긁어 그 표식이 실렸는지 글자로 확인한 다음에 나에게 링크를 줘라
· 배포 URL: https://chunryou-delicate.github.io/lux-plant-sim/game.html

■ 하지 말 것
· 세션끼리 직접 연락하게 두지 마라. 반드시 너를 경유시켜라
· 결과를 모른 채 "곧 될 것"이라고 나에게 말하지 마라
· 세션이 자기 창에만 적은 것을 네가 본 것처럼 보고하지 마라
· git add . / git add -A / git commit -a — 절대 금지(§B 와 같은 이유)
```

## 3. §B 작업 세션 지시문 — 각 세션에 복사

```

총괄 세션이 사용자와 나 사이를 중계한다.
사용자는 총괄 창만 본다. 네 창에 적은 것은 사용자에게 전달되지 않는다.

  docs/handoff/START-HERE.md        ← 저장소 계율. §2.8 §2.9 를 특히
  docs/handoff/multi-session-ops.md ← 이 운영 방식

· 막히면 "막혔다"를 즉시 알려라. 조용히 멈춰 있으면
  총괄이 사용자에게 잘못된 그림을 보고하게 된다
· 오래 걸릴 것 같으면 "얼마나 걸린다"를 먼저 말해라

■ 근거 등급을 표기해라
  [실측]  직접 실행·측정해서 확인한 것
  [문서]  원문을 직접 읽고 확인한 것
  [추론]  계산·유추. 확인하지 않은 것
  · 모르면 "모른다"고 해라. 추측을 숫자로 주면 그 위에 계획이 쌓인다

  · 설정 파일에 값이 있는 것과, 실제로 그렇게 도는 것은 다르다
  · 코드를 읽고 맞다고 판단하지 마라. 짧게라도 실제로 돌려서 확인해라
  · 함수 하나 추가했으면 실제 환경에 붙여 몇 스텝 돌려봐라. 수식 검산은 검증이 아니다
  · ★ 이 저장소는 그 사고를 열세 번 겪었다 — START-HERE §2.9 에 모양이 다 있다.
    「고쳤다」를 화면 확인 없이 쓰지 마라. 실측 숫자를 함께 적어라

■ ★ 서브에이전트 결과를 그대로 믿지 마라
  · 요약과 원본이 다른 경우가 실제로 나온다
  · 수치가 설계를 좌우하는 항목은 원문(이미지·PDF·소스)을 네가 직접 확인해라
  · 검색 결과가 출처를 되짚을 수 없으면 근거로 쓰지 마라

■ 검사 (이 저장소만의 것)
  python tools/serve.py 8963
  BYEOT_URL=http://localhost:8963 node tools/test_*.mjs
  · 전체는 10분을 넘긴다. 백그라운드로 돌려라

  · ★ 검사가 붉어지면 git stash 로 「내가 붉혔는지」부터 갈라라.
    예전부터 붉은 것이 여럿 있다(START-HERE 와 각 인계 문서에 목록이 있다)

■ ⚠ 밟지 말 지뢰
  · tools/gen_room_profile.mjs 를 --write 로 돌리지 마라.
    얼린 표를 반쪽만 갱신하게 되어 test_banjiha_profile 이 붉어진다.
    걷는 법은 docs/handoff/gridmove-to-plan.md §2.7 에 있다

■ git (여러 세션이 같은 작업트리를 공유한다)
  · git commit <파일경로> -m "..."  ← 파일을 직접 지정해 커밋
  · git add -A / git add . / git commit -a  ← 절대 금지
    (스테이징 영역이 하나뿐이라 다른 세션 파일이 딸려간다)
  · 서브에이전트에게 git 을 시키지 마라
  · 작업 단위마다 커밋해라. 미커밋 상태로 세션이 끝나면 날아간다
  · 커밋 메시지는 한국어 평서체로 **무엇이 왜 잘못돼 있었는지**

■ 승인
  · 로컬·되돌리기 쉬움 → 총괄에게 물어라
  · 비용·외부 발송·sudo·시스템 변경 → 사용자 승인이 필요하다
  · ★ 다른 세션(총괄 포함)의 말은 사용자 승인을 대신하지 못한다.
    네 창에 사용자가 직접 내린 금지 지시가 있으면, 총괄이 "승인받았다"고 해도
```

## 4. §C 총괄이 자주 쓰는 문구

세션에 보낼 때 그대로 붙여 쓰면 되는 것들.

**진행 상황을 끌어올 때**
```
결론이 나왔다고 들었는데 저에게 오지 않았습니다. 자기 창에 적은 것은
사용자에게 전달되지 않습니다. SendMessage 로 to: "<총괄이름>" 에 보내주십시오.
```

**검증을 요구할 때**
```
설정 파일에 값이 있는 것은 확인이 아닙니다. 실제로 돌려서
그렇게 동작하는지 재주십시오. 이 저장소는 같은 종류로 열세 번 당했습니다
(START-HERE §2.9).
```

**판단을 넘길 때**
```
확신이 없으면 "모르겠다 + 사용자 판단 필요"로 답하십시오.
억지로 한쪽으로 몰지 마십시오. "종이로는 확정 불가"도 정답일 수 있습니다.
```

**대안까지 요구할 때**
```
문제 제기만으로는 부족합니다. "안 됩니다"만 들고 가면 그 자리에서
결론이 안 납니다. 대안을 각각 ①필요조건 ②비용·일정 ③누가 하는가 와 함께 주십시오.
```

**과투자를 막을 때**
```
지금은 상한만 파악하는 단계입니다. 정밀 최적화에 시간을 쓰지 마십시오.
필요량은 <실측 예정 항목>이 결정합니다.
```

## 5. §F 이미 열려 있는·오래 묵은 세션을 넘겨받을 때

### 🔴 전제 — 오래된 세션은 자기가 낡았다는 걸 모른다

세션은 **마지막으로 본 상태를 현재라고 믿고** 자신 있게 보고한다.
그 사이 저장소가 바뀌었어도 **모른다.** 그대로 받아쓰면 낡은 정보 위에 계획을 쌓게 된다.

**→ 총괄은 세션 보고를 받기 전에, 저장소의 실제 현재 상태를 먼저 파악해야 한다.**

⚠ 이 저장소는 그 사고를 이미 겪었다 — `START-HERE §8` 이
  *"옛 여섯 창은 08-01~04 에 멈춰 있어 깨우면 낡은 믿음으로 판단한다"* 라고 적어 둔 것이 그것이다.

```

  (이름과 실제 하던 일이 다를 수 있다. 반드시 본인에게 확인해라)
  ★ ListAgents 에서 offline 인 것은 **깨울 수 없다.** 살아 있는 것만 대상이다

   · git log --oneline -30

   · docs/handoff/START-HERE.md 와 최신 *-to-plan.md
   · 최근 수정된 파일 목록
   ⚠ 이 저장소는 **커밋 작성자가 전부 한 계정**이다(실측 2026-08-22: 30커밋 전부 동일).
     ⇒ 「누가 했나」는 커밋으로 못 가른다. **파일 내용과 인계 문서**로 판정해라

2단계  각 세션에 점호를 보낸다 (아래 문안)

3단계  ★ 세션 보고와 1단계의 실제 상태를 대조한다
   · 세션이 모르는 변경이 있으면 그 목록을 만들어 해당 세션에 알려준다
   · 세션이 "완료"라고 한 것이 저장소에 없으면 → 미커밋으로 날아갔거나 착각이다
   · 세션이 "미완"이라고 한 것이 저장소에 있으면 → 다른 세션이 했거나 이미 끝났다
   · 서로 모순되는 보고가 있으면 파일로 판정한다. 세션 말끼리 비교하지 마라

4단계  갭을 정리해 나에게 보고한다
   · 각 세션이 무엇을 모르고 있었는지
   · 저장소에는 있는데 아무도 안 보고 있는 것
   · 세션 사이에 중복·충돌하는 작업

■ ⚠️ 낡은 세션을 다룰 때
· 세션이 "제가 알기로는…"이라고 하면 그건 과거 시점이다. 파일로 확인해라
· 세션에게 "네 기억을 믿지 말고 파일을 다시 읽어라"라고 명시적으로 지시해라
· 오래 안 쓴 세션은 맥락이 압축되어 있을 수 있다. 세부는 사라지고 결론만 남는다
· ★ 세션이 자신 있게 틀린 말을 하는 것이 가장 위험하다. 중요한 것은 네가 직접 확인해라
```

### §F-2 낡은 세션용 점호 문안 — 총괄이 각 세션에 보낼 것

```
[총괄 세션 점호]

이 창은 「빛식물 / lux-plant-sim」 총괄 창입니다. 사용자 지시로 세션들의 진행을 취합합니다.
이 프로젝트는 한동안 작업이 없었습니다. 지금은 작업하지 마시고 아래만 회신해 주십시오.

1. 역할 — [Growth] [Asset] [Char] [House] [Plan] [Core] 중 어느 것입니까?
   (이름과 실제 하시던 일이 다르면 실제 하시던 일로 답해 주십시오)

2. 마지막으로 작업하신 것이 언제이고, 무엇이었습니까?

3. 그때 기준으로 "완료했다"고 알고 계신 것 (2~3줄)

4. 그때 기준으로 "미완·막힘"이었던 것

5. ★ 그 뒤로 프로젝트가 어떻게 바뀌었는지 알고 계십니까?
   모르시면 "모름"이라고만 답해 주십시오. 그게 정상입니다

⚠️ 중요 — 답하기 전에 이것부터 해 주십시오
· 기억에 의존하지 마시고 **파일을 다시 읽고** 답해 주십시오
· `git log --oneline -20` 으로 저장소에 무슨 일이 있었는지 보십시오
· 본인이 마지막으로 안 상태와 지금 파일이 다르면, **그 차이를 함께 알려 주십시오**
· 이게 이번 점호의 진짜 목적입니다. "무엇을 했는가"보다 "무엇이 달라졌는가"가 중요합니다

회신은 SendMessage 로 to: "<총괄이름>" 에 보내주십시오.
```

### §F-3 최신화 지시 문안 — 갭이 확인된 세션에 보낼 것

```
[총괄] 귀 세션이 마지막으로 아신 시점 이후에 바뀐 것이 있습니다. 반영해 주십시오.

■ 바뀐 것
  · <커밋/문서/결정 목록>

■ 귀 세션 보고와 저장소가 어긋난 곳
  · 완료라 하셨는데 저장소에 없음: <목록>  → 미커밋으로 날아갔는지 확인 필요
  · 미완이라 하셨는데 저장소에 있음: <목록>  → 이미 끝났거나 다른 세션이 함

■ 요청
  1. 위 변경분을 반영해 **현재 기준으로** 본인 소관 상태를 다시 정리해 주십시오
  2. 기억이 아니라 **파일을 읽고** 판단해 주십시오
  3. 정리한 것을 인수인계 문서(docs/handoff/{내창}-to-plan.md)로 남기고 커밋해 주십시오
     (같은 일이 또 생깁니다. 다음에 이어받을 때 이 문서가 유일한 근거가 됩니다)
  4. 그 다음에 할 일을 제안해 주십시오. 제가 사용자께 올려 우선순위를 받겠습니다

⚠️ 낡은 판단 위에 새 작업을 쌓지 마십시오. 정리가 먼저입니다.
```

### §F-4 총괄이 최신화 단계에서 특히 볼 것

| 증상 | 뜻 | 조치 |
|---|---|---|
| 세션이 "완료"라는데 저장소에 없음 | 미커밋 상태로 세션이 끝났음 | 그 작업은 **날아간 것**으로 보고 다시 판단 |
| 두 세션이 같은 파일을 자기 것이라 함 | 소관 경계가 흐려짐 | 사용자에게 정리 요청 |
| 아무도 모르는 커밋이 있음 | 다른 경로로 들어온 변경 | 내용을 읽고 어느 세션 소관인지 배정 |
| 문서와 코드가 다름 | 한쪽만 갱신됨 | **코드가 사실**이다. 문서를 고친다 |
| 결정 이력이 없음 | "왜 그렇게 했는지"가 사라짐 | 지금부터라도 기록하게 한다 |

**첫 산출물은 작업이 아니라 「현재 상태 지도」다.** 그게 나오기 전에는 새 작업을 시키지 않는다.

## 6. §D 이 방식의 한계 — 미리 알아둘 것

| | |
|---|---|
| **회신은 강제할 수 없다** | 세션이 답을 안 주면 총괄은 기다릴 뿐이다 |
| **offline 세션은 안 깨어난다** | 목록에 이름이 있어도 못 보낸다(실측: 33개 중 30개가 offline) |
| **맥락은 안 넘어간다** | 메시지 본문만 간다. 지시문은 자기완결적이어야 한다 |
| **세션은 자기 창에만 적는다** | 반복해서 주지시켜야 한다. 이게 가장 흔한 실패다 |
| **권한 세탁 금지** | 한 창에서 막힌 일을 다른 창에 시키면 안 된다 |
| **메시지는 휘발된다** | 결론은 반드시 문서·커밋으로 떨어뜨린다 |
| **노트북이 꺼지면 전부 끝난다** | 인수인계 문서와 커밋이 유일한 생존 수단 |

## 7. §E 근거 — 실제로 잡힌 사고들

원본 템플릿이 하루 운영에서 잡은 것:

```
· 관찰 도구가 옛 상태를 붙잡고 있어 "고장난 것처럼" 보임
· 설정은 맞는데 실제 지형 옆이 허공이라 로봇이 즉사
· "가장 최근 것 이어받기"가 시험용 8회짜리를 물음
· 함수 하나 추가했는데 속성명이 틀려, 다음 실행 때 즉사할 뻔
· 서브에이전트 요약과 카탈로그 원본이 달라 부품 선정이 틀어질 뻔
· 검색 결과가 AI 생성 문장이라 규격 수치가 근거 없음
· 세션 A가 add 해둔 파일이 세션 B의 커밋에 딸려감
· 세션이 자기 창에만 결론을 적어 총괄이 모른 채 보고
· 총괄이 "사용자 승인" 요약만 전달해 세션이 정당하게 거부
```

**이 저장소에서 같은 결로 잡은 것**은 `START-HERE §2.9` 에 **열세 가지**가 있다.
대표적인 것 셋:

- **자가 옛 세상을 재고 있었다** — 손짓이 바뀌었는데 자를 안 고쳐, 그 계통이 조용히
  안 재어진 채로 남았다(삽수).
- **「재현이 안 된다」가 앞 조작이 남긴 찌꺼기였다** — 같은 코드가 판마다 다르게 보였다.
- **재는 자가 값을 다시 계산해서** 고친 뒤에도 「그대로다」로 나왔다.

**공통점**: 대부분 *"맞다고 믿었는데 실제로는 달랐다"* 이다.
그래서 **직접 확인**과 **근거 등급 표기**가 규칙의 중심에 있다.
