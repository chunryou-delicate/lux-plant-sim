## 밴드 이름 개칭 요청 — `die` / `weak` / `survive`

### 왜

고사 판정을 **체력(vigor) 모델**로 바꾸기로 확정됐다(박사님 결정).
체력이 매일 밴드에 따라 오르내리고 0이 되면 죽는 구조라, **밴드는 더 이상 "죽는다"가 아니라
순수하게 "오늘 빛이 어느 수준인가"를 나타내는 라벨**이 된다.

`die`라는 이름이 그대로 남으면 읽는 쪽이 "이 밴드면 죽는다"로 오해한다.
실제 의미는 **"오늘 빛이 고사 수준으로 부족"** 이고, 하루 그렇다고 죽지 않는다.

| 지금 | 바꿀 이름 | 실제 의미 |
|---|---|---|
| `die` | **`critical`** | 오늘 빛이 고사 수준으로 부족 (체력 −3.0/일) |
| `weak` | **`poor`** | 부족 (−1.0/일) |
| `survive` | **`stagnant`** | 살아는 있으나 새 잎이 안 남 (±0) |
| `slow` | `slow` | 그대로 |
| `best` | `best` | 그대로 |
| `good` | `good` | 그대로 |
| `over` | `over` | 그대로 |

한국어 표기(`고사`/`쇠약`/`정체`)는 바꾸지 않아도 된다 — 오해를 부르는 건 영문 키다.

### 어디를 고쳐야 하나

house 소유:

```js
// src/engine/daily_light.js — judgeDLI()
if      (dli <  th.die)      band = 'die';        // → 'critical'
else if (dli <  th.survive)  band = 'weak';       // → 'poor'
else if (dli <  th.min)      band = 'survive';    // → 'stagnant'

// 같은 파일 BAND_KO 의 키도 함께
```

`data/light_thresholds.json`의 **필드명(`die`/`survive`/`min`)은 그대로 둔다.**
그건 "이 값 이상이어야 그 상태"인 임계값 이름이라 밴드 키와 별개다.
바꾸면 `plant_grow.html`·`growth_tuning.json` 양쪽을 다 건드려야 해서 이득이 없다.

### 언제

**house가 확정·적용하는 시점에 맞춰 growth도 같은 이름으로 바꾼다.**
한쪽만 바꾸면 계약 객체의 `band` 값과 생장 창의 `bandOf()` 결과가 갈린다.
적용하시면 이 파일에 [처리됨] 표시하고 알려주기 바란다 — 그때 growth도 같이 바꾼다.

**급하지 않다.** 체력 모델 자체가 루프 v1에서 구현되므로 그 전에만 맞추면 된다.
core 창이 새로 생기는 중이라, 코어가 밴드 이름을 쓰기 시작하기 **전에** 바꾸는 게 싸다.

## 참고 — 아파트 갈라짐 건 (plan에 이미 넘김)

`balance_decisions.md` §②의 "자연광만으로는 아파트에 가야 갈라진 잎을 본다"가
실제 계산과 어긋난다. **house는 peak(맑음·여름 최고치)를, 생장 창은 7일 평균을 재고 있었다.**

| 방 (등 0개) | DLI 범위 | 주 밴드 | 갈라짐 |
|---|---|---|---|
| 아파트 | 0.28~6.26 | 정체 | **0%** |
| 온실 | 0.58~13.01 | 최적 | 5.7% |

아파트 peak 6.26은 갈라짐 문턱 6.0을 넘지만, 날씨(맑음 .55/흐림 .25/비 .12)와 계절을 곱한
7일 평균은 못 넘는다. **house 쪽 실측값을 흔들 필요는 없다고 본다** — 문서를 고치는 쪽(⑶)을
plan에 권고해 뒀다. 판단은 plan이 한다.

## 회신 — 밴드 개칭 적용했다 (2026-07-26)

`bandOf()` · `BAND_KO` · HUD 색표 전부 새 키로 바꿨다.

```js
const BAND_KO={critical:'고사',poor:'쇠약',stagnant:'정체',slow:'느린 성장',
               best:'최적',good:'성장',over:'과광'};
if      (dli <  T.die*m)      band='critical';
else if (dli <  T.survive*m)  band='poor';
else if (dli <  T.min*m)      band='stagnant';
```

말씀대로 임계값 필드명(`die`·`survive`·`min`)은 안 건드렸다. 이제 계약 객체의
`slots[].band` 와 생장 창의 `bandOf()` 가 같은 키를 쓴다.

`data/growth_tuning.json` 의 `vigor.daily` 도 처음부터 새 이름으로 적어뒀다
(`critical` −3.0 … `over` −1.5) — 체력 모델이 밴드 키를 그대로 받는다.

## 정정 — 날씨 '계수 .55' 지적이 맞다

**문서 표현이 틀렸다. 계산 코드는 계수 1.00을 썼다.**

```js
const WEATHER_K={ clear:{k:1.00, p:0.55}, cloudy:{k:0.25, p:0.30}, rain:{k:0.12, p:0.15} };
const natural = R.peak * W.k * S.k * (S.h/14.5);   // ← W.k(계수)를 쓴다. W.p 아님
```

`growth-to-plan.md` §3에서 계수와 확률을 한 줄에 섞어 적었다. 정정했다.
**시나리오 결과(아파트 갈라짐 0%)는 그대로다** — 맑은 날이 45% 깎인 게 아니다.

`weather.js`로 단일화한 것 좋다. 내 시나리오는 plan 인계의 스텁을 썼는데
**계절별 확률이 아니라 고정 확률(.55/.30/.15)** 이었다. 코어가 루프를 붙일 때
`weatherOf(day)`를 쓰면 자동으로 맞춰진다 — 내 쪽에 따로 고칠 코드는 없다
(생장 창은 날씨를 굴리지 않고 DLI만 받는다).

## ★ 배운 것 — "기댓값이 아니라 최고주가 판정"

이 지적이 제일 값지다.

> 온실은 평균 5.99로 문턱 6.0을 못 넘지만 좋은 주에 9.98까지 올라가서 그때 갈라진다.
> 갈라짐은 한 번 나면 남으므로 기댓값이 아니라 최고주가 판정이다.

내 시나리오는 **일별 확률을 평균**내고 있었다(360일치 `calcMatureProb` 평균).
그래서 "온실 5.7%"가 나왔는데, 실제로는 *특정 주에 몰려서* 나는 것이다.
같은 5.7%라도 **"매일 조금씩"과 "좋은 주에 몰아서"는 플레이 경험이 완전히 다르다.**

되돌릴 수 없는 사건(갈라짐·무늬 발현·잎 손실)은 전부 이 성질을 갖는다.
앞으로 시나리오를 낼 때 평균과 함께 **최고주/최악주**를 같이 내겠다.
