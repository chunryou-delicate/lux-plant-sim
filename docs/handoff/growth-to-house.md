## 밴드 이름 개칭 요청 — `die` / `weak` / `survive`

### 왜

고사 판정을 **체력(vigor) 모델**로 바꾸기로 확정됐다(박사님 결정).
체력이 매일 밴드에 따라 오르내리고 0이 되면 죽는 구조라, **밴드는 더 이상 "죽는다"가 아니라
순수하게 "오늘 빛이 어느 수준인가"를 나타내는 라벨**이 된다.

`die`라는 이름이 그대로 남으면 읽는 쪽이 "이 밴드면 죽는다"로 오해한다.
실제 의미는 **"오늘 빛이 고사 수준으로 부족"** 이고, 하루 그렇다고 죽지 않는다.

| 지금 | 바꿀 이름 | 실제 의미 |
|---|---|---|
| `die` | **`critical`** | 오늘 빛이 고사 수준으로 부족 (체력 −3.0/일) |
| `weak` | **`poor`** | 부족 (−1.0/일) |
| `survive` | **`stagnant`** | 살아는 있으나 새 잎이 안 남 (±0) |
| `slow` | `slow` | 그대로 |
| `best` | `best` | 그대로 |
| `good` | `good` | 그대로 |
| `over` | `over` | 그대로 |

한국어 표기(`고사`/`쇠약`/`정체`)는 바꾸지 않아도 된다 — 오해를 부르는 건 영문 키다.

### 어디를 고쳐야 하나

house 소유:

```js
// src/engine/daily_light.js — judgeDLI()
if      (dli <  th.die)      band = 'die';        // → 'critical'
else if (dli <  th.survive)  band = 'weak';       // → 'poor'
else if (dli <  th.min)      band = 'survive';    // → 'stagnant'

// 같은 파일 BAND_KO 의 키도 함께
```

`data/light_thresholds.json`의 **필드명(`die`/`survive`/`min`)은 그대로 둔다.**
그건 "이 값 이상이어야 그 상태"인 임계값 이름이라 밴드 키와 별개다.
바꾸면 `plant_grow.html`·`growth_tuning.json` 양쪽을 다 건드려야 해서 이득이 없다.

### 언제

**house가 확정·적용하는 시점에 맞춰 growth도 같은 이름으로 바꾼다.**
한쪽만 바꾸면 계약 객체의 `band` 값과 생장 창의 `bandOf()` 결과가 갈린다.
적용하시면 이 파일에 [처리됨] 표시하고 알려주기 바란다 — 그때 growth도 같이 바꾼다.

**급하지 않다.** 체력 모델 자체가 루프 v1에서 구현되므로 그 전에만 맞추면 된다.
core 창이 새로 생기는 중이라, 코어가 밴드 이름을 쓰기 시작하기 **전에** 바꾸는 게 싸다.

## 참고 — 아파트 갈라짐 건 (plan에 이미 넘김)

`balance_decisions.md` §②의 "자연광만으로는 아파트에 가야 갈라진 잎을 본다"가
실제 계산과 어긋난다. **house는 peak(맑음·여름 최고치)를, 생장 창은 7일 평균을 재고 있었다.**

| 방 (등 0개) | DLI 범위 | 주 밴드 | 갈라짐 |
|---|---|---|---|
| 아파트 | 0.28~6.26 | 정체 | **0%** |
| 온실 | 0.58~13.01 | 최적 | 5.7% |

아파트 peak 6.26은 갈라짐 문턱 6.0을 넘지만, 날씨(맑음 .55/흐림 .25/비 .12)와 계절을 곱한
7일 평균은 못 넘는다. **house 쪽 실측값을 흔들 필요는 없다고 본다** — 문서를 고치는 쪽(⑶)을
plan에 권고해 뒀다. 판단은 plan이 한다.
